This document records what the checks and exit criteria of [M9](milestones.md#m9-git) showed so far, so that the owner can review the plugin Git, ADR-0038 and ADR-0039, and see what remains before v0.4.0. The owner accepted both ADRs and the plugin's two ADRs with the plan (D37). Each section names the checks, where they ran, the result, and what is open.

The runs below were made on 2026-10-20 on the owner's Windows 11 workstation: on Windows with git 2.54.0.windows.1 and WebView2 155.0.4283.62, and in Docker on the same machine for Linux. The Linux runs used the image of `task test:linux`, `rust:1.99` with Debian 13 and its git 2.47.3, with git 2.40.0 and 2.54.0 built from their release tarballs beside it, and Ubuntu 22.04 with WebKitGTK 2.50.4 and git 2.54.0 for the end-to-end tests, as CI's job does. The changes are not committed yet, and they were tested on top of 044bbd0. Nothing of M9 ran in CI or on the owner's Linux machine, and the manual checks with real remotes and signing keys are open (section 9).

## 2. Windows

Checks: `task ci`, which now runs its steps side by side (ADR-0037), and `task e2e` with every spec file. The Rust tests ran through cargo-nextest: 1,123 of the root workspace with 7 that need live services ignored, 137 of the git plugin, 141 of Workers, 50 of SSH, 29 of Images, 5 of the fixture plugin and 1 of the desktop binary.

Result: passed. `task ci` ran twice after the rebase, and every step passed in one run or the other; each run failed in one step, where a test that measures time failed under the load of the steps beside it, and each test passed alone:

- `bounds the time of every text it accepts`, in `tests/apps/desktop/src/lib/utils/markdown.test.ts`, took 868 ms against its bound of 250 ms while Vitest ran beside Clippy and the Rust tests. Vitest alone passed all 450 tests, and in the second run of `task ci` too.
- `every_subscriber_ends_with_the_state_of_a_fresh_snapshot`, a property test of 24 cases with timed subscribers in `crates/mannie-runtime/tests/subscriptions.rs`, ran into nextest's limit of 5 minutes in the second run. It passed ten times alone, the root workspace's 1,123 tests then passed in 30 s, and the rest of the step, the desktop binary's test and the doctests, passed.

Both tests belong to code that M9 does not change, and both became sensitive to load when `task ci` started running its steps side by side.

The end-to-end tests ran on WebView2 155.0.4283.62. Before the rebase, all 22 spec files passed, with the 8 tests of the new Git spec (section 5). After it, 21 passed, the Git spec's included; in `chat-durability.test.ts` the reply that a test stops within a second completed before the stop, and the test after it, which retries the stopped reply, found nothing to retry. The spec passed three times alone.

## 3. Linux

Checks: `task test:linux`, Clippy with `-D warnings` and the Rust tests of the root's workspace and of every plugin's, in Docker with the repository mounted read-only.

Result: passed after the fix of section 7: Clippy of the five workspaces and 1,458 tests in 104 test binaries. The first run failed in the git plugin's test of a hook that refuses a commit.

## 4. Versions of git

Checks: `plugins/git/` with Clippy once, then its tests with each git first on the `PATH`, on Linux: 2.40.0, the oldest that the plugin supports, Debian's 2.47.3, and 2.54.0. The tests run every tool against repositories that the installed git builds, and include the hook coverage test, which installs every client hook as a recorder and checks that each change lists every hook that git started for it, the conflict scenarios of merges, rebases, cherry-picks and reverts, history edits through `merge-tree --write-tree --merge-base`, fetches and pushes through a remote in a folder, and the panel's commands.

Result: passed with each version: 131 unit tests and the 6 tests of the plugin through the harness. Before git 2.54, the plugin reads the hooks from the hooks folder; from 2.54, `git hook list` answers, and both passed the coverage test. On Windows, the same tests passed with git 2.54.0.windows.1. Git for Windows 2.40 was not run.

## 5. End-to-end tests

Checks: `plugins/git/tests/e2e/git.test.ts`, new, with a repository and a remote in temporary folders: the Plugins page lists the installed program that Git runs, and Git turns on; `git_status` runs without asking, and its card lists the changed files; a commit that runs a pre-commit hook asks first, names the hook and its source, runs the hook and commits once allowed; with changes in the workspace allowed, a commit without a hook runs without asking; a push asks for its remote and names the endpoint, "Save rule…" saves a rule for `git push`, and the next push runs without asking; a commit's card opens to its patch; the Git button in the toolbar opens the side panel with the branch, the changed files and the history; and the Tools settings list the rule, which the owner deletes. Axe runs on each step in the light and the dark theme.

Result: passed on WebView2 155.0.4283.62, with every other spec file. The first runs found two defects, both fixed (section 7).

## 6. WebKitGTK

Checks: the Git spec in Docker, as CI's job "End-to-end tests (ubuntu-22.04)" runs the end-to-end tests: Ubuntu 22.04 with WebKitGTK 2.50.4 and its WebDriver, Xvfb, a D-Bus session and GNOME Keyring, Node.js 24.15.0, Task 3.40.1 and tauri-driver 2.1.0, with the validation build made from the work tree in the container.

Result: 5 of the Git spec's 8 tests passed, with axe in both themes: the Plugins page, the hooked commit with its approval, the commit without asking, the push with its endpoint and its saved rule, and the rule in the settings. The 3 others failed where they read the text of an element that clips its text with an ellipsis: the files of the status card, the path in the commit's card, and the label of the Git button. The core's tools spec, run beside it for comparison, passed 10 of its 16 tests. Five of its failures were the same, on the project's name, the profile button, the row of a call and its status line; the sixth, which kills the app, found no tool call after the restart.

The cause is WebKitWebDriver: it returns no text for an element with `text-overflow: ellipsis`, although the element is laid out with its text and WebDriver itself reports it as displayed. A diagnostic run read, for the label of the Git button, an empty text from WebDriver, and "Git: main" as the element's `innerText` in a box of 53 by 19 pixels. Every spec that reads such an element fails on WebKitGTK, the core's as well as the plugin's, so CI's job needs the specs to read those texts another way (section 9).

The first runs had WebKitGTK's DMA-BUF renderer and compositing on, as a desktop with a GPU has them. Then axe measured text in the middle of its fade-in, as nearly white on white, and only 3 of the Git spec's tests and 6 of the tools spec's passed. With `WEBKIT_DISABLE_DMABUF_RENDERER=1` and `WEBKIT_DISABLE_COMPOSITING_MODE=1`, the software rendering of a machine without a GPU, axe found nothing and the results above followed, so CI's machines may need the same. The base image also lacked fonts, which a desktop has; installing them changed none of the results.

## 7. Defects found

- On Linux, git runs a file of the hooks folder only when it is executable. Three tests wrote their hooks without that bit, so on Linux the hook that should refuse a commit never ran and the commit went through. The tests now install hooks through `TestRepository::write_hook`, which sets the bit on Unix. The plugin also counted a hooks folder file that git skips on Unix, and asked about a hook that would not run; it now counts only executable files there, as git does, and a new test checks that such a file is neither listed nor run.
- The side panel's effect that starts reading the repository also read the overview's state, so each read restarted the watch, which read again. The watch now starts untracked, and a new watch ends the one before it.
- "Save rule…" said that a run of git that the rule covers then runs without asking. A rule covers the run of git only, and its change in the workspace still follows the setting for changes, so a push that a rule covered asked again for its write while changes in the workspace asked. The dialog now says so, and the documents of approvals do too.
- The side panel kept a read that failed in place of what it showed, offered no "Try again" for a view, and read a view that had failed only when the panel opened again. A failed read now keeps the value that shows, every view offers "Try again", and each refresh reads the views that were opened again.

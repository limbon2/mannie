## Context

- The owner wants "first class support for an sqlite database for the harness", "something of adminer", for SQLite files that already exist on the owner's machines ([decision D46](../roadmap/milestones.md#5-decisions)). The owner's answers of 2026-11-01 (D46):
  - Only files that the owner registers. Mannie creates no databases.
  - Every conversation and the general child agent see every registered database, and their reads run without asking.
  - The first version changes rows and schema. The owner's view runs a schema statement after a confirmation, and an agent's schema change always asks, with no grant that covers it.
- The design rules this out today:
  - rusqlite is a dependency of `mannie-store` alone (ADR-0009 d2, ADR-0030 d9, ADR-0034 d2, validation V5), and `deny.toml` refuses it anywhere else. The `store` service runs only the statements that a plugin lists, on the plugin's own tables in Mannie's database, under an authorizer that refuses ATTACH, PRAGMA, transactions and more (ADR-0034 d7).
  - `ToolAccess` names a remote command, a path, a program run, a tool of a tool server or a terminal command. None names a statement on a database. A path access shows the owner a file and a mode but never the statement, and a grant for a path covers a folder.
  - No plugin command changes anything on the owner's behalf. ADR-0038 d10 lets a command run a program only to read, Git's panel actions wait for an ADR on how the owner's own action is journaled (`plugins/git/docs/panel-actions.md`), and the owner's typing in a terminal is not an operation (ADR-0053 d6).
  - A plugin command takes handles, never paths (ADR-0034 d5), and the native dialog chooses an export's destination, since the webview supplies no path (ADR-0040 d5). The `file-dialog` service returns handles that read a file once.
- Facts of this repository, verified on 2026-11-01:
  - rusqlite 0.40.2 with the features `bundled` and `hooks`. libsqlite3-sys 0.38.2 bundles SQLite 3.53.2 and declares `links = "sqlite3"`, so the desktop binary and the worker each hold one SQLite. Its build turns on column metadata, FTS3 and FTS5, JSON, R\*Tree, URI filenames and foreign keys by default.
  - The export journal `exports_operations` holds metadata only, with the states executing, completed, failed and uncertain, and its record is committed before any file is created (ADR-0040 d6).
  - A tool's execution carries a `BackgroundTicket` for a background remote command, without which the service starts nothing (ADR-0041 d11).
  - Mannie's data and log folders are protected: an access inside them asks with `MannieFolder` and offers no grant, unless the conversation is in full access (ADR-0029 d3).
  - The plugin ID `sqlite` is reserved, and so is any table name that starts with `sqlite_`, which SQLite keeps for itself.
- Facts of third parties, verified on 2026-11-01:
  - SQLite's guidance for untrusted SQL and untrusted database files (sqlite.org/security.html) names `SQLITE_DBCONFIG_DEFENSIVE`, lower limits through `sqlite3_limit()` with `SQLITE_LIMIT_ATTACHED` at 0, an authorizer, a progress handler or `sqlite3_interrupt()`, trusted schema off, `cell_size_check=ON` and `mmap_size=0`. Its heap limit, `sqlite3_hard_heap_limit64()`, applies to the whole process.
  - SQLite's authorizer has 33 action codes, among them codes for attaching and detaching databases, PRAGMAs, transactions, savepoints, functions and the creation and removal of virtual tables. None of them is for VACUUM.
  - rusqlite 0.41.1 is the newest release. `Connection::authorizer` and `progress_handler` need its feature `hooks`, `limits` needs its feature `limits`, and `Statement::readonly` needs no feature.

## Decision

1. The core gives plugins the owner's SQLite files through a new sensitive service, `sqlite-files`, major 1. `mannie-store` holds the engine, in a new module with connections of its own, apart from Mannie's database, its writer and its readers, so rusqlite stays exclusive to `mannie-store` and V5 holds. The runtime provides the service (`crates/mannie-runtime/src/sqlite_files.rs`), since it joins the engine with tickets, the protected folders and the journal. `mannie-host-kit` offers the same engine and journal to a plugin's programs.
2. A database is registered when the owner chooses its file. On this computer, the service shows the native file dialog, whose chooser the desktop core provides, since rfd stays exclusive to it. The core keeps the registration, scoped to the plugin: a key, the owner's name for it, the path, the file's identity, and whether the owner marked it read-only. The plugin and the webview handle keys and never paths. The service refuses Mannie's own folders in every mode, as an exception to ADR-0029 d3, since a file there is Mannie's own state behind the store's authorizer (T-18). It also refuses network paths, links, the companion files `-wal`, `-shm` and `-journal`, and any file without SQLite's header. [ADR-0057](0057-let-the-master-work-with-the-databases-on-a-workers-host.md) decides registrations on a worker's host.
3. Every connection is hardened as SQLite's guidance describes, with these settings:
   - It opens read-only, or read-write without create, with `SQLITE_OPEN_NOFOLLOW` and without URI filenames.
   - `SQLITE_DBCONFIG_DEFENSIVE` is on, trusted schema and extension loading are off, `cell_size_check` is on, `mmap_size` is 0, and read connections set `query_only`.
   - `SQLITE_LIMIT_ATTACHED` is 0. The limits on lengths, SQL length, expression depth, compound selects, trigger depth, LIKE patterns and variables are lower than SQLite's defaults, and high enough for real databases. There is no heap limit, which would cap Mannie's own store.
   - An authorizer refuses ATTACH, DETACH, transactions and savepoints, since the engine owns its transactions, the creation and removal of virtual tables, `load_extension`, and PRAGMAs outside a read-only list. Every form of VACUUM is refused, by the limit or by the classification of decision 6, as spike S1 of M15 settles.
   - A run prepares exactly one statement, and a read runs only a statement that `readonly()` reports.
   - Rows, bytes and time are limited, and dropping a call interrupts its statement.
4. The service lets a plugin choose a file; list and forget its registrations; read a database's schema; browse a table in keyset pages by rowid or primary key; run a read; and write. A write is one statement; a batch of up to 16 statements in one transaction; a row edit that checks the row's old values; an insert; or a deletion of rows that checks their old values. Values keep SQLite's types: integers travel as text through IPC, since its bindings refuse 64-bit integers, and an infinite real has a value of its own. SQLite's error messages are content: the UI shows them under the catalog's wording, and nothing logs the text or the values of a statement.
5. A plugin tool's access to a database is a new SDK access, `ToolAccess::Database`, which the runtime maps to the core's `Access::Database` with the plugin's ID. It names the database's key, its home for a worker's database (ADR-0057), the statement's text, its parameters cut for display with a digest of all of them, and its class: read, write or schema. For this computer, the core fills in the path and the identity from its registry. The operation's digest covers every field, so a statement, a parameter or a file that changed between the approval and the execution goes back to the policy (ADR-0013 d4).
6. A new tool effect, `ReadsDatabases`, returns 1 to 16 read accesses and is never journaled, like `ReadsFiles` (ADR-0038 d3). A side-effect tool returns write and schema accesses, and its execution carries a `DatabaseTicket`, without which the service writes nothing, as `BackgroundTicket` works for background commands (ADR-0041 d11). Preparation classifies each statement by preparing it under the authorizer: against the file on this computer, or against an in-memory copy of a worker's database's schema. The engine classifies it again before it runs, and a statement whose class changed goes back to the policy.
7. The policy decides database accesses:
   - A read of a registered database runs with the decision `registered_database`, in every conversation and for the general and explore child agents.
   - A write asks with the reason `database_write`, unless full access allows it or a grant covers it. A grant for the conversation, its project or every conversation covers the same statement text on the same plugin and database, whatever its parameters.
   - A schema change asks with the reason `database_schema`, and no grant covers it. Full access allows it, as full access allows every operation (ADR-0029 d1), which the owner confirms by accepting this ADR.
   - A database that the owner marked read-only refuses writes and schema changes with `read_only_database`.
   - Databases have no rules, as the tools of tool servers have none (D42). The approval shows the database, its machine, the statement and its parameters.
8. The owner's own change from a plugin's view is an owner operation. The service journals it before it runs, in its module's table of operations, as the export journal does (ADR-0040 d6): the plugin, the database's key, the statement's text and a digest of its parameters, never their values, with the states executing, completed, failed and uncertain. The record is committed with full durability before the write, recovery at start marks an executing record uncertain, and an uncertain operation never runs again. An owner operation never asks, since the owner's action is the consent. The view asks the owner to confirm a schema change and a deletion of rows before it sends them. An agent's write stays in its tool call's record (ADR-0013 d1), and the service never journals it twice.
9. Typing in a terminal is not an operation, because a shell reads keystrokes as they come and no step of it can be named before it runs (ADR-0053 d6). A write to a database is one statement whose text, target and outcome the journal names before it runs, which is what ADR-0013 asks of a side effect. From now on, a plugin command that changes something on the owner's action is an owner operation of the core's journal, which refines ADR-0038 d10 and gives Git's panel actions their route.
10. The service is sensitive. A plugin's manifest declares it, or a feature's does (ADR-0055), and `task plugins:grants` and the Plugins page list it. The engine module's prefix is reserved in `ids.rs` and `plugin-rules.json`. It is neither `databases`, which stays free for a plugin, nor a name that starts with `sqlite_`.
11. The threats of [security](../architecture/security.md) gain T-74 to T-78: a hostile database file attacks the engine; prompt injection makes an agent read out a registered database, since reads run without asking; a grant covers other parameter values than the ones the owner saw; script in the webview writes through a plugin's view; and statements lock the owner's own applications out of their files.

## Consequences

- Positive: the owner and agents work with SQLite files on this computer under the same approvals, grants, full access and journal as other operations, and the approval shows the statement. The hardening lives in one place, which no plugin can loosen. The owner operation gives later plugin views, such as Git's panel, a route for the owner's own changes.
- Negative: the core gains an engine for files that are not Mannie's state, a service and an access kind, and the policy, the approvals and the Git plugin's exhaustive matches on `ToolAccess` change with it. The engine stays on the rusqlite of the core, so its version moves only with the store's. Reads run without asking in every conversation, so a prompt injection can read a registered database (T-75).
- Risks: an authorizer rule or a limit admits a statement that it should refuse, which spike S1 and a matrix of planted attacks in the engine's tests check. Another program's locks make writes fail as busy, or a long read stalls its checkpoints (T-78, spike S4); reads are short, writes run in short transactions, and a busy file fails with `busy`. A file that an application saves by replacing it changes identity, which sends approvals back to the policy and shows the file as changed (spike S5).

## Alternatives considered

| Option                                                   | Why not chosen                                                                                                                                    |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| rusqlite directly in a plugin crate                      | Each plugin would carry its own hardening, ADR-0034 d2 and V5 would break, and `deny.toml` would have to name a plugin crate, against ADR-0035 d1 |
| Path accesses on the database file                       | The owner would approve a file and a mode without seeing the statement, and a grant for a folder would cover every statement on every file in it  |
| The `processes` service with an installed `sqlite3`      | It needs `sqlite3` on every machine, yields text instead of typed rows, and still needs an ADR for the owner's changes from a view                |
| An MCP server for SQLite through the plugin MCP          | Possible today, but every call asks (D42), nothing classifies reads, writes and schema changes, and it has no view and no workers                 |
| A journal of the owner's changes in each plugin's tables | The core journals side effects (ADR-0013), and each plugin would rebuild the states and the recovery                                              |

## Validation

M15:

- Spikes S1 to S5 of M15: the authorizer's codes for every statement that the engine refuses, opening other programs' files read-only and in WAL mode, interrupts and limits, contention with the owner's applications, and file identity on Windows, on OneDrive and with applications that save by replacing the file.
- The engine's tests: a matrix of planted attacks (ATTACH, VACUUM INTO, `load_extension`, `writable_schema`, a hostile trigger under trusted schema off, a second statement, a write in a read), each limit, an interrupt, and recovery of an owner operation that a crash cut off.
- Policy tests for every source of a decision on a database: registration, grants of the three scopes for the same statement and for another, a schema change under a grant, full access and a read-only database.
- Runtime tests with a test plugin's tool: a read without asking, a write with Allow once and with a grant, a ticket that does not match the authorized accesses, and a class that changed between the approval and the execution.

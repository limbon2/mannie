## Context

- The owner asked on 2026-10-16 to mention files in a message with "@". A mention gives the model the file's text, but one mention must not fill the context. Folders can be mentioned too, as in "read the @docs folder and implement a feature". The list of files includes the ones that `.gitignore` excludes and hidden ones, because hiding them confused models in other harnesses. Nothing is blocked, and files that may hold secrets, such as `.env`, get a small warning.
- On 2026-10-17 the owner asked for mentions to be an extension point: "we may want to mention things like a sibling chat or a worker or something that a plugin would want to add".
- The message box is chat's component. `send_message` and `start_conversation` take only text, and the owner's message is a single `user_text` part, which the model reads as one user message. No registry or slot contributes to the message box.
- The model reads files through system tools. Reads inside the conversation's workspace run without asking, accesses inside Mannie's own folders ask, and full access allows everything ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)). `read_file` returns one page that fits the result limit: 64 KiB, or a quarter of the context budget when that is smaller, and never less than 4 KiB.
- The webview is untrusted. Every command validates its input and applies the same policy as a model's request ([ADR-0004](0004-keep-system-access-in-the-rust-core.md), decision 2). Script in the webview can already make the model list and read the workspace without a question: it sends a message, and reads the output in the tool call's view.
- `move_to_project` runs without a question when the owner's message of the turn names the project ([ADR-0023](0023-organize-conversations-into-projects.md), decision 3, threat T-19). The policy reads that message from the turn's first owner part.
- Plugins contribute tools, agent definitions, instruction sections and task executors, and the UI has slots for their entries ([ADR-0030](0030-split-mannie-into-a-core-and-plugins.md), decision 5). A new extension point needs an ADR ([ADR-0002](0002-grow-through-extension-points.md)).

## Decision

1. A mention is something the owner picks from a list that opens when they type "@" in the message box. The box puts a readable token into the text, such as `@src/main.rs`, so the model sees where the owner referred to it. The message carries a reference, a provider and a key, for each token that is still in the text when it is sent. A token that the owner typed counts when it equals the token of an entry that the list showed. Pasted text never becomes a mention. `send_message` and `start_conversation` gain `mentions`, a list of references that is empty when left out ([ADR-0002](0002-grow-through-extension-points.md), growth by addition).
2. Mention providers are an extension point of `mannie-runtime`. A provider has an ID and three functions:
   - whether it is offered in a place: an existing conversation, or a new one with or without a project;
   - its suggestions for a query: entries with a key, a label, the token, a variant such as a file or a folder, an optional warning code, and whether choosing the entry keeps the list open, as for a folder;
   - resolving a key into content that renders within any number of bytes, as the text the model reads and a summary for the owner: a code with numbers.
3. The composition root registers the core's providers. A plugin adds providers through its contributions. The runtime keeps each one with the plugin's ID, drops it when the plugin stops, and refuses a provider whose ID is taken, or a plugin's provider whose ID is neither the plugin's ID nor starts with it and a dot ([ADR-0030](0030-split-mannie-into-a-core-and-plugins.md), decision 5, grows).
4. The UI gets a slot of mention kinds ([ADR-0020](0020-complete-the-ui-shell-slots.md) grows). For each provider, the entry gives the heading of its group in the list, an icon for each variant, the sentence for each warning and refusal code, and the summary of a sent mention. A provider without an entry gets generic texts. The list groups its entries by provider, in the order of the slot, and the message box and the transcript show each mention as a chip.
5. When a message is sent, the core checks its references. A message has at most 20 mentions. Each provider must be registered and offered in the place. Each provider checks its key again, as untrusted input. A reference to a provider that is not there fails with `mention_unavailable`, and a refused key fails with `mention_refused` and the provider's code. Nothing is stored, and the message box keeps the text.
6. The mentions of one message share one budget in bytes: the tool result limit of the conversation's provider profile. The core divides it max-min fairly: a mention that needs less than an equal share gets all it needs, and the rest is divided among the others. Each provider renders its content within its share, and the core cuts a longer text at the share.
7. Each mention is stored as an owner part of the kind `mention`, after the owner's text and in the same transaction. Its text is what the model reads, and its document holds what the owner sees: the provider, the key, the label, the variant and the summary.
   - The model reads the mentions after the owner's text, in the same user message.
   - A retry sends the stored text again. Compaction summarizes each mention as a shortened line, and the context estimate and the checkpoint's hash count it like any part's text.
   - The policy reads the owner's words from the `user_text` part alone, so a mention never stands in for them.
8. Content read for a mention never grants a permission ([ADR-0013](0013-journal-every-side-effect.md), decision 8). A provider that reads files applies the path checks and the policy of a model's read, with the conversation's workspace, grants and full access. It never asks: what the policy would ask about is left out, and the model reads a note instead. Suggestions and mentions are reads, so they journal nothing. Providers log labels and content only at `debug`.
9. The core's first provider, `files`, offers the files and folders of the place's workspace, and chat registers its kind in the slot ([mentions](../features/chat/mentions.md)).

## Consequences

- Positive: one list in the message box for every kind of mention. A later feature or plugin adds a kind, such as a sibling conversation or a worker, with a provider and an entry in the slot, without editing chat. The owner sees what each mention gave the model, and the shared budget keeps a message's mentions from filling the context.
- Negative: one more registry and one more slot to keep stable. The message box keeps track of the tokens the owner picked. A message reads its mentions before its reply starts, which adds a moment for large files. A token that the owner typed counts only when the list showed it.
- Risks:
  - A provider renders more than its share. The core cuts the text at the share and logs the provider's ID.
  - A provider puts content into its labels or its logs. Its review and its tests check that.
  - Script in the webview sends a forged key, such as a path outside the workspace. The provider's checks refuse it, and tests send such keys.

## Alternatives considered

| Option                                                                 | Why not chosen                                                                                                              |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Tokens that the core parses from the text, with a prefix for each kind | Titles of conversations are not unique, every kind would need a syntax of its own, and pasted text would turn into mentions |
| An attach button with a dialog                                         | The owner asked for "@" in the text, and the model would not see where the owner referred to each item                      |
| Mentions as tool calls in the model's reply                            | The owner's choice would read as the model's, and a profile without tools would get nothing                                 |
| Each feature adds its kind to the message box itself                   | Chat's module would grow a branch for each kind, which ADR-0002 rules out                                                   |
| The whole text of each mention                                         | One large file could fill the context                                                                                       |

## Validation

M6:

- Tests of the registry with a fake provider: offered only where it says so, stored as a part that the model's request holds, the budget divided across two providers, a provider that is not there, a refused key, and a plugin's provider that leaves with its plugin or whose ID is not the plugin's.
- Tests of the slot of mention kinds with a fake kind, and without an entry.
- The tests of the `files` provider and the end-to-end tests of the [mentions](../features/chat/mentions.md) feature, with axe.

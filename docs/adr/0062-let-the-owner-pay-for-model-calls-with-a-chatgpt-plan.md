## Context

- The owner wants Mannie's conversations to run on their ChatGPT subscription instead of an API key that bills each call: "i want to introduce support for a chatgpt subscription" ([decision D51](../roadmap/milestones.md#5-decisions)).
- A provider profile reaches its model through an API endpoint, with an optional key of its own ([providers](../features/chat/providers.md)):
  - A run reads the key once, and a refused key (HTTP 401) ends the run.
  - A change of the key raises the profile's configuration revision, which stops the replay of the encrypted reasoning that earlier revisions produced ([ADR-0011](0011-own-the-provider-adapters.md), decision 6).
  - The Responses adapter always sends `max_output_tokens`, and the function tools as a flat list.
  - The master lends a task's key to the worker that runs it ([ADR-0010](0010-keep-provider-credentials-on-the-master.md), decision 5).
- Facts of OpenAI's documentation, verified on 2026-11-08:
  - Sign in with ChatGPT has an optional capability, ChatGPT plan usage: an app asks for the user's permission to use their ChatGPT plan for eligible requests to the Responses API, which gives it no access to their conversations. At launch it is available to "open-source projects, personal projects that run locally, and selected private apps", and the makers of paid or remotely hosted apps fill in an interest form. OpenAI lists the route's current limits as preview limitations ([Sign in with ChatGPT](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt), [overview](https://developers.openai.com/siwc/token-sharing-open-source)).
  - Registration: the first sign-in sends `client_id=dynamic_agent_client`, the app's name as `agent_name_hint`, and `ext_agent_host_id`, a stable and opaque ID that differs for each host and is chosen before the first sign-in. The callback returns the issued `client_id`, which later sign-ins send instead, with the saved email as `login_hint`. An issued client ID is bound to the user and the workspace chosen at registration ([overview](https://developers.openai.com/siwc/token-sharing-open-source), [registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)).
  - The redirect is an HTTP loopback callback on `127.0.0.1` from the initial registration on, the same in the request and in the code exchange, and its scheme, host and path never change. The page's example is `http://127.0.0.1:1455/auth/callback`, and later sign-ins may use another available port, since only the port may vary ([registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in)).
  - The request uses PKCE with S256, a fresh `state` and `nonce` for each attempt, the scopes `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct` and `resource=https://api.openai.com/v1`, and the code exchange needs no client secret. The app checks the ID token's signature against OpenAI's published keys, its issuer, its audience against the issued client ID, its expiry and the attempt's nonce, and OpenAI's example allows 5 seconds of clock skew. A valid ID token alone does not allow plan usage: the granted scopes of the token response must hold `chatgpt.tokens.use.direct` ([registration and sign-in](https://developers.openai.com/siwc/token-sharing-open-source/sign-in), [on your website](https://developers.openai.com/siwc/website)).
  - The OpenID configuration names the issuer `https://auth.openai.com`, the endpoints `/api/accounts/authorize`, `/api/accounts/oauth/token`, `/api/accounts/oauth/revoke` and `/.well-known/jwks.json`, RS256 as the only algorithm of ID tokens and S256 as the only PKCE method, and no registration endpoint ([OpenID configuration](https://auth.openai.com/.well-known/openid-configuration)).
  - An access token lasts one hour (`expires_in: 3600`). A refresh token lasts 30 days, and each refresh returns a replacement with a fresh 30-day lifetime. An app stores the latest replacement and serializes the refreshes of a session, so that two processes do not race a rotating token. The codes `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated` and `refresh_token_reused` mean that the refresh token is unusable and the user signs in again, and a temporary network or server failure keeps the credentials ([token reference](https://developers.openai.com/siwc/token-sharing-open-source/token-reference), [accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions), [errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)).
  - Signing out stops requests, revokes the refresh token with the issued client ID, which an empty HTTP 200 confirms, and clears the tokens. When the revocation is not confirmed, the app says so, and the user can disconnect the app in ChatGPT's settings ([accounts and sessions](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions)).
  - Another host, such as a self-hosted VM, takes over a session by receiving a copy of its tokens and client ID. It keeps a host ID of its own and owns the later refreshes ([self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms)).
  - `GET /v1/models` returns a list `models` whose entries have a `slug`, a `display_name` and a `visibility`, and an app shows the entries whose visibility is `list`, in the server's order. `POST /v1/responses` takes `store: false` and `stream: true` ([models and inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference)).
  - The plan route does not support `max_output_tokens`, `temperature`, `top_p`, `user`, `metadata`, `truncation` and other fields, or `previous_response_id` over HTTP. It wants function tools grouped in namespaces or sent as `additional_tools` input items. It does not support hosted tools such as file search, image generation and Code Interpreter, and web search depends on the model and the account's policy ([preview limitations](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations)).
  - A namespace is a tool of type `namespace` with a name, a description and its functions. A `function_call` item names the `namespace` of its function, and an assistant message carries a `phase`, `commentary` or `final_answer`, which newer models want resent on follow-ups ([function calling](https://developers.openai.com/api/docs/guides/function-calling), [tool search](https://developers.openai.com/api/docs/guides/tools-tool-search), [creating a response](https://developers.openai.com/api/reference/resources/responses/methods/create)).
  - Plan calls fail with codes of their own, which decision 12 maps: a usage limit, unavailability, an unsupported capability or route, a user who is not eligible or cannot be validated, and a permission context that does not authorize the call. A body of the form `{"detail": ...}` before a stream opens is diagnostic text without a stable code ([errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery)).
  - The guidelines ask for the action "Continue with ChatGPT" with the ChatGPT logo, in one of the approved button formats; a notice after the first sign-in only; "Using ChatGPT plan" near the composer or the model selector, with a link "Manage usage" to `https://chatgpt.com/settings/usage`; and at a usage limit, "Usage limit reached" with "Manage usage" as the primary action ([UI and UX guidelines](https://developers.openai.com/siwc/ui-ux-guidelines), [on your website](https://developers.openai.com/siwc/website)).
- The Windows credential store keeps at most 1,280 UTF-16 units in an entry, fewer than these tokens hold ([M12 validation results](../roadmap/m12-validation.md), R36).
- The plugin MCP signs in to remote servers with OAuth through a listener on a random loopback port ([its ADR-0002](../../plugins/mcp/docs/adr/0002-sign-in-to-remote-servers-with-oauth.md), decision 4; T-58), and the `oauth2` crate is the plugin's alone.
- Provider profiles and their credentials belong to the core ([ADR-0030](0030-split-mannie-into-a-core-and-plugins.md), decision 1). The plugin SDK has no extension point for providers or ways of signing in, and [ADR-0047](0047-serve-embeddings-and-reranking-through-provider-profiles.md) kept search profiles in the provider module.

## Decision

1. The ChatGPT plan is a feature of the core. Provider profiles and credentials are the core's, the SDK has no extension point for providers or ways of signing in, and ADR-0047 already chose the provider module over a plugin. The SDK does not change, and plugins cannot reach the account: the service `models` lists only search profiles, and the lender behind the service `credentials` refuses plan profiles (decision 13).
2. Mannie holds one ChatGPT account per installation, and every plan profile uses it. "Use another account" signs in to a new account, which replaces it.
3. The sign-in follows OpenAI's documentation, written by hand on the core's shared reqwest client. The flow has parameters that OAuth libraries do not know, and the `oauth2` crate stays the plugin MCP's.
   - The endpoints are constants with the date they were verified: the issuer `https://auth.openai.com`, `/api/accounts/authorize`, `/api/accounts/oauth/token`, `/api/accounts/oauth/revoke` and `/.well-known/jwks.json`, and the API at `https://api.openai.com/v1`.
   - Mannie is a public client with PKCE S256, a fresh `state` and `nonce` for each attempt, and `resource=https://api.openai.com/v1`. The scopes are `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`.
   - `ext_agent_host_id` is `urn:uuid:` followed by a UUIDv4 that `uuid::Builder::from_random_bytes` builds from random bytes of `ring`, since `clippy.toml` bans `Uuid::new_v4`. Mannie creates it once and keeps it.
   - The first sign-in sends `client_id=dynamic_agent_client`, `agent_name_hint=Mannie` and the redirect `http://127.0.0.1:1455/auth/callback` of OpenAI's example, since OpenAI lets only later sign-ins use another port. Mannie keeps the issued `client_id` of the callback with the account once the sign-in completes, and refuses a callback without one as an incomplete registration.
   - Later sign-ins send the saved `client_id`, the saved email as `login_hint`, and a redirect on any free port. "Use another account" registers again.
   - Mannie checks the ID token once: its RS256 signature against the JWKS with `ring`, which is already the only crypto provider; `iss`; `aud` equal to the client ID; `exp` and `iat` with 5 seconds of leeway; the attempt's `nonce`; and a `sub` that is not empty. Then it drops the ID token and keeps only `sub` and `email`.
   - Plan usage needs `chatgpt.tokens.use.direct` in the `scope` of the token response. Without it, the sign-in fails with `plan_usage_not_granted`, and Mannie revokes the tokens.
4. The callback listener follows the plugin MCP's ([its ADR-0002](../../plugins/mcp/docs/adr/0002-sign-in-to-remote-servers-with-oauth.md), decision 4) and T-58, with the fixed port of the first registration as the one exception.
   - It binds before the browser opens, and serves one sign-in for at most 5 minutes.
   - It answers only `GET /auth/callback`, and gives each request 10 seconds and 16 KiB.
   - A wrong `state` gets a 400, and the listener keeps waiting. An `error` parameter ends the sign-in as refused.
   - The page that the browser shows is escaped, sent with the Content Security Policy `default-src 'none'`, `no-store` and `no-referrer`, and takes its texts from the UI's catalog.
   - When another program holds port 1455, as the Codex CLI does while it signs in, the sign-in fails with `port_in_use` before anything opens.
5. The browser opens only when the owner clicks, through the core's `links::open`. A run never opens a browser, and the webview never receives the authorize URL or a token ([ADR-0004](0004-keep-system-access-in-the-rust-core.md)).
6. The tokens live only in the operating system's credential store ([ADR-0010](0010-keep-provider-credentials-on-the-master.md)).
   - They form one bundle, `{"v":1,"access","refresh","expiresAt"}`, split into parts of at most 1,000 UTF-16 units as the plugin MCP splits its secrets. The core splits them with code of its own, since it cannot import a plugin.
   - The entries are named `provider/chatgpt/<generation>-<part>`. `provider` is a prefix that no plugin can take.
   - A write saves the new parts, then compares and sets the generation in the account's row, then deletes the old parts.
   - The vault saves and reads the parts through the new `CredentialVault::save_part` and `read_part`, which do not register them with the log redactor for the life of the process, since they change every hour. Each whole token is registered on its own instead, through a new `CredentialVault::protect`, and the registrations of old tokens end after the next refresh. `id_token` joins the names of the fields whose values the redactor replaces.
7. One refresh runs at a time. It starts when less than 5 minutes of the access token remain, in a task of its own that holds the account's gate until the rotated tokens are stored, so a run that stops never drops a refresh that the server already rotated.
   - The codes `invalid_grant`, `invalid_refresh_token`, `token_expired`, `refresh_token_expired`, `refresh_token_invalidated` and `refresh_token_reused` end the session: the account's state becomes `sign_in_needed`, and the parts are deleted.
   - Network failures, timeouts, 429 and 5xx keep the tokens, and are transient failures of the run.
   - Quitting waits up to 5 seconds for a refresh in flight.
8. Every model call of a plan profile gets a fresh token. Right before the call, the runtime resolves a target that belongs to that call alone: for each step, each retry, the calls of summaries and compaction, the provider test and the catalog.
   - `invalid_credential` marks the call's token as rejected, if it is still the current one. One refresh follows, and the call is made once more.
   - A second refusal ends the run with `chatgpt_sign_in_needed`.
   - A refused call goes through `discard_attempt`, so no tool operation repeats.
9. The binding of provider-private data refines [ADR-0011](0011-own-the-provider-adapters.md), decision 6. A plan profile's binding is `{profile}:{revision}:{account key}`, where the account key is the first 16 hex characters of SHA-256 over the client ID and the subject. A refresh changes nothing, the same account keeps its encrypted reasoning when it signs in again, and another account never receives it. When the account changes during a reply, the reply ends with `chatgpt_account_changed`.
10. The plan's requests and answers follow ADR-0011, decisions 1 and 5: one adapter, with the differences of servers as data. The profile's new field `access` selects the shape, since the provider test overwrites `ServerKind` and edits reset it.
    - `max_output_tokens` is never sent. The output limit stays a budget that Mannie keeps, and a summary longer than its allowance is cut down with `compaction::fit`.
    - The functions go into one tool `{"type":"namespace","name":"mannie",...}`, and every replayed `function_call` carries `"namespace":"mannie"`.
    - A replayed assistant message gets `"type":"message"` and a `phase`: `commentary` for text that a call follows in the same model call, and `final_answer` otherwise. Each model call already has an assistant message of its own in the context.
    - The rest of the request stays as it is. Fixtures recorded from the live route settle each of these quirks, since a quirk is trusted only when a recorded fixture shows it (V8).
    - The route sends its event streams without a content type, as the first replies on the owner's machine showed on 2026-11-09. This refines ADR-0011, decision 4: on the plan, an answer without a content type is read as the event stream that the request asked for, and the stream's other checks apply as before. An answer that names another type is refused, on the plan as on every other server.
11. `GET /v1/models` gives a plan profile's models. Mannie keeps the entries whose `visibility` is `list`, in the server's order, shows `display_name` and stores `slug`. The limits come from the defaults of known models, or the owner enters them. The catalog is longer than the 64 KiB that Mannie keeps of an error body, so Mannie reads all of it, up to the 16 MiB of other lists of models.
12. Errors refine ADR-0011, decision 3. OpenAI's codes of plan usage apply only to plan calls, and are read before the rules of the HTTP status:

    | OpenAI's code                                                                                         | Run failure                                                                                             |
    | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
    | `subscription_sharing_usage_limit_exceeded` (429, or in `response.failed`)                            | `chatgpt_usage_limit_reached`, never retried. The reply shows "Usage limit reached" with "Manage usage" |
    | `subscription_sharing_usage_unavailable`, `subscription_sharing_user_unavailable` (503)               | `chatgpt_unavailable`, transient, within the bounded backoff of other transient failures                |
    | `subscription_sharing_unsupported_capability` (400), `subscription_sharing_route_not_supported` (403) | `chatgpt_unsupported`, with `param` cleaned to at most 64 safe characters                               |
    | `subscription_sharing_user_not_eligible` (403)                                                        | `chatgpt_not_eligible`                                                                                  |
    | `subscription_sharing_invalid_user` (401)                                                             | `invalid_credential`, which leads to the one refresh and the one repeat of decision 8                   |
    | `chatpass_v2_scope_not_authorized`, `chatpass_v2_invalid_authorization_context` (403)                 | `chatgpt_sign_in_needed`                                                                                |

    A body of the form `{"detail": ...}` keeps the class of its HTTP status, and Mannie reads it for the log only.

13. Plan profiles stay on the master, which refines ADR-0010, decision 5.
    - The lender refuses a plan profile with `NotPermitted`. It never answers `Ok(None)`, which the plugin Workers reads as a profile that needs no lease.
    - Runs on a plan profile get no executors' tools or sections, and their follow-ups on executor tasks are refused.
    - Local child agents work as before.
14. Signing in and signing out are not journaled. They change only Mannie's own credentials, as a profile's key and the plugin MCP's sign-in do ([ADR-0013](0013-journal-every-side-effect.md)).
15. NFR-OPS-04 adds `auth.openai.com`, for sign-ins, refreshes, revocations and its keys.
16. Later work, outside this decision: several accounts, lending to workers, embeddings and reranking on the plan, OpenAI's hosted tools, WebSocket, and the Codex app-server.

## Consequences

- Positive:
  - The owner's conversations run on the ChatGPT subscription that the owner already pays for, without an API key, and endpoint profiles send the same requests as before.
  - The tokens stay in the credential store and refresh by themselves: a reply crosses a refresh, and a restart keeps the account.
  - Encrypted reasoning keeps replaying across refreshes, and across sign-ins of the same account.
- Negative:
  - The provider module gets an account, a sign-in, a service of refreshes and a second request shape of the Responses adapter.
  - Runs on a plan profile cannot give tasks to workers, and the plan serves no embeddings or reranking.
  - On the plan, the output limit is a budget that only Mannie keeps: a model can write past it, and summaries are cut down after they arrive.
  - The first sign-in fails while another program, such as the Codex CLI, holds port 1455 (R52).
  - A later sign-in shows OpenAI's selector of accounts, since Mannie keeps no ID token to send as `id_token_hint`.
- Risks:
  - OpenAI changes the preview route, its OAuth parameters or its codes (R51). The live check, `task provider:live:chatgpt`, and its recorded fixtures show the change, each failure names what failed, and endpoint profiles keep working.
  - A local program catches the callback on port 1455. PKCE with S256 and `state` make a code that it catches useless (T-94).
  - Two refreshes race and end the session. One refresh at a time and the compare-and-set of generations prevent it (T-96).
  - The tokens leak, or reach a worker or a plugin. The credential store, the redactor and the lender's refusal keep them in the master's core (T-95, T-97).

## Alternatives considered

| Option                                                      | Why not chosen                                                                                                                                                                             |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| A plugin                                                    | Provider profiles and their credentials are the core's, and the SDK has no extension point for providers or ways of signing in. A plugin would need a new service that hands it the tokens |
| The Codex app-server                                        | A second agent runtime, a program to ship or find, which takes its own RPC inputs in place of Responses requests, so Mannie's loop, tools, journal and adapters would not apply            |
| A second API interface, or a second adapter, for the plan   | The plan route is the Responses API with a few differences, which ADR-0011 keeps as data of one adapter                                                                                    |
| The `oauth2` crate                                          | The flow's parameters, such as `agent_name_hint`, `ext_agent_host_id` and `resource`, and the client that its callback issues are its own, and the crate is the plugin MCP's               |
| An encrypted file of tokens                                 | It needs a key that lives somewhere, and puts a file on disk, while the credential store already keeps provider credentials (ADR-0010)                                                     |
| Raising the configuration revision when the account changes | A sign-in that lands between reading the profile and reading the account would pair the old binding with the new account                                                                   |
| Lending hourly access tokens to workers                     | The owner deferred it (D51): plan profiles stay on the master                                                                                                                              |

## Validation

M19: the tests of the provider crate, the store and the runtime, with constructed fixtures; the tests of a planted token; and the end-to-end test against a fake authorization server. Then the live check `task provider:live:chatgpt`, whose recorded fixtures replace the constructed ones, and the owner's checks of the development build on Windows, recorded in the [M19 validation results](../roadmap/m19-validation.md).

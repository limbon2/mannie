## Context

- The owner wants an optional plugin in `plugins/proxmox/` aimed at a regular Proxmox VE user account rather than a cluster administrator. Using username with realm (such as `user@pve` or `user@pam`) and password, the owner should choose which QEMU virtual machines to expose to Mannie, let agents pick an ISO from connected storage, attach it, update boot order, restart the VM, and use VNC tools to perform installations and other actions inside the VM while the owner watches or takes over in a live console side panel beside the conversation on Windows and Linux.
- On 2026-11-24, the owner decided four rules for version 1 (D74):
  - each registered Proxmox server starts with zero VMs exposed to agents, and a pre-configuration step in Settings lets the owner explicitly choose which QEMU VMs are available to Mannie;
  - VM hardware/power changes and VNC console access use per-VM grants (conversation, project or always), and conversation full access ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)) allows both automatically on allowed VMs while active owner takeover in the VNC side panel still blocks all agent VNC operations until the owner resumes agent control;
  - guest passwords and disk passphrases are entered through owner takeover in the live VNC side panel alone, without opaque session secret references in version 1;
  - registered Proxmox servers and their explicitly allowed VMs are visible in every conversation and to the `general` child agent by default (like SSH hosts), with `@` mentions for servers and allowed VMs.
- Earlier decisions that this design touches:
  - [ADR-0034](0034-build-plugins-on-a-plugin-sdk.md), decision 6: `ToolAccess` has no variant for Proxmox VM configuration, power or VNC console operations, and `Instance` has no lifecycle hook to notify plugins when conversations are deleted so per-conversation VNC sessions can close immediately.
  - [ADR-0013](0013-journal-every-side-effect.md): `Access`, `GrantScope`, `ApprovalReason` and `Refusal` are exhaustive across the core.
  - [ADR-0036](0036-let-plugins-run-commands-on-remote-hosts.md), decision 9, and [ADR-0043](0043-let-plugins-offer-the-tools-of-tool-servers.md), decision 8: outbound network connections initiated from plugin UI commands on the owner's action require an ADR.
  - NFR-OPS-04 in [goals and scope](../product/goals-and-scope.md) enumerates the network endpoints Mannie may reach.
  - [ADR-0017](0017-license-and-dependency-policy.md) governs dependencies, while `image` remains exclusive to `plugins/images/`.
- Facts verified on 2026-11-24:
  - Proxmox VE regular user authentication uses `POST /api2/json/access/ticket` (`username` with realm and `password`), returning a 2-hour `PVEAuthCookie` ticket and `CSRFPreventionToken` (required on `POST`, `PUT` and `DELETE` requests). Tickets can be renewed with an unexpired ticket or credentials.
  - Proxmox VE QEMU console proxying calls `POST /api2/json/nodes/{node}/qemu/{vmid}/vncproxy` with `websocket=1` and `generate-password=1`, returning a short-lived `port`, `ticket` (`vncticket`) and RFB `password`. The WebSocket upgrade at `GET /api2/json/nodes/{node}/qemu/{vmid}/vncwebsocket?port={port}&vncticket={ticket}` requires the `Cookie: PVEAuthCookie=...` authentication header and speaks standard RFB 3.8 (RFC 6143) over binary frames.
  - Standard Proxmox VE installations serve a node leaf certificate (`/etc/pve/nodes/<node>/pve-ssl.pem`) signed by the local cluster CA (`/etc/pve/pve-root-ca.pem`), where Issuer differs from Subject, alongside standalone self-signed certificates.
  - `png` 0.18.1 (`MIT OR Apache-2.0`), `flate2` 1.1.10 (`MIT OR Apache-2.0`), `ring` 0.17.14, `rustls` 0.23.46, `tokio-rustls` 0.26.6, `rustls-platform-verifier` 0.7.1, `rustls-webpki` 0.103.16 and `reqwest` 0.13.5 (with `.tls_backend_preconfigured`) are already in `Cargo.lock`.

## Decision

1. Add an optional internal plugin `proxmox` in `plugins/proxmox/` (order 100, off by default on new installations per D28). Its manifest declares `store = 1`, `secrets = 1` with keyed family `server`, and `[native] sockets`, with zero new third-party crates. The plugin encodes VNC screenshots and live canvas updates with `png` and decodes RFB Zlib rectangles with `flate2`, keeping `image` exclusive to `plugins/images/`. A zero-unsafe pure-Rust RFC 6455 binary WebSocket client and RFB 3.8 client live inside `mannie-proxmox` (including RFC 6143 SecurityType 2 DES authentication and strict framebuffer and decompression limits) over `tokio-rustls` and `ring`.
2. Enforce an explicit, fail-closed per-server QEMU VM allowlist (`proxmox_allowed_vms`, keyed by `(server_id, vmid)` with cached `node` and `name`):
   - Newly registered Proxmox servers and newly discovered VMs start disallowed.
   - After adding a server (and after pinning its certificate when needed), Settings presents a pre-configure step listing all QEMU VMs visible to that account so the owner explicitly selects which VMs Mannie may access.
   - Every agent discovery, config, power, VNC tool and `@` mention enforces the allowlist in Rust before calling Proxmox or requesting approval. Unselected VMs are never listed, inspected, mentioned or modified.
   - Unchecking a VM in Settings closes any active VNC session for that VM immediately. Changing a server's host or port clears both its pinned TLS fingerprint and its VM allowlist so VMIDs on a different server cannot inherit access.
3. Verify TLS certificates against the operating system trust store (`rustls-platform-verifier` over `ring`) by default, and support explicit SHA-256 leaf-certificate pinning shared across both REST (`reqwest::ClientBuilder::tls_backend_preconfigured`) and VNC WebSocket (`tokio-rustls` with RFC 6455 binary framing):
   - Settings provides a certificate inspection action that opens a TLS handshake only, captures the presented leaf DER certificate (SHA-256 fingerprint, subject, issuer, SANs and validity dates), and closes before sending any HTTP request or credential.
   - When the owner pins a leaf SHA-256 fingerprint for a server, the custom `rustls::client::danger::ServerCertVerifier` requires an exact SHA-256 match on the presented leaf DER, checks the leaf's X.509 validity window, and verifies TLS 1.2 and TLS 1.3 handshake signatures with `ring` against the leaf public key. This works for both Proxmox cluster-CA-signed node certificates and standalone self-signed certificates without modifying the operating system trust store.
   - Changing a server's host or port clears its pin. A presented certificate that differs from the pinned fingerprint aborts the TLS handshake before sending the password or ticket and reports both fingerprints in Settings.
4. Keep Proxmox passwords strictly in the master's operating system credential store (`proxmox/server/<server-id>`), write-only from the UI:
   - Passwords never appear in SQLite, logs, transcripts, tool results, approvals or IPC responses. Editing a server with an empty password field keeps the stored password.
   - Session tickets (`PVEAuthCookie`), `CSRFPreventionToken` and short-lived VNC proxy tickets/passwords live only in Rust memory, renew automatically before expiry or on `401`, are cleared when the server is edited or removed or the plugin turns off, and never reach the webview.
   - Automatic HTTP redirects are disabled (`Policy::none()`), URLs with embedded userinfo are refused, and TFA challenges fail with an explicit `tfa_unsupported` code.
5. Add `ProxmoxVmScope` (`Config`, `Power`, `Vnc`), `ToolAccess::ProxmoxVm(ProxmoxVmAccess)` in `mannie-plugin-sdk`, and `Access::ProxmoxVm`, `GrantScope::ProxmoxVm`, `ApprovalReason::ProxmoxVm`, `ApprovalReason::ProxmoxVnc` and `Refusal::NoProxmox` in `mannie-types`:
   - The core adapter supplies `plugin` and validates server ID, canonical `https` origin (`endpoint`), TLS trust identity (`"os_trust"` or `"sha256:<64 hex>"`), node name, positive `vmid`, scope, action tag and sanitized `summary` before authorization; invalid fields fail with `plugin_invalid`.
   - `Access::ProxmoxVm::changes()` is `true`, so every VM config change, power action and VNC operation is journaled before execution ([ADR-0013](0013-journal-every-side-effect.md)). `ToolCallDocument::view` cuts `summary` to `MAX_VIEW_ARGUMENTS_BYTES` and sets `summary_cut`.
   - Policy authorization (`mannie-tools`): the workspace never allows `Access::ProxmoxVm`; full access allows it ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)); unmatched calls ask with `ApprovalReason::ProxmoxVm` (`Config` and `Power`) or `ApprovalReason::ProxmoxVnc` (`Vnc`).
   - `GrantScope::ProxmoxVm` covers `(plugin, server_id, endpoint, identity, vmid, scope)` at conversation, project or always scope (`server_label`, `node` and `vm_name` are display only). Changing a server's endpoint or pinned certificate identity falls outside existing grants and asks again. No saved command rules apply.
   - A worker's policy ceiling refuses `Access::ProxmoxVm` with `Refusal::NoProxmox`.
6. Add an additive default no-op lifecycle method `Instance::conversations_deleted(&self, conversations: Vec<ConversationId>)` to `mannie-plugin-sdk` (SDK 1):
   - `PluginHost::conversations_deleted` forwards conversation deletions (both single conversation deletion and project removal) to all running plugin instances so per-conversation resources such as live VNC sessions close immediately.
7. Contribute fixed static tools, an instruction section (`proxmox-servers`, position 350), a mention provider (`proxmox`), a Settings section, a conversation control, a live VNC side panel and tool kinds:
   - Read-only discovery tools (`proxmox_list_vms`, `proxmox_get_vm_config`, `proxmox_list_isos`) declare `ToolEffect::ReadsOwnData` and are offered to `AgentSelector::Every`, enforcing the VM allowlist in Rust.
   - Config, power and VNC tools (`proxmox_attach_iso`, `proxmox_eject_iso`, `proxmox_set_boot_order`, `proxmox_vm_power`, `proxmox_vnc_screenshot`, `proxmox_vnc_pointer`, `proxmox_vnc_keyboard`, `proxmox_vnc_close`) declare `ToolEffect::SideEffects` and are offered to conversation agents and the `general` child agent (`AgentSelector::Agents(["conversation", "general"])`), never to `explore`, `Plan`, read-only custom agents or workers.
   - Live VNC side panel renders the Rust framebuffer onto an HTML `<canvas>` over a plugin IPC channel (`follow_vnc_session`) with throttled dirty-rect PNG tiles on Windows and Linux and zero encoding when no panel is subscribed. Under agent control, canvas input is disabled in UI and refused in Rust (`agent_in_control`). Under owner takeover, ALL agent VNC tools (including screenshots) are refused in Rust (`owner_in_control`), even in conversation full access, until the owner clicks Resume. Owner input grants the agent no permission.
   - Owner-initiated UI actions in Settings (inspect certificate, test login, discover VMs) and in the live VNC panel (open console, watch, takeover input, close) connect directly on the owner's action without an agent approval prompt, refining [ADR-0036](0036-let-plugins-run-commands-on-remote-hosts.md), decision 9, and [ADR-0043](0043-let-plugins-offer-the-tools-of-tool-servers.md), decision 8. NFR-OPS-04 in [goals and scope](../product/goals-and-scope.md) allows outbound connections to configured Proxmox servers while `proxmox` is on.
8. Record threats `T-121` through `T-127` in [security](../architecture/security.md).

## Consequences

- Positive:
  - Regular non-admin Proxmox users can expose strictly chosen VMs to agents without cluster administrator privileges, while unselected VMs stay invisible and unreachable.
  - All credentials, TLS pinning, REST tickets, WebSocket framing and RFB state remain inside Rust; the webview only receives rendered framebuffer images and sends owner gestures while in takeover.
  - Live VNC viewing and owner takeover work identically on Windows and Linux without native window overlay complexity.
  - Pure-Rust RFB 3.8 avoids external VNC crate advisory risk and keeps strict bounds on framebuffer memory and decompression.
- Negative:
  - The core adds one `Access`, `GrantScope` and `Refusal` variant, two `ApprovalReason` variants and one default method on `Instance`.
  - RFB 3.8 decoding in `mannie-proxmox` supports Raw, CopyRect, Zlib and DesktopSize encodings (standard on QEMU's VNC server); other specialized encodings such as Tight or H.264 are out of scope for version 1.
- Risks:
  - A compromised or misconfigured Proxmox node could send oversized RFB frames or compressed payloads; strict dimension caps (`4096 x 4096`), rectangle count caps and bounded zlib inflation limit memory usage (T-126).
  - A compromised webview could invoke owner VNC input commands on an active session in owner mode or trigger Settings connection tests; the plugin starts off and passwords remain write-only (T-127).

## Alternatives considered

| Option                                                 | Why not chosen                                                                                                                                        |
| ------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Expose every VM the Proxmox user can see automatically | The owner explicitly wants a pre-configure step to select which VMs Mannie may access so sensitive or production VMs stay unreachable                 |
| Connect noVNC directly from the webview to Proxmox     | Violates [ADR-0004](0004-keep-system-access-in-the-rust-core.md) by giving the untrusted webview network access, Proxmox cookies and VNC tickets      |
| Use an external VNC client crate                       | Existing crates add transitive dependencies or lack strict framebuffer memory caps and RFC 6143 SecurityType 2 DES over custom `tokio-rustls` streams |
| Reuse Browser's `Issuer == Subject` self-signed check  | Standard Proxmox VE nodes serve leaf certificates signed by the cluster's local `pve-root-ca.pem`, where Issuer differs from Subject                  |
| Support opaque guest secret references in version 1    | The owner chose owner takeover in the live VNC panel alone as simpler and safer for typing OS installer passwords and disk passphrases                |

## Validation

V16: unit, integration, runtime and end-to-end tests verify TLS OS-trust rejection, certificate inspection without credentials, SHA-256 leaf pinning (including cluster-CA-signed and self-signed certs), certificate mismatch rejection before sending passwords, host/port change clearing both pin and VM allowlist, fail-closed VM allowlist enforcement across every tool and `@` mention, ticket login and renewal, TFA refusal, `Access::ProxmoxVm` validation and per-VM grant matching, worker ceiling refusal (`no_proxmox`), pure-Rust RFB 3.8 handshake (DES VNC auth) and bounded decoding, PNG screenshot delivery via ADR-0044, live VNC side panel canvas updates and owner takeover blocking agent screenshots and input even under full access, session teardown on conversation deletion / project removal / allowlist removal / server edit / plugin off / idle timeout, planted-secret audits, plugin conformance, keyboard operability, pseudo-locale and axe WCAG 2.1 AA checks in light and dark themes.

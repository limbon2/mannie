## Context

- Every side effect is an operation that the policy authorizes, and the policy's last source is the owner ([ADR-0013](0013-journal-every-side-effect.md)). On the master a command asks unless a grant or a rule covers it, a change asks unless the workspace setting allows it, and an access inside Mannie's data and log folders always asks and offers no grant ([operations and approvals](../features/system-tools/operations-and-approvals.md#policy)).
- On a worker, the ceiling decides ([ADR-0028](0028-run-assigned-tasks-under-the-host-ceiling.md), [decision D21](../roadmap/milestones.md#5-decisions)). Even the mode `autonomous` asks for a command that no host rule covers, for an access outside the allowed folders and for any access inside the worker's own folders. The worker's request offers Allow once and Deny, and the owner answers it in the master.
- The owner finds approving every command too slow and asked for a mode like Claude Code's `--dangerously-skip-permissions` or Codex's full access, on the master and on workers, and decided how it works ([decision D22](../roadmap/milestones.md#5-decisions)).
- Mannie assumes that any text the model reads may carry instructions written by someone else, and approvals are the check that limits what such an instruction achieves ([security](../architecture/security.md#6-prompt-injection)).

## Decision

1. Full access is a standing decision of the owner that allows every operation that would otherwise ask. An operation that runs under it is journaled as every operation is, with the decision `full_access`, and its recovery after a crash stays the same. Only the owner switches it: in the UI on the master and in the host's configuration on a worker. Nothing that the model reads can switch it on, create it or extend it.
2. On the master, every conversation has a full access switch. The Tools settings hold "Full access for new conversations", off by default, and a conversation takes that value when it starts; its own switch overrides it afterwards. A conversation's child agents ([ADR-0024](0024-run-child-agent-tasks-in-the-parent-run.md)) follow their parent's switch. The policy reads the switch for every call, so turning it off applies from the next call.
3. A conversation in full access allows every operation without asking: commands, commands with shell metacharacters, changes anywhere, accesses inside Mannie's data and log folders, and a move into a project that the owner's message did not name.
4. A worker's ceiling gains the mode `full_access`, which the host's configuration sets. In it every access runs, inside and outside the allowed folders and inside the worker's own folders, and every command runs. A task narrows it as it narrows any mode, so a task with `read_only` stays read-only.
5. When a worker in another mode asks the owner, and the task's parent conversation on the master is in full access, the master answers the request at once with Allow once, marked as automatic, and the worker records the decision as `full_access`. The host's configuration can refuse this with `allow_full_access_from_master = false`, and then the request waits for the owner as it does today; the default is `true`. Full access never turns a refusal into a run: what a read-only host refuses stays refused.
6. The UI shows full access wherever it acts: the switch on the conversation, which asks for confirmation when it turns on and says that nothing will ask; a mark on the conversation and in the conversation list while it is on; the decision "Allowed by full access" in the details of a call; and in the Workers settings the host's mode and whether it accepts the master's full access.
7. Contracts and stored data change only by addition ([ADR-0002](0002-grow-through-extension-points.md)): the decisions `full_access` and `host_full_access`, the ceiling mode `full_access`, the conversation's switch in its summary and a column of conversations, a field of the Tools settings, a command that switches a conversation, a field of the host's ceiling in `Hello`, and a field of the link's `Approvals.Decide` request that marks an automatic answer.

## Consequences

- Positive: the owner decides for each conversation and each host how much runs without a check, and the default stays the check of today. Every operation is still journaled with what allowed it, and a crash still never runs an operation twice.
- Negative: in full access, text injected into anything that the model reads can run commands and change files with the owner's rights on the master and the worker account's rights on a host, including Mannie's own database, logs and settings and a worker's link key, and no person sees the operation before it runs.
- Risks: the owner forgets that a conversation is in full access. The mark stays visible on the conversation and in the list, a new conversation starts with the setting's value, which is off by default, and turning it off applies from the next call. A host that should never run unchecked work keeps that guarantee with `allow_full_access_from_master = false` and a mode other than `full_access`.

## Alternatives considered

| Option                                                      | Why not chosen                                                                                                                          |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Grants and rules only, as today                             | The owner still approves every command that no rule covers                                                                              |
| A grant that covers everything                              | It would be full access without its mark, its setting or its place in the journal                                                       |
| One global switch for every conversation                    | The owner chose a default for new conversations and a switch on each one (D22)                                                          |
| Full access that keeps Mannie's own folders asking          | The owner chose that nothing stays protected (D22)                                                                                      |
| Full access only from the host, or only from the master     | The owner chose both (D22); the host keeps the last word through `allow_full_access_from_master`, as workers own their hosts (ADR-0015) |
| The master's full access as a flag in the task's assignment | The worker would keep the flag for the whole task, so turning full access off would not reach a task that runs                          |

## Validation

M4: unit tests of the policy for full access with every other source; runtime tests in which a conversation in full access and its child agents run commands and changes without asking, turning it off asks from the next call, a host in `full_access` runs everything, a full-access conversation answers a worker's request automatically and the worker records `full_access`, and a host that refuses the master's full access asks; link tests of the automatic answer; and end-to-end tests of the switch, its confirmation, the marks and a command that runs without a request, with axe.

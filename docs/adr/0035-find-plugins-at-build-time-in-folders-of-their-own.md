## Context

- The owner decided that adding a plugin must need nothing in the core, as if a third party had written it ([decision D32](../roadmap/milestones.md#5-decisions)). Today a plugin edits lists outside its folder: the workspace members and path dependencies in `Cargo.toml`, `deny.toml`, the desktop's `Cargo.toml`, `state.rs`, `build.rs`, `ipc.rs` and `capabilities/main.json`, `registrations/plugin-list.ts`, the message catalog, `cspell.config.yaml` and the core's documents, and a plugin with programs or contracts also edits the Taskfile, the workflows and `buf.yaml`. Its UI files, tests and messages live in the core's folders ([ADR-0030](0030-split-mannie-into-a-core-and-plugins.md) d10).
- ADR-0030 d2 lists the plugins in code because plugin code is reviewed like the core's and nothing is discovered, downloaded or loaded at run time. ADR-0002's refinement in M5 and rule 2 of the [extension points](../architecture/extension-points.md#1-rules-for-every-extension-point) say that registration is explicit code and that nothing is discovered by scanning.
- Facts verified by experiment on 2026-10-17 with Cargo 1.99.0, Tauri CLI 2.12.2, Vite 8.3.4, SvelteKit 3.0.1, Svelte 5.57.2, Paraglide JS 2.27.0 with its message-format plugin 4.5.2, Tailwind CSS 4.3.3, Vitest 5.0.4 and ESLint 10.12.0:
  - Cargo has no way to depend on every crate that matches a pattern. A build script cannot add dependencies. linkme and inventory still need a dependency and a reference in code.
  - A workspace member glob that matches nothing fails, and so does a matched folder without `Cargo.toml`.
  - A path dependency into a generated folder that does not exist yet stops the whole workspace from loading, including `cargo metadata` and rust-analyzer.
  - Adding a crate to the root workspace changes the root `Cargo.lock`, and every cargo call in the Taskfile that builds, tests or runs code passes `--locked`.
  - A binary crate whose `package.workspace` points at a generated workspace builds with the Tauri CLI: `tauri build` produced the NSIS installer, the installed app ran, and `-- --locked` passed. `tauri dev` rebuilt after edits in core and plugin crates once `tauri.conf.json` listed their folders in `additionalWatchFolders`, and a root `.taurignore` kept UI edits on Vite's hot reload. A library that the binary uses must not sit below the binary's folder. This was checked on Windows only.
  - A lockfile for that generated workspace can be seeded from committed lockfiles and normalized offline, and a check can require each of its registry packages to equal an entry in a committed lockfile. Adding a plugin left the other lockfiles byte-identical.
  - Vite compiles Svelte files outside the app's folder with the app's Svelte options, and `vite dev` serves the imported ones without a `server.fs.allow` entry, which `plugins/` needs only for assets and `?url` requests. A folder without `package.json` never changes `pnpm-lock.yaml`, and it cannot resolve npm packages that only the app has.
  - An inlang project accepts an array of `pathPattern` sources and compiles them into one catalog for each locale. It reports neither duplicate keys nor missing files.
  - Tailwind's `@source`, TypeScript's `include` and ESLint's file globs accept `plugins/*/...`, and so does Vitest's `include` once its `test.dir` is the repository root. ESLint's type-aware rules need a root `tsconfig.json` that references the app. Vite's and Tailwind's globs and inlang's paths that match nothing load nothing, with no warning.

## Decision

1. A plugin is the folder `plugins/<id>/`, and adding a plugin changes no committed file outside that folder. The folder holds:
   - `plugin.toml`, the manifest: the ID, which equals the folder's name; the SDK major; the order of starts and of the Plugins page; the entry crate; the services, secret entries and third-party crates that only this plugin may use; its programs, with the library crates that only they use, their targets, signing, self-check, smoke scripts and end-to-end build; and its contracts, such as protobuf packages. A JSON Schema in the SDK describes it;
   - `Cargo.toml` and a committed `Cargo.lock`, a Cargo workspace of the plugin's own, with its crates in `crates/` and its programs beside them;
   - `ui/`, a plain folder without `package.json`, whose `index.ts` exports the plugin's `definePlugin`, and `ui/generated/`, which is git-ignored;
   - `messages/<locale>.json`, with every key under the plugin's prefix;
   - `tests/ui/` and `tests/e2e/`, while Rust tests stay in each crate's `tests/`;
   - `docs/`, with the plugin's feature document in `README.md` and its own ADRs in `docs/adr/`;
   - `CHANGELOG.md` with `## Unreleased`, and `cspell-words.txt`.
2. Nothing is discovered or loaded at run time. At build time, a folder under `plugins/` with a `plugin.toml` registers a plugin, and the manifest in the plugin's change is the reviewed registration. The reason of ADR-0030 d2 stays: plugin code is reviewed like the core's, and what runs is fixed by the build.
3. `task gen` runs `scripts/plugins/generate.mjs`, which checks the manifests and writes every list that names plugins into git-ignored folders: the launcher workspace and its plugin list crate, the plugin bindings program, the index of manifests and interfaces, each plugin's bindings, constants and message barrels, the UI's static plugin list and catalog, the inlang projects, the spelling words and an editor workspace. It writes a file only when its content changed. Its `--check` mode, which a new `task lint:plugins` runs together with the message check of decision 8, reports stale output. It writes a fingerprint last, after the boundary checks pass, and the desktop binary's build script refuses to build when plugin files changed since, with the message "The plugins changed since `task gen` ran. Run `task gen`."
4. Mannie builds from three kinds of Cargo workspace, with one target folder that `.cargo/config.toml` sets:
   - The root workspace holds the core's crates in `crates/` and `mannie-desktop-core` in `apps/desktop/core/`, a library with the desktop app's code. It excludes `plugins`, `.generated`, `apps/desktop/src-tauri` and `tests/fixtures/plugins`, so it loads on a fresh clone and its committed `Cargo.lock` pins the core and Tauri.
   - Each plugin's workspace, in its folder, with its own committed `Cargo.lock`. It reaches the SDK, the harness and the host kit as path dependencies and repeats the root's package settings and lints, which a check keeps equal.
   - The launcher, `.generated/desktop/`, which `task gen` writes. It holds the binary `mannie-desktop` in `apps/desktop/src-tauri/`, whose `Cargo.toml` names the launcher as its workspace, and the generated crate `mannie-plugin-list`, which depends on every plugin's entry crate and returns the plugins in the manifests' order, with a fixture plugin behind the `validation` feature. The binary keeps `tauri.conf.json`, `build.rs`, the capabilities and the icons, and its build script generates an inlined Tauri plugin and a capability for each plugin (ADR-0034 d8).

   Two crates now use Tauri, `mannie-desktop-core` and `mannie-desktop`, which changes [ADR-0003](0003-build-the-desktop-app-on-tauri-2.md) d2 and the Tauri ban of [ADR-0008](0008-one-workspace-two-binaries.md) d3. Tauri still never reaches the crates in `crates/`, the plugins or the worker, and cargo-deny checks that.

5. Lockfiles stay committed and builds stay locked. `task gen` seeds the launcher's lock, which is git-ignored, from the root's and every plugin's lock, normalizes it offline and requires every registry package in it to equal, by name, version, source and checksum, an entry in a committed lock. Every build after that passes `--locked`. A check requires every crate that two committed locks pin within one compatible range to have the same version and checksum. No committed lock is written by `task gen`, `task dev`, `task build`, `task e2e` or the release build. Only these tasks write committed locks: `task deps:update`; `task deps:align`, which brings plugin locks to the root's versions; `task plugins:lock ID=<id>`; `task plugins:new ID=<id>`, which seeds a new plugin's lock from the root's; and `task release:prepare`, which also sets the version in every workspace. cargo-deny and cargo-about run for every workspace and for the launcher's graph ([ADR-0017](0017-license-and-dependency-policy.md)), and the release archives the launcher's lock with the SBOMs ([ADR-0018](0018-release-from-tagged-builds.md)).
6. The boundaries of ADR-0034 d2 are checked where the owner builds (D24):
   - `generate.mjs`: manifest errors, IDs that break the rules or nest with another prefix, a matched folder without `Cargo.toml`, and path dependencies that leave the plugin's folder other than the SDK, the harness and the host kit;
   - `scripts/plugins/check-boundaries.mjs`, in `task gen` and `task lint:deps`: the dependency rules from `cargo metadata` of every workspace and the launcher, for every dependency kind and target, and glob re-exports in the SDK;
   - the binary's build script: the fingerprint;
   - a Vite plugin in `vite dev`, `vite build` and Vitest: imports that leave a plugin's folder and the SDK, core imports of plugin files, and the transport imported by a hand-written file;
   - ESLint, by folder: a plugin's UI imports only the SDK, its own files and its generated files, never Tauri, `#lib`, `$app` or another plugin, and core files never name a plugin's message keys. The rules of the desktop app's block, which allow text only from the catalogs and refuse network globals, `$app/stores` and `invoke`, also cover `plugins/*/ui/**`, and plugin files may not use `__TAURI_INTERNALS__`;
   - cargo-deny for every workspace, a generalized check that headless programs never reach Tauri, GTK or WebKitGTK (V5), and Clippy on plugin library crates with a configuration of the core that refuses direct process, file-write and socket calls, whose allowed exceptions `task plugins:grants` lists.
7. The UI finds plugins through the generated static list `apps/desktop/src/lib/generated/plugin-list.ts`, which imports each plugin's `ui/index.ts` and carries a catalog entry also for a plugin without UI, and a validation list that adds the fixture plugin. `registrations/plugin-list.ts` goes. The app's configuration learns `plugins/*` once, through globs and aliases: `vite.config.ts`, the tsconfig files and a root `tsconfig.json` that references the app, `src/app.css`, the ESLint configuration, the WebdriverIO configuration, `.prettierrc.json`, `.gitignore`, `tauri.conf.json`'s watch folders and a root `.taurignore`. A plugin's UI cannot add an npm package: the SDK adds it to the app, passes the license review and re-exports it.
8. Messages: the core keeps `apps/desktop/messages/<locale>.json`, and each plugin keeps its own catalogs. `task gen` writes a git-ignored inlang project whose `pathPattern` lists the core's file and then each plugin's file in the manifests' order, so Paraglide still compiles one catalog for each locale with one `m` namespace. Each plugin gets a barrel of its own keys, so svelte-check refuses another plugin's key. `scripts/plugins/check-messages.mjs` refuses keys outside their file's prefix, a key in two sources, a missing `<prefix>_plugin_name` or `<prefix>_plugin_description`, and a plugin catalog for a locale that the core does not register. The pseudo-locale comes from every source, and `task gen` also writes one project for each source for translation tools. Adding a language registers the locale once and adds a file to the core and to each plugin.
9. Tests of the core use a fixture plugin in `tests/fixtures/plugins/example/`, which only validation builds link, and never the real plugins. Vitest, WebdriverIO and the script tests also read `plugins/*/tests/`, and the test-location rule admits them.
10. The build, the release, CI and the end-to-end tests iterate over the manifests' `[[programs]]`, and the contract checks over `[[contracts]]`, each plugin with its own `buf.yaml`. A plan job turns the manifests into CI and release matrices, and the path filters become the static `plugins/**` in place of today's `plugins/workers/**`. A FreeBSD host and the nightly FreeBSD run build the worker from its plugin's workspace with cargo alone, without Node or generated files.
11. A plugin's documents live in `plugins/<id>/docs/`. Its `README.md` is its feature document, with a `Plugin` field that equals the folder's ID and an optional `Milestone`, and it needs no link from the roadmap. Its own ADRs, such as one for a significant dependency that only it uses, live in `plugins/<id>/docs/adr/` with an index there, and the documentation checks read them. An ADR that changes the SDK or the core stays in `docs/adr/`. Scheduling a plugin in a milestone and accepting its ADRs stay the owner's entries in the decision record. This changes the [feature protocol](../features/README.md), which puts feature documents in `docs/features/` and gives every accepted feature a line in the roadmap, the convention of [the documentation](../README.md) that a feature document has a milestone row, and the rule of the [milestones](../roadmap/milestones.md#1-delivery-approach) that an accepted feature gets a line there. The other documentation checks reach `plugins/**` through their globs, and `release.mjs` folds each plugin's `## Unreleased` into the root changelog under the plugin's name.
12. `task gen` writes `.generated/mannie.code-workspace`, which links the root, the launcher and every plugin workspace for rust-analyzer, so a new plugin needs no edit in an editor's settings.
13. On a fresh clone, cargo works at the root and in each plugin workspace. `task setup` fetches every committed workspace once and runs `task gen`. Before that, a cargo build of the desktop binary fails because `.generated/desktop/Cargo.toml` does not exist, which CONTRIBUTING explains, and `task build` and `task dev` stop in `task gen` with a message that names `task setup`. `task plugins:new ID=<id>` copies the fixture plugin as a template, with a lock seeded from the root's.

## Consequences

- Positive: a plugin is one folder that can be reviewed, copied and removed as a whole. Adding one that needs nothing new from the core changes no committed file elsewhere, including `Cargo.lock`, `pnpm-lock.yaml` and every list and documentation index, and a planted plugin in a scratch clone proves it. The core's workspace builds and tests without any plugin. Each plugin's dependencies stay pinned in its own lock, and the shipped graph stays fully locked.
- Negative: three kinds of Cargo workspace instead of one. A dependency bump in the core runs `task deps:align`, which rewrites plugin locks, and a release sets the version in every workspace. The desktop's Rust splits into two crates. rust-analyzer sees plugin tests through the generated editor workspace. The generator, the lock seed and the checks are scripts that the repository has to keep. Plugin UIs share the app's npm packages. Adding a plugin still changes files outside its folder when it needs a newer compatible version of a crate that a committed lock pins, which `task deps:update` brings into the root's lock first, or a shadcn-svelte component, a bits-ui primitive or an npm package that the SDK does not re-export yet, which is an SDK change in `apps/desktop`. Each is a core change ahead of the plugin.
- Risks: the launcher layout was verified with the Tauri CLI on Windows only. A spike on Linux with WebKitGTK, including `tauri build` for deb and rpm, `tauri dev` and the validation build, runs before the layout lands. If it fails, the fallback makes plugin crates glob members of the root workspace with a generated plugin list crate, in place of decisions 4 and 5. The root workspace then loads only after `task gen`, which changes decision 13, and adding a plugin changes the root `Cargo.lock` through a tool, which needs the owner's ruling against D32. Globs that match nothing fail silently in Vite, Tailwind and inlang, so the generator's own checks run in `task gen` and `task lint:plugins`.
- Refinement in step 0 ([M5 validation results](../roadmap/m5-validation.md#11-plugin-sdk-spikes-step-0)): the spikes on Windows made these decisions concrete. In decision 5, `task gen` first checks every committed lock with `cargo metadata --locked --offline`, runs the agreement check before it seeds, because Cargo keeps one of two disagreeing versions and the pin check cannot tell, seeds also from the fixture plugin's lock, because Cargo locks the plugin list's optional dependencies whatever features a build enables, and normalizes with `cargo metadata --offline`, never `cargo generate-lockfile`, which resolves again. `task plugins:lock` runs `cargo update --workspace --offline` and uses the network only when Cargo's cache lacks a crate, `task setup` also fetches the fixture plugin's workspace, and the generator turns Cargo's offline failures into messages that name `task setup` or `task plugins:lock ID=<id>`. cargo-about runs on the launcher and on each plugin workspace with a released program. In decision 6, `deny.toml` names no plugin crate: `mannie-desktop-core` joins the wrappers of `tauri`, `mannie-secrets` and `rfd`, and `check-boundaries.mjs` checks each manifest's crates that only the plugin may use. The Clippy rule covers the library crates that a plugin's entry crate reaches and lists the process, file and socket methods and types in full, with tonic's connect and serve calls. In decision 8, the generated inlang project also copies `paraglide.config.js`, `task lint:messages` passes `--source ./src ../../plugins`, the pseudo-locale reads every source, and `vite.config.ts` stops with "Run `task gen`." when the project is missing. In decision 12, the editor workspace links the root, then the plugins, then the launcher, because rust-analyzer analyzes a file that several workspaces share in the first linked workspace that holds it, and its find-references and rename do not cross workspaces. Features unify differently in each workspace, so a root build after a launcher build recompiled 98 crates, and a cold `task test` compiled 37% more units. Linux, WebKitGTK and FreeBSD stay open.
- Refinement in step 6: decision 6's allowed exceptions are grants of the manifest. Its `[native]` table names the categories `file-writes`, `processes` and `sockets`, each with its reason, which `Manifest::parse` and `task gen` refuse when it is blank. `scripts/plugins/check-native.mjs`, in `task lint:rust`, runs Clippy on the library crates that a plugin's entry crate ships, with their default features, the root's `clippy.toml` and the methods and types of std, tokio, tonic and reqwest in every category that the manifest does not grant. It fails when Clippy cannot resolve a path of std outside `std::os`, which Clippy only warns about, and when the crates' sources suppress the rule's lints, or a group that holds them, with `allow` or `expect`, so a grant stays the only exception. A build script may suppress them, since it runs only where the plugin builds. `task plugins:grants` prints each plugin's grants. Workers grants `sockets` for the link, and Images and the fixture plugin grant nothing.
- Refinement in step 7: decision 11's changelog of a plugin, `plugins/<id>/CHANGELOG.md`, keeps an Unreleased section with the kinds of change of Keep a Changelog, and `task release:prepare` moves its lines into the root's section under each kind and a heading with the plugin's name from its English catalog. The fixture plugin's changelog is the template's. A plugin's own ADRs are numbered on their own, beside their index in `plugins/<id>/docs/adr/README.md`, which the documentation checks hold to the same rules as the core's, and the plugin's documents may name them. When the documents of Workers and Images moved, the migrations kept their text, since stored data does not change, so their comments still name the old paths.

## Alternatives considered

| Option                                                                                  | Why not chosen                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One root workspace with plugin crates as glob members and a generated plugin list crate | Adding a plugin rewrites the root `Cargo.lock`, a committed file outside its folder. A path dependency into the generated crate also stops the whole workspace from loading until `task gen` runs. It is the fallback if the launcher fails on Linux |
| A committed plugin list, kept in sync by a check                                        | Every plugin would edit a file outside its folder, which D32 rules out                                                                                                                                                                               |
| Distributed registration with linkme or inventory                                       | It still needs a dependency and a reference in code for each plugin, and two new crates with a license review                                                                                                                                        |
| `import.meta.glob` over `plugins/*/ui/index.ts`                                         | A glob that matches nothing builds silently, a plugin without UI would have no catalog entry, and the fixture plugin would reach release builds                                                                                                      |
| A pnpm workspace package for each plugin's UI                                           | Adding a plugin would change `pnpm-lock.yaml`                                                                                                                                                                                                        |
| Cargo features that select plugins                                                      | The owner turns plugins on and off in one installed app (ADR-0030), and features would still list each plugin in a committed manifest                                                                                                                |

## Validation

M5:

- Generator tests with planted manifests: a bad ID, a reserved ID, a Tauri plugin's name, a nested prefix, a folder that does not match its ID, an unknown service, a missing entry crate, a crate folder without `Cargo.toml` and an SDK major that is too new. Output is written only when it changed, and `--check` reports stale output.
- Lock tests: the seed, offline normalization, a pin check that refuses a package absent from the committed locks, disagreeing versions refused, and `--locked` builds after `task gen`.
- Boundary tests with planted violations in Rust, TypeScript and messages, and the fingerprint refusal after a plugin edit without `task gen`.
- A planted plugin: in a scratch clone, the fixture copied to `plugins/zz-planted`, then `task gen` and the validation build. The plugin shows on the Plugins page, and `git status` lists only `plugins/zz-planted`.
- A fresh clone on Windows and Linux runs `task setup`, `task ci` and `task e2e`. The worker builds from its plugin workspace with cargo alone on Windows, Linux and FreeBSD. A release dry run produces the notices and SBOMs from the launcher.

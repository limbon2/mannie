## Context

- The owner wants SQLite databases in Mannie as "an optional subplugin for workers", and described it as "an optional feature that can be enabled/disabled in a plugin" ([decision D46](../roadmap/milestones.md#5-decisions)). The owner chose a switch for it, nested under Workers on the Plugins page, with its code in `plugins/workers/`, so that the worker service can run it ([Databases](../../plugins/workers/docs/databases.md)).
- The design has no such part today:
  - A plugin is on or off as a whole (ADR-0030 d7). The owner's choices are one map, `PluginsSettings.enabled` in `crates/mannie-types/src/plugins.rs`, and the host changes one plugin at a time (`PluginHost::set_enabled` in `crates/mannie-plugins/src/host.rs`).
  - The runtime keeps a plugin's contributions as one group with one generation (`crates/mannie-runtime/src/plugins.rs`). It takes all of them or none, refuses a second group for a plugin that has one, and drops them together. A tool execution checks its plugin's generation, so a call into a plugin that went off and on again never runs (ADR-0030 d8, ADR-0036 d7).
  - A plugin binds the services that its manifest declares when it starts (ADR-0034 d5). A service that only an optional part uses would stay bound while that part is off, which for a sensitive service, such as the one that ADR-0056 adds, is more than the owner turned on.
  - A plugin never depends on another plugin (ADR-0030 d10), and the manifest has no field for dependencies. ADR-0031 rejected a separate plugin for the worker service, and only Workers' own code runs in the worker (ADR-0034 d12), so a separate database plugin could not put code into the worker.
- Facts of this repository, verified on 2026-11-01:
  - The manifest refuses unknown fields (`Manifest::parse` in `crates/mannie-plugin-sdk/src/manifest.rs`), `task gen` checks manifests in `scripts/plugins/lib/manifests.mjs`, and a plugin's name and description are its messages `<prefix>_plugin_name` and `<prefix>_plugin_description`, which `scripts/plugins/lib/ui.mjs` writes into the generated list.
  - The slots show an entry only while its plugin is on, and decide by the registration that added the entry (`apps/desktop/src/lib/state/shell-slots.svelte.ts`). The entry types in `apps/desktop/src/lib/types/shell-slots.ts` are shared with the core's own entries.
  - Turning a plugin off removes its contributions, refuses its commands with `plugin_off`, ends its channels, waits up to 5 seconds for its calls and tool executions, and then stops it ([plugins](../features/plugins.md)).
  - The executors point allows one entry per plugin, whose ID is the plugin's ID.

## Decision

1. A plugin may have optional features. A feature is a part of a plugin that the owner turns on and off on its own while the plugin is on. Its code is the plugin's code, in the plugin's folder and crates, under the plugin's dependency rules (ADR-0034 d2). A feature belongs to one plugin, and features do not nest.
2. The manifest lists each feature as a table `[features.<id>]`. A feature's ID follows the rules of a plugin's ID (ADR-0030 d3). The table may declare `services`, in the form of the plugin's `[services]`. A service is declared by the plugin or by one of its features, never by both, and `task gen` refuses a manifest that breaks this. The manifest gives a feature no default: every feature starts off, and only the owner turns it on.
3. The plugin's catalog names each feature with `<prefix>_feature_<id>_name` and `<prefix>_feature_<id>_description`, with underscores in place of the ID's hyphens. `task gen` refuses a feature without both messages, and the generated plugin list carries them.
4. The owner's choices are kept in the core's settings section `plugins`, in a new field `features`: for each plugin's ID, whether each of its features is on. The field has a default, so the section keeps version 1. A feature's choice outlives its plugin's switch: turning Workers off keeps the choices of its features, and turning it on starts the features that are on.
5. A feature starts on the running plugin. The SDK's `Instance` gains `start_feature(FeatureContext)`, which returns `FeatureStarted`: the feature's contributions, its command and channel handlers, and a `FeatureInstance` with `work` and `stop`. The default implementation fails with the new start failure `feature_unknown`. `FeatureContext::service::<S>()` binds only the services that the feature declares, so a feature's sensitive service is bound while the feature is on and released when it stops. The plugin's `Interface` names the commands and channels of each feature (`Interface::feature`), so the host and the generated bindings know them before any start.
6. The runtime keeps contributions by contributor: the plugin, or one of its features. Each contributor has a generation of its own. A feature's group is added and removed on its own, all or nothing, and turning the plugin off removes its features' groups with its own. The registries that the runtime keys by plugin key by contributor, so turning a feature off waits only for its own work: the plugin executions, the plugins of agents, the drains of tool sources, the sources of terminal hosts and the background commands. A feature contributes to every point except task executors, whose ID rule allows one entry per plugin.
7. The host starts a plugin, then each of its features that is on, in the order of the manifest. A feature that fails to start leaves the plugin on, shows as failed under it with "Try again", and keeps the owner's choice, as a plugin does (ADR-0030 d6). Turning a feature off follows the order of turning a plugin off: the host stores the choice, removes the feature's contributions, refuses its commands with the new host refusal `feature_off`, ends its channels with the new end `feature_off`, waits up to 5 seconds for its calls and executions, then stops it and releases its services. A call that this wait aborts ends as on plugin-off (ADR-0036 d7), and the model reads that the owner turned the feature off. Turning the plugin off stops its features first. When a feature has work in progress, its switch asks first, with the items of `FeatureInstance::work`.
8. Dispatch checks a command in this order: shutting down, plugin off, unknown command, feature off, then the input's size, decoding and checks. A feature's handlers run in a set of calls in flight of their own, so turning the feature off waits only for them, and a call that the feature's stop aborted answers `feature_off`.
9. The contracts grow by addition: `HostRefusal::FeatureOff` and `SubscriptionEnd::FeatureOff`; a `feature` field on the not-run reason and the interruption `plugin_off`; `features` in the view of a plugin, each with its ID, its state, the owner's choice, the code of a failed start and what it may use; the core commands `set_plugin_feature_enabled` and `plugin_feature_work`; and the error `unknown_feature`.
10. A plugin's UI registers a feature's parts through `context.feature(id)`, which has the plugin context's `slots`, `isOn` and `whileOn`. The slots show the feature's entries only while the plugin and the feature are on. The Plugins page lists each feature under its plugin, with its name, its description, what it may use and a switch, which is disabled while the plugin is off and shows the owner's choice. The address of a view, a settings page or a side panel of a feature that is off says that the feature is off, names its plugin, and links to the Plugins page, as for a plugin that is off.
11. The harness gains `turn_feature_on` and `turn_feature_off`, and `conformance()` checks each feature: its commands answer `plugin_off` while the plugin is off and `feature_off` while the feature is off, its start hands over exactly the commands and channels that its interface names, its inputs refuse unknown fields, it stops and starts again, turning the plugin off stops it first, and a feature of the manifest that the plugin cannot start fails with `feature_unknown`. The fixture plugin gets a feature, which `task plugins:new` copies.

## Consequences

- Positive: a plugin grows optional parts without becoming several plugins that depend on each other, and the owner turns off what they do not use. A sensitive service is bound only while the part that needs it is on. Databases can live in Workers, whose worker service runs Workers' own code.
- Negative: the host, the runtime's registries, dispatch and the slots gain a second level, and every registry that keys by plugin changes its key. The Plugins page shows more switches and states, and the manifest and the catalogs grow. Each plugin with features carries more conformance checks.
- Risks: a feature's parts could rely on state that only the plugin's start sets up, and break when the feature starts alone; the feature starts on the running `Instance`, and `conformance()` starts, stops and starts each feature again. "Feature" already names a feature document and a link's feature level, so the glossary defines "plugin feature" apart from both.

## Alternatives considered

| Option                                                  | Why not chosen                                                                                                                                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Tagging a feature's contributions at the plugin's start | Every reader of the registry would filter hidden entries, one generation would serve both, and the feature's handlers would exist while it is off, against ADR-0034 d4               |
| A plugin for each optional part, with dependencies      | Breaks ADR-0030 d10 and ADR-0035 d1, and the build, the host and every boundary check would learn the order of dependencies; another plugin's code still could not run in the worker |
| A switch in each plugin's own settings page             | Each plugin would rebuild the states, the question and the draining, the Plugins page would not show what is on, and the part's services would stay bound                            |
| A default for a feature in the manifest                 | Nothing reads it (ADR-0035 d1): a feature is new to every owner, who turns it on                                                                                                     |

## Validation

M15:

- Host and dispatch tests: a feature starts after its plugin and only while it is on, a failed feature leaves the plugin on, turning a feature off refuses its commands with `feature_off`, ends its channels and waits for its calls, and turning the plugin off stops its features first.
- Runtime tests: a feature's tools reach the runs that start while it is on, a run keeps the tools that it started with, a call of a feature that went off and on again never runs, and turning a feature off drains only its executions.
- `conformance()` with the fixture plugin's feature, and the generator's tests with planted errors: a service that the plugin and a feature both declare, and a feature without its messages.
- Unit tests of the slots and the Plugins page, and `tests/e2e/specs/plugins.test.ts`: the fixture's feature turns on and off from the keyboard without a reload, with axe passing in both themes on WebView2 and WebKitGTK.
- Spike S7 of M15: feature generations while a run uses a feature's tool and the feature goes off and on.

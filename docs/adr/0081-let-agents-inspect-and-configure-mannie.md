## Context

- The owner wants Mannie's conversation agent to understand Mannie itself (storage layout, database, backups, logs, credential store, plugins and settings) so it can diagnose broken setups and configure Mannie and its plugins directly from chat without the owner opening Settings.
- Today, the agent knows only the operating system, shell, workspace and the narrow instruction sections contributed by plugins that are already enabled. Mannie's data and log folders are protected by T-18 so raw file reads and writes always prompt, and direct edits to `mannie.sqlite` are unsafe.
- Mannie caps each model request at 128 tools ([agent runtime](../architecture/agent-runtime.md#4-model-calls)). Adding separate tools for each of the 15 core configuration domains and 10 plugins would add more than 60 tools to every request, burn tokens on unrelated chats and still leave off plugins unreachable until a later turn.
- On 2026-11-26, the owner approved four boundaries (D75):
  - hybrid secret entry: masked secret inputs directly on the inline chat approval card by default so sensitive credentials never enter chat, the model provider, SQLite or logs, plus an optional top-level `secrets` map on `mannie_configure` for throwaway credentials the owner chooses to type in chat, scrubbed before the tool-call part is stored or published;
  - always-ask authorization: every configuration change asks for `Allow once` or `Deny` with no reusable grants or rules, even when conversation full access is on, and workers refuse it outright;
  - read-only inspection and bounded reading of Mannie's redacted logs run without prompting for conversation agents;
  - full coverage across core settings, diagnostics and all 10 plugins through a new Plugin SDK extension point.
- Earlier decisions that this design touches:
  - [ADR-0010](0010-keep-provider-credentials-on-the-master.md) and SO-2 in [security](../architecture/security.md): secrets never reach logs, SQLite, transcripts or models; throwaway credentials typed in chat still cross the owner's chat message to the provider, while Mannie keeps them out of tool-call records, accesses, plugin tables, logs and exports.
  - [ADR-0013](0013-journal-every-side-effect.md): `Access`, `ApprovalReason`, `Refusal` and `ToolOutcome` are exhaustive across the core.
  - [ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md): conversation full access allows most accesses without asking, except explicit exceptions such as Browser sites and credentials.
  - [ADR-0030](0030-split-mannie-into-a-core-and-plugins.md) and [ADR-0034](0034-build-plugins-on-a-plugin-sdk.md): the core never depends on plugins, and plugins expose new capabilities only through SDK extension points.
  - `DecideApproval` crosses the Workers link as JSON (`Serialize + Deserialize`), while `Secret` deliberately does not implement `Serialize`.

## Decision

1. Add three runtime-owned tools to `mannie-runtime` when the desktop composition root binds an `AppHost` port (never on workers):
   - `mannie_inspect` (`PermissionClass::ReadOnly`): returns Mannie's runtime metadata, canonical paths (data folder, SQLite database, backups, logs, skills, browser data), database schema health, installed plugins and optional features with their live states (`on`, `off`, `failed`), self-knowledge and troubleshooting guides, secret-free configuration snapshots for any core domain or active plugin, and exact JSON Schemas for any action.
   - `mannie_read_logs` (`PermissionClass::ReadOnly`): lists and reads bounded, filtered excerpts of Mannie's daily JSON logs and crash logs strictly inside canonical `app_log_dir` (refusing path separators, `..` and symlinks). Log lines already passed through `mannie-logging`'s `Redactor`.
   - `mannie_configure` (`PermissionClass::SideEffects`): performs validated configuration actions against any of the 15 core domains or any active plugin's `ManagementProvider`, going through the full `prepare` -> `decide` -> `ask` -> re-`prepare` -> durable `Executing` journal -> `execute` lifecycle ([ADR-0013](0013-journal-every-side-effect.md)).
   - `mannie_inspect` and `mannie_read_logs` are offered to `Requester::Owner` conversation agents (including read-only conversation agents such as `Plan`). `mannie_configure` is offered only to non-read-only `Requester::Owner` conversation agents. Child agents (`explore`, `general`, custom child agents) and workers receive none of these three tools.
2. Add a static core instruction section `mannie` (position 155, when `mannie_inspect` is offered) explaining the three tools, forbidding direct edits to Mannie's SQLite files and instructing the model not to ask for real passwords in chat text, plus a compact dynamic section `mannie-state` (position 305) naming Mannie's version and installed plugins with their live states.
3. Add `Access::AppConfig` (with `owner`, `domain`, `action`, `title`, sanitized `fields`, `secret_fields` metadata without values, `security_sensitive`, canonical `payload` and `payload_cut`), `ApprovalReason::AppConfig`, `ApprovalReason::AppConfigSecurity`, `Refusal::NoAppConfig`, `ToolsError::SecretRequired`, `ToolsError::SecretInvalid` and `ToolOutcome` variants (`MannieInspect`, `MannieLogs`, `MannieConfigure`) in `mannie-types`:
   - `Access::AppConfig::changes()` is `true`.
   - `takes_full_access` returns `false` for `Access::AppConfig`: every configuration change asks for `Allow once` or `Deny` with empty `grants` and `rule = None`, even when conversation full access is enabled ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md) refined).
   - A worker's policy ceiling refuses `Access::AppConfig` with `Refusal::NoAppConfig` in every ceiling mode.
4. Keep `DecideApproval` unchanged for the Workers link and add a master-only IPC command `decide_config_approval` taking `DecideConfigApproval { conversation_id, part_id, digest, allow, secrets: BTreeMap<String, Secret> }` (`Deserialize` only, never `Serialize`):
   - Sensitive credentials enter through masked inputs rendered on `ToolApproval.svelte` for each declared `ConfigSecretField`, going straight from the approval card over IPC to Rust and the OS credential store without touching the model, transcript, SQLite or logs.
   - If the owner types a throwaway credential in chat and the model places it in `mannie_configure`'s top-level `secrets` map, `RunActor::complete_arguments` extracts and scrubs those values to `"[redacted]"` before storing `Change::Delta` or publishing events, holding the `Secret` values only in an in-memory map cleared on drop for that single call. Any value entered on the approval card overrides a chat value.
   - Plain `decide_approval` rejects `AllowOnce` when a required secret field has no value from chat or the card (`ToolsError::SecretRequired`).
5. Add a new Plugin SDK extension point `points::management` (`Management`, `NAME = "management"`, `MAJOR = 1`, `IDS = IdRule::Owned`) in `mannie-plugin-sdk` and consume it in `mannie-runtime`:
   - A plugin (or optional feature such as `workers.databases`) registers a `ManagementProvider` providing `guide()`, secret-free `inspect(query)`, side-effect-free `prepare_action(...)` and `execute_action(...)` (receiving resolved `BTreeMap<String, Secret>`).
   - `mannie_inspect` and `mannie_configure` read `runtime.contributions()` live rather than from the run's start-of-turn snapshot, so enabling an off plugin via `mannie_configure(target = "plugins", action = "set_enabled")` makes that plugin's management actions immediately usable in the next step of the same reply (while its operational tools enter on the next user turn per [ADR-0030](0030-split-mannie-into-a-core-and-plugins.md), decision 8).
   - Implement `ManagementProvider` across all 10 plugins (`ssh`, `mcp`, `proxmox`, `terminal`, `network`, `notebooks`, `browser`, `workers` + `workers.databases`, plus read-only guides for `git` and `images`), reusing each plugin's existing managers, validation, SQLite statements, OS credential entries and live channels.
6. Record threats `T-128` through `T-134` in [security](../architecture/security.md).

## Consequences

- Positive:
  - The owner can diagnose issues and configure Mannie and every plugin directly in chat, even when a plugin starts off.
  - Adding only three tools keeps prompt overhead small and avoids colliding with the 128-tool cap.
  - Sensitive passwords and API keys stay out of chat and provider traffic via inline masked approval inputs, while throwaway credentials still work quickly without hitting SQLite or logs.
  - Core and plugin boundaries stay strict: the core knows no plugin's schema or commands.
- Negative:
  - The model makes one `mannie_inspect` call to fetch an action's schema before calling `mannie_configure` for unfamiliar actions.
  - `Access`, `ApprovalReason`, `Refusal`, `ToolsError` and `ToolOutcome` each gain variants, and `ToolApproval.svelte` renders masked inputs for configuration approvals.
- Risks:
  - A model might put a password inside `arguments` instead of `secrets`; `complete_arguments` scrubs known secret key names as defense in depth and `prepare` refuses secret-named keys in `arguments` (T-129).
  - An owner who types a production password in chat text exposes that message to the model provider; the instructions and UI direct the owner to use the masked approval card input for real credentials.

## Alternatives considered

| Option                                                         | Why not chosen                                                                                                          |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Register dedicated tools per core domain and per plugin action | Would add 60+ tools, consume context budget on every unrelated chat, hit the 128-tool limit and miss disabled plugins   |
| Allow agents to edit `mannie.sqlite` directly with SQL/files   | Breaks T-18 protection, bypasses Rust validation, risks database corruption and cannot write to the OS credential store |
| Extend `DecideApproval` with a `Secret` map                    | `DecideApproval` crosses the Workers link as JSON and implements `Serialize`, which `Secret` forbids                    |
| Auto-allow `Access::AppConfig` in conversation full access     | Lets a prompt injection in one full-access chat make persistent global changes such as installing MCP servers or keys   |

## Validation

V17: unit, integration, runtime, plugin conformance and UI tests verify `Access::AppConfig` policy (always asks even under full access, zero grants/rules, worker `no_app_config` refusal), `mannie_inspect` accuracy across paths/schema/plugins/core domains, `mannie_read_logs` path confinement and filtering, `mannie_configure` prepare/re-prepare digest enforcement and crash recovery, enabling an off plugin and configuring it in the next step of the same reply, planted-secret audits across both approval-card and scrubbed-chat paths, prompt-injection corpus blocking, child/Plan/worker isolation, all 10 plugins' `ManagementProvider` implementations (including SSH add/scan/trust/test, MCP dynamic secrets, Proxmox pin/allowlist), Workers link compatibility, and Vitest keyboard/accessibility/pseudo-locale checks on `ToolApproval.svelte`.

Later changes: on 2026-10-22 the owner corrected decision 2. The access always carries `background`, because the generated TypeScript bindings cannot express a field that is written only when true, and the digest leaves the field out while it is false.

## Context

- The owner wants agents to run long-running commands, such as `journalctl -f`, file watchers and test runs, keep working with other tools, and read the commands' output later ([decision D40](../roadmap/milestones.md#5-decisions)).
- The design rules this out today:
  - `run_command` holds the conversation's tool calls until the command ends, with a timeout of 60 seconds by default and 600 at most (ADR-0014 d7), and when the command ends, everything it started ends too (d8). ADR-0014's consequences say that a command cannot start a server or an application that keeps running after it, and the [system tools](../features/system-tools/README.md) leave background processes that outlive their command to a feature of its own.
  - A tool's execution returns once ([ADR-0024](0024-run-child-agent-tasks-in-the-parent-run.md)), and the journal record of an operation is its tool call's part, which is final once the call finishes (ADR-0013 d1).
  - A run starts from the owner's message or retry, from a parent's task, or from a task that another machine assigns. Nothing tells an idle agent that something it started has ended.
  - A plugin's tool runs a remote command only until its call ends (ADR-0036 d10).
- The owner's answers of 2026-10-21 (D40): a background command outlives the reply that started it, until it ends or is stopped; when one ends on its own while its conversation has no active reply, Mannie wakes the agent; the owner's conversations, general child agents, worker tasks and SSH hosts all get them; a grant or a rule given for a command in the foreground does not cover it in the background; approving the plan of the feature accepts this ADR.
- Facts verified on 2026-10-21:
  - The supervisor's platform modules hold a command's tree in a value with its child process. On Unix only a walk of the shell's descendants, made while the shell still lives, reaches processes that left the shell's process group, and a shell killed first loses them (`crates/mannie-tools/src/supervisor`).
  - The master follows a worker task's conversation as JSON of the conversation's updates, and a worker newer than the master gets no task ([compatibility](../../plugins/workers/docs/compatibility-and-updates.md)).
  - The SSH plugin ends a remote command from a drop guard that sends TERM, then KILL, and closes the channel, without waiting for the end.

## Decision

1. Three registry tools join `run_command`, which stays as it is. `start_command` starts a command in the shell of `run_command`, in the conversation's workspace or a working directory, and returns at once with the command's number. `read_command_output` returns a command's state and the lines after what the model read; it can wait up to 600 seconds for the command's end or for a line that matches a pattern, and it can read from a given line. `stop_command` ends a command and returns how it ended. Numbers count from 1 in each conversation and are never reused. The conversation agent and the general child agent get the three tools, and the explore agent gets none.
2. `start_command` is an operation. Its access is the command's access with `background`, false in the foreground and for every access that existed. The digest of an operation leaves `background` out while it is false, so a command in the foreground keeps its digest. The policy decides it as it decides `run_command`, with one difference: a grant or a rule covers a command in the background only when it was given or saved from the approval of a command in the background, and such a grant or rule covers the command in both modes. Full access allows it, and a worker's ceiling decides it as it decides `run_command`. The approval says that the command runs in the background until it ends or is stopped.
3. `stop_command` is an operation without accesses, which the policy allows, so its call is journaled like any other side effect. `read_command_output` reads, creates no operation, and is offered only with `start_command`. Both act only on the commands of their own conversation, as `read_tool_output` reads only its own outputs.
4. A background command has no timeout. It ends when it exits; when the agent stops it with `stop_command`; when the owner stops it; when its conversation is deleted; when its task's run ends, for a child agent or a worker task; when its plugin goes off or Mannie closes the session it runs in; and when Mannie or the worker quits. Stopping a reply ends a wait of `read_command_output` and leaves the commands running. When a local command ends, the supervisor ends everything it started, as ADR-0014 d8 says for every command, and a background command's shell is never killed before its tree.
5. The runtime of each machine creates one registry of background commands, and the tools reach it through a port of their call's surroundings, as a move into a project does. The supervisor keeps a background command's tree after the call that started it, and the registry holds the tree, a log of the output, the state and the model's read position. The log reads both streams into one list of lines in the order they arrive, keeps the first 256 KiB and the last 768 KiB of them with their numbers, and marks what it left out. A conversation runs at most 8 background commands at once, and a machine 32.
6. A command's record outlives its call's part. A table of the runtime's module of the store keeps the command, its folder or host, its process, its state, how it ended and who ended it, its exit code, its times, the model's read position, whether the model was told of its end, and the archive of its output. The record, with the process, is stored with full durability before the call that started the command completes, and a record that cannot be stored ends the command's tree before the call fails. Beside its run, the registry writes a conversation's command records, the events that report a command's start and end, never its lines, and the archive of a command's log under its start call's part, where `read_tool_output`, the owner and the conversation export find it. The conversation's snapshot lists its commands, and its export record lists them with their ends.
7. Output reaches the model only as results of `read_command_output`. A note of Mannie's own tells the model about commands that ended or still run: their numbers, their texts, how they ended and how many of their lines are unread, never their output. During a reply, the note comes before the next model call after a step's tool calls, and a reply that would end with ends untold continues once with the note, as a reply with unread reports does (ADR-0024 d8). A reply that the owner's message starts begins with the note, stored with the message for the model only, when it has something to tell.
8. When a command of a top-level conversation on the master ends on its own while the conversation has no active run, the runtime starts a reply of the conversation agent with the conversation's provider profile. Its request is a part of a new kind, `command_note`, which the owner sees and the model reads as Mannie's note, and the transaction that stores it marks the ends as told. Mannie checks for a wake-up when it records an end and whenever a conversation becomes free. Ends within 2 seconds of each other share one reply. A conversation wakes at most 6 times an hour, does not wake after the owner stopped a reply until the owner's next message, and does not wake when the setting of the Tools section that is on by default is off. An end by the agent, the owner, a deletion, quitting, a plugin or Mannie closing a session never wakes, and an end that does not wake is told in the next reply. A task conversation never wakes. In every other way a wake-up's reply is an ordinary reply.
9. A task's commands end with its task's run, before the task's ending and report are stored, for child agents and for worker tasks, whose `worker` agent gets the three tools. The owner may stop a command of a child's task conversation, as the owner may stop its reply. Nothing wakes on a worker. The master shows a worker task's commands through the task conversation's events, which the link carries already; a worker newer than the master gets no task, so an older master never meets them. In this version, stopping one of a worker's commands from the master means stopping its task.
10. At startup, before any run starts, every record that was running becomes interrupted and is told to the model in the next reply, and on Linux and FreeBSD the runtime ends what is left of each tree, as it does for uncertain commands. A plugin's command becomes interrupted with the note that the processes it started may still run on its host. A conversation's next number follows the highest number it ever had. When Mannie or a worker quits, the registry stops taking commands, ends every local tree at the same time and waits for them, then stores their ends and archives.
11. A plugin's tool may run a remote command in the background. The SDK's remote-command access gains `background`, and an execution whose authorized accesses include such an access carries a ticket for one start. A new service, `background-commands` (major 1, sensitive), takes the ticket and a trait object that the plugin hands the host, as the protocol rules allow (ADR-0034 d3): a stream of the command's lines that ends with an item that says how the command ended, and a stop that ends the command and resolves with how it ended. The core uses the ticket once, takes the command's label and text from the authorized access, and awaits the stop when the agent or the owner stops the command, when the plugin goes off and when Mannie quits, before the plugin closes its sessions. A command whose stream ends without its last item ended as let go. The question before turning a plugin off counts its running commands. The plugin SSH gets the tool `start_ssh_command` this way, and it replaces the host's password in every line before the core sees it.
12. The interface shows a conversation's background commands in a control of its toolbar and their output in a side panel with Stop. The start call's card shows its command's state, a `command_note` shows as a row of the transcript, and the tools settings get the switch of wake-ups. The window's warning before closing or quitting, a part of the [window and tray](../features/window-and-tray.md) feature that this ADR changes, counts running background commands beside active replies, which the runtime reports together.
13. The threats of [security](../architecture/security.md) gain T-52 to T-54: a command that keeps running after the owner's attention moved on, a reply that a command's end starts without the owner's message, and instructions that arrive over time in a long-lived command's output.

## Consequences

- Positive: agents follow logs, keep watchers and servers running, and run long test suites while they go on working, under the same approvals, journal and containment as `run_command`. An agent learns of a command's end without polling, and the owner sees and stops every running command.
- Negative: a command can run until the owner or the agent stops it, so a forgotten watcher or server keeps using the machine; the limits, the toolbar and the quit warning keep that bounded and visible. A grant or rule for a command in the foreground asks once more before the command runs in the background. Wake-ups spend tokens and act while the owner may be away, and under full access without asking (T-29), within their limits. The runtime gains a way to start runs and a table, the supervisor keeps trees past their calls, the SDK gains a service with a handle, and the window's warning changes for another feature.
- Risks: on Unix each running command keeps one blocking thread for its status, bounded by the limit of 32. A remote command's processes may outlive its stop, as T-42 records. A chain of wake-ups, in which each reply starts a command that ends and wakes the agent again, stops at the hourly limit (R31).

## Alternatives considered

| Option                                                     | Why not chosen                                                                                                                          |
| ---------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| A `background` argument of `run_command`                   | It changes the schema and the result of a tool that every agent has, and an agent definition could not offer one mode without the other |
| Open parts that hold the reply, as background tasks do     | A reply could never end while `journalctl -f` runs                                                                                      |
| The command's state in its start call's part               | A finished part is final, and the toolbar would miss commands of turns that the view has not loaded                                     |
| Output stored in the database as it arrives                | A busy log would write to the database many times a second; the archive at the end keeps what the log kept                              |
| Grants and rules of the foreground covering the background | An old grant for `npm run dev` would start a server that never ends without asking (D40)                                                |
| A terminal with input                                      | A terminal is a plugin of its own (D26), and these commands need no input                                                               |
| Notes in the next reply without wake-ups                   | The owner chose wake-ups (D40)                                                                                                          |
| Wake-ups in task conversations                             | A task's runs belong to its parent's run or to the master's task, and nothing there reads an end after the task                         |
| Stopping a remote command by dropping its stream           | The core could not tell how the command ended, and quitting could close the session before the command was asked to end                 |

## Validation

M11:

- V4's process tree tests gain background commands: Stop, the command's own end and the registry's shutdown leave no process alive on Windows, Linux and FreeBSD.
- Tool tests of the three tools: reads while a command runs, waits, patterns, pages, the limits and the archive at the end.
- Policy tests of grants and rules in both modes.
- Store tests of the table, its upgrade from the runtime module of 0.4.0, its cascades and its recovery.
- Runtime tests with a scripted provider: the notes, wake-ups and their limits, task ends, deletion, shutdown, and crashes at each point where the start of a command is stored.
- Plugin tests of the service with a fake tool, and the plugin SSH's tests against its test server.
- A test with a paired worker, and end-to-end tests of the toolbar, the panel, Stop and a wake-up.

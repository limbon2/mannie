## Context

- The owner wants the databases of [ADR-0056](0056-let-plugins-work-with-the-owners-sqlite-files-through-the-core.md) on every machine, as a part of Workers, and asked whether rqlite or an implementation of Mannie's own should spread them ([decision D46](../roadmap/milestones.md#5-decisions)). The owner's answers of 2026-11-01 (D46):
  - Each database has one home: this computer or a paired worker. The master's view and the master's agents reach a worker's database through the link, and the worker decides each statement under its ceiling.
  - Nothing replicates a database: neither rqlite nor a consensus of Mannie's own.
  - Databases is an optional feature of Workers ([ADR-0055](0055-let-plugins-have-optional-features.md)), so the worker service runs its worker side.
- The design rules this out today:
  - The master never runs tools on a worker's host (ADR-0015 d2). ADR-0036 superseded that decision in part for computers without Mannie, and terminals on a worker's host wait for the same change (D45).
  - The worker builds its runtime from the system tools alone, and its ceiling refuses every access that plugin tools return, with `no_remote_commands`, `no_programs_on_host`, `no_external_tools` and `no_terminals`, because a worker runs no plugins (`crates/mannie-tools/src/policy.rs`).
  - The link has six packages, and the master refuses a worker whose agreed levels lack any package that the master knows (`levels::covers_every_package` in `hub/connection.rs`). A new package would cut off every worker one minor version behind, which ADR-0016 d6 keeps working.
  - A worker's approval request offers Allow once and Deny, the worker grants nothing for longer, and it refuses any other choice (ADR-0028 d5). A conversation in full access answers a worker's request, unless the host sets `allow_full_access_from_master = false` (ADR-0029 d5).
  - The ceiling is a mechanism of the core, which the worker reaches through `mannie-host-kit` (ADR-0031 d3, ADR-0034 d12).
- Facts of this repository, verified on 2026-11-01:
  - The master connects to the worker (ADR-0016 d1), and workers never connect to each other.
  - `Hello` carries the worker's details as JSON, and `WorkerDetails.ceiling` already shows the master the host's mode and whether it accepts full access from the master (`plugins/workers/crates/mannie-link/src/host.rs`).
  - The worker's configuration file refuses unknown keys.
- Facts of third parties, verified on 2026-11-01:
  - rqlite 10.6.6, of 2026-10-28, is a Go program under MIT that replicates SQLite with Raft. Its releases carry builds for Linux and Windows, and FreeBSD has it in its ports (`databases/rqlite`, at 10.2.7). Its nodes reach each other on a port of their own, with optional TLS between nodes and an HTTP API whose users come from a JSON file of passwords. Explicit `BEGIN`, `COMMIT` and `ROLLBACK` are not supported.
  - openraft's stable line is 0.9, and 0.10 is in alpha.

## Decision

1. The master works with the databases on a worker's host through the worker. The worker runs each statement on its host, under its ceiling, and records it, and the master never opens a worker's file. This supersedes ADR-0015 d2 in part: the master's agents and the owner's view act on a worker's registered databases through the worker, which decides. The master still runs no tool on a worker's host, and no other kind of access crosses the link.
2. The host consents in its configuration: `[databases]` with `enabled = true` in `worker.toml`, false by default. Without it, the worker refuses every database request with `no_databases_on_host`, and its ceiling refuses database accesses as before. An older worker refuses a configuration file that holds the new table, which the setup guide says.
3. The owner registers a worker's database from the master with a typed absolute path and a name. The worker checks the path. The file lies inside the ceiling's allowed folders unless the host is in full access, and never inside the worker's own folders. The worker refuses a network path, a link and a file without SQLite's header. It keeps the registration in its own store through `mannie-host-kit` and returns a key and the file's identity. The master keeps a copy of each worker's list, for display while the worker is offline, and unpairing clears the worker's registrations. A path that script in the webview supplies can reach only what the host's consent and allowed folders admit (T-81).
4. The link gets the package `mannie.link.databases.v1`, with calls to register, list, forget, read a schema, browse, read and write, whose documents use the SDK's types of ADR-0056. `levels.rs` splits the packages into required and optional ones. The six packages of today stay required, and the master connects to a worker that lacks an optional package, whose databases then say that the worker needs an update. The window of ADR-0016 d6 does not change.
5. The ceiling decides database requests in the core, in `mannie-tools`, which the worker reaches through `mannie-host-kit` (ADR-0031 d3):

   | Request                                                 | Read-only | Ask                                    | Autonomous                             | Full access |
   | ------------------------------------------------------- | --------- | -------------------------------------- | -------------------------------------- | ----------- |
   | A read                                                  | Runs      | Runs                                   | Runs                                   | Runs        |
   | A write or schema change on the owner's action          | Refused   | Runs                                   | Runs                                   | Runs        |
   | A write or schema change with the owner's Allow once    | Refused   | Runs                                   | Runs                                   | Runs        |
   | A write with a grant of the master                      | Refused   | Needs the owner's decision             | Runs                                   | Runs        |
   | A write or schema change under the master's full access | Refused   | Runs when the host accepts full access | Runs when the host accepts full access | Runs        |

   A database whose file no longer lies inside the allowed folders, after the host's configuration changed, is refused with `outside_allowed_folders` until the owner registers it again. A schema change never arrives with a grant, since no grant covers one (ADR-0056 d7).

6. The master's policy narrows a decision to the host. A database access names its home, and for a worker the host's mode and whether it accepts full access from the master, as `Hello` reported them. For a read-only host, a tool's preparation refuses a write and the view offers none. For an ask host, a write asks with only Allow once and Deny, and no grant covers it. Full access on the master counts only when the host accepts it, and the master asks the owner otherwise.
7. A write request carries evidence that the core produces from the call's ticket or the owner operation, never the plugin:
   - an operation ID, good once;
   - the database's key, and the identity that the master saw;
   - the write;
   - its origin: the conversation and the call, or the owner operation;
   - its authority: the owner's action, the owner's Allow once with the digest that the owner approved, a grant of the master with its scope, or the master's full access.

   The worker computes the digest again from its own registry and the write, checks the authority against its ceiling, and answers done, needs the owner's decision with the digest, or refused with a code. A choice that its ceiling does not accept is refused, whatever the master sends (ADR-0028 d5).

8. Both machines journal. The master records the tool call (ADR-0013) or the owner operation (ADR-0056 d8). The worker records each statement in its own store by its operation ID, before it runs, so a request that a dropped link made the master send again never runs twice, and a record that a crash cut off becomes uncertain and never runs again. A write whose answer a dropped link cut off ends uncertain on the master, and the worker's record holds its outcome.
9. While a worker is offline, its databases say so, and every request fails with `worker_offline`. Nothing waits in a queue.
10. The threats of [security](../architecture/security.md) gain T-79 to T-81: a compromised master reaches the registered databases of every worker that consented; a compromised worker returns forged rows, which the model reads as untrusted content; and script in the webview registers a path on a worker.

## Consequences

- Positive: the owner works with SQLite files on every machine from one view, and the master's agents query and change them under both the master's policy and the host's ceiling. The design adds no port, no trust between workers and no second program, and workers one minor version behind keep working.
- Negative: a worker's databases are out of reach while the worker or the link is down. Results cross the link in pages, under gRPC's message limits. The ceiling gains rows for a new kind of request, the master keeps a copy of each worker's list, and both machines journal each write. The rule in AGENTS.md that the master never runs tools on a worker's host changes with this ADR, as do the security document's account of what the link carries, the domain model and the orchestration document.
- Risks: a compromised master reads every registered database of every worker that consented (T-79). The host's consent, its allowed folders and a read-only mode limit what it reaches. A worker one minor version behind shows its databases as needing an update, which the owner fixes with `mannie-worker update`. A page of results larger than the link's message limit fails until the engine cuts pages to fit, which spike S8 of M15 settles.

## Alternatives considered

| Option                                                   | Why not chosen                                                                                                                                                                                                                                               |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| rqlite on the workers                                    | A second program to ship, update and supervise on three systems, a Raft port and direct connections between workers, node certificates and a file of passwords, no explicit transactions and no FreeBSD release build; the owner wants each file where it is |
| A consensus of Mannie's own, with openraft and rusqlite  | Workers never connect to each other, so it needs a mesh with trust and ports of its own, and Mannie would own consensus code; the master's desktop is often off, so it could not be a voter                                                                  |
| The master opens a worker's file through a network share | SQLite's locking is unreliable on network file systems, and the access would pass the host's ceiling                                                                                                                                                         |
| Delegating a task whose worker agent runs `sqlite3`      | Possible today, with a model in the loop for every page, text in place of typed rows, and no view                                                                                                                                                            |
| Database tools for worker tasks only                     | The owner asked for one view of every machine's databases; these tools stay an idea ([database tools for worker tasks](../../plugins/workers/docs/database-tools-for-worker-tasks.md))                                                                       |

## Validation

M15:

- Spikes S2, S4 and S8 of M15: opening other programs' files on Linux and FreeBSD, contention with the owner's applications, and an optional package with a real worker of the previous release, with page sizes against gRPC's limits.
- Link tests over loopback: registration refuses a path outside the allowed folders, inside the worker's own folders, a network path and a file without SQLite's header; every row of the ceiling's table; a forged authority and a reused operation ID are refused; a link that drops during a write runs it once.
- Compatibility tests with the levels of the previous release: the master connects, and the worker's databases say that it needs an update.
- Policy tests of the master's narrowing for read-only and ask hosts and for a host that refuses full access from the master.
- The owner's checks with workers on Linux and FreeBSD.

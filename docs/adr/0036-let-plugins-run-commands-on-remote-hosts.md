[ADR-0041](0041-let-agents-run-commands-in-the-background.md) refines decisions 2, 5 and 10: a remote-command access may run in the background, its execution carries a ticket for the core's registry, and the host ends a background remote command through the plugin's stop.

## Context

- The owner wants agents to work on computers that do not run Mannie, such as appliances, short-lived virtual machines and hosts that the owner does not administer ([decision D35](../roadmap/milestones.md#5-decisions)). The owner registers each host by hand, with its address, port, user name and password, and points an agent at it. A worker needs Mannie on its host, so it does not serve these computers.
- The design rules this out today:
  - ADR-0015 d2: an agent's tools act only on its own machine, and the master never runs tools on a worker's host. ADR-0015 rejected workers as plain remote shells over SSH, because such a worker would neither act on its own nor know its host. That reason still holds for workers, and it does not cover a host that will never run Mannie.
  - [Tools](../architecture/tools.md) §1 says that a tool acts only on the machine where its agent runs, and ADR-0014 d8 that nothing a command starts outlives it. A process on another computer is out of the supervisor's reach.
  - ADR-0034 d6: `ToolAccess` has no variant in SDK 1, the runtime's adapter runs every plugin tool as read-only, and a plugin tool that acts on the network or takes a shell string needs an SDK change, with an ADR, that maps it onto the core's accesses and policy. A plugin tool's calls are never journaled and never ask the owner, and the end of a long result is lost, because a plugin cannot store archives.
  - ADR-0034 d8 waits for a plugin's tool executions when the plugin turns off, but it was never built, because no plugin contributed a tool.
  - The `secrets` service allows only the entries that a manifest names, and it has no `delete`. A plugin that keeps a password for each host needs entries that come and go with the hosts.
- The owner's answers of 2026-10-19 (D35): every conversation, and the `general` child agent, can use every registered host, and "@" points an agent at one; remote commands get the same approval choices as local commands; version 1 only runs commands, and file transfer and SSH keys come later; hosts whose only key is RSA are refused; the work is M8, released as v0.4.0.
- OpenSSH's server has honored some of the signals that a client sends over the SSH protocol since 7.9, never for forced commands (verified 2026-10-19). A client can ask a remote command to end, and cannot make sure that it ends.

## Decision

1. A plugin may give agents a tool that runs commands on a remote host: a computer without Mannie that the owner registered with that plugin. An agent's tools act on its own machine, and on a remote host only through a remote-command access that the master's policy authorized. The master still never runs tools on a worker's host: a machine that runs a worker is reached through the worker, and the plugin's documents tell the owner not to register such a machine as a remote host.
2. The SDK's `ToolAccess` gets its first variant, a remote command. It names the plugin's key for the host (the target), the host's name as the owner gave it (the label), the endpoint, such as `deploy@build-box.lan:22`, what identifies the host beyond its address (the identity, such as the fingerprint of its pinned key), and the command's text. The runtime's adapter maps it to the core's `Access::RemoteCommand` and adds the plugin's ID, so no plugin speaks for another. The operation's digest covers every field, so a host whose endpoint or key changed between the approval and the execution goes back to the policy (ADR-0013 d4).
3. A plugin tool declares its effect. `ReadsOwnData`, the default, keeps the behavior of SDK 1: prepare returns no access, and the call is not journaled. `SideEffects` makes each call an operation: prepare returns 1 to 16 accesses, the policy decides them, the call is stored as executing before it runs, and a call that a crash cut off becomes uncertain and never runs again (ADR-0013 d5). The adapter fails a call with `plugin_invalid`, and nothing runs, when a side-effect tool returns no access, a read-only tool returns one, or a field is empty, too long or holds control characters. The core never offers a side-effect plugin tool to the `explore` child agent, whose tools only read.
4. The policy decides a remote command apart from the commands of its own machine:
   - The workspace never allows one, and Mannie's protected folders do not apply to it.
   - Full access allows it ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)).
   - A grant for the conversation, its project or every conversation covers the same command text on the same plugin, target and endpoint. The label is for display only, so renaming a host keeps its grants, and so does trusting a new key at the same endpoint.
   - A rule of leading words is always limited to its plugin, target and endpoint. The rules for remote hosts live in a table of their own, so a rule of this machine never matches a command on a remote host, and the reverse.
   - A command with shell metacharacters or a backslash never matches a grant or a rule, and the owner can only allow it once or deny it.
   - The request names its own reason, `remote_command`.
   - On a worker, the ceiling refuses a remote command with `no_remote_commands`. No plugin runs there, and the refusal keeps the policy's decisions complete.
   - A removed host leaves its grants and rules listed and inert, since no other host gets its target, and the owner can revoke them.
5. A side-effect plugin tool acts on exactly what the owner authorized. `ToolExecution` carries the authorized accesses, the limit of the run's results and up to 4 archive IDs that the core reserved, and the tool checks the accesses against its own data before it acts. `ToolResult` may carry up to 4 archives of at most 2 MiB each under those IDs, such as the whole of a stream that did not fit in the result. The core stores them, and `read_tool_output` reads them as it reads the archives of `run_command`. A field that a plugin does not send takes its default, so the change is additive.
6. Cancelling a plugin's execution still means dropping its future (ADR-0034 d3), and a plugin ends what it started, such as a remote command, from a drop guard. A result that is ready when Stop arrives wins. A side-effect call that the owner stopped while it ran becomes uncertain, with the interruption `stopped`. A call that was executing when Mannie quit becomes uncertain on the next start, as before.
7. Turning a plugin off waits for its tool executions, as ADR-0034 d8 decides: the host removes the plugin's contributions, closes its calls and asks the runtime to drain its executions, which get 5 seconds before the runtime aborts them. An aborted side-effect call becomes uncertain, with the interruption `plugin_off`, and an aborted read-only call ends as not run. The runtime checks the plugin's generation again after an approval, so a call that waited for the owner while its plugin went off never runs.
8. The `secrets` service gains keyed families. A manifest's `[secrets]` lists them, such as `keyed = ["host"]`, and the entry `host/<key>` is stored as `<id>/host/<key>`, where a key has 1 to 64 characters of `A` to `Z`, `a` to `z`, `0` to `9` and `-`. `SecretsApi` gains `delete`.
9. A plugin opens the sockets of its connections itself, under a `[native] sockets` grant with its reason ([ADR-0035](0035-find-plugins-at-build-time-in-folders-of-their-own.md) d6). The SDK gets no network service. ADR-0034 d6's rule also covers a plugin command that acts on the network: such a command connects to a registered host only on the owner's action in the plugin's settings, to read the host's key or to test its login, as pairing a worker does, and it never runs a command there. Only the tool runs commands, and only through the policy. Prepare reads stored data and never touches the network. A compromised webview could make Mannie connect to an address of its choice through these commands, which is the residual risk that [security](../architecture/security.md) §8 already accepts for pairing.
10. A command on a remote host is outside the process supervisor (ADR-0014 d1 and d8). Stop and timeout ask the host to end it and close its channel, and the result tells the model that the processes it started may still run.
11. The threats of [security](../architecture/security.md) gain T-39 to T-43: a prompt injection that reaches remote hosts, a host impersonated to catch its password, a password exposed in Mannie or in a command's output, remote processes that outlive Stop, and a compromised master that reaches every registered host. NFR-OPS-04 also allows the remote hosts that the owner registered.

## Consequences

- Positive: agents reach computers that cannot or should not run Mannie, under the same approvals, grants, rules, full access and journal as the commands of their own machine. The SDK's first access gives later plugins, such as git hosting, databases or Jira, the route for their own accesses. Turning a plugin off now waits for its tool executions, which closes an open item of M5.
- Negative: password login hands the password to every server that the owner logs in to, and only the pinned key tells a server apart from an attacker, so the owner must check each new key's fingerprint. Processes on a remote host can outlive Stop and the timeout. A remote host's output is untrusted content for the model. The core keeps two tables of rules, and the SDK's tool surface grows by an effect, accesses, a result limit and archives. The documents of tool calls gain the field `interruption`, which the Workers plugin's link carries, so the link's fixtures gain a folder for v0.4.
- Risks: an owner registers a worker's host as a remote host and passes around that worker's ceiling, which the plugin's documents warn about. `cmd.exe` on a Windows host reads `^` and `%`, which the check for metacharacters does not refuse, so a rule for a command there may match more than its words; the plugin's documents say so. A server that asks more than one question during keyboard-interactive login is refused.

## Alternatives considered

| Option                                     | Why not chosen                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| A worker on every machine                  | Some computers cannot or should not run Mannie: appliances, short-lived virtual machines and hosts that the owner does not administer |
| Approvals inside the plugin                | Grants, rules, full access and the journal would split from the core's policy, and the owner would keep two sets                      |
| Reusing `Access::Command`                  | Its shell, working directory and protected folders are local, and the rules of this machine would match commands on remote hosts      |
| Running `ssh` through `run_command`        | The password would reach a child process, and Mannie would not check the host's key                                                   |
| A stop signal that the core hands the tool | The SDK's protocol rules already cancel by dropping the future (ADR-0034 d3), and a drop guard can end the remote command             |
| File transfer and SSH keys in version 1    | The owner deferred them (D35). Each needs accesses and storage of its own, and the plugin records them as ideas                       |

## Validation

M8:

- Policy tests for every source of a decision on a remote command: the workspace, grants of the three scopes on the same host and on another, rules limited to their host, metacharacters, full access and a worker's ceiling.
- Store tests for the rules of remote hosts and their unique key.
- Runtime tests with a fake remote tool: Allow once, with an archive that `read_tool_output` reads; a grant for the conversation that covers only its host; a rule limited to its host; full access; a side-effect tool that returns no access; Stop while the call runs; and turning the plugin off while the call waits for the owner, while it runs and after it completed.
- The SSH plugin's tests against an SSH server in the test process, and the owner's checks against OpenSSH on Linux, FreeBSD and Windows.

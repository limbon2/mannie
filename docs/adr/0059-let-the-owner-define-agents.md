## Context

- The owner wants to create and edit agents in the app, "easily created and edited by the user instead of writing custom js code", and wants the first one to work like Codex's Ultra: it does little itself and hands the work to child agents.
- [Agent definitions](../architecture/extension-points.md#32-agent-definitions) exist as an extension point, but every definition is a compile-time constant, with `&'static` names, instructions and tools (`crates/mannie-runtime/src/agents.rs`). [Child agents](../features/child-agents/README.md) named definitions written by the owner as a feature of its own.
- A conversation cannot choose an agent: `new_run` names the conversation agent, and neither `StartConversation` nor a conversation's summary holds one. A plugin's definition that answers to the owner registers, and nothing runs it. A plugin cannot change this without the same changes in the core, so the feature belongs to the core ([ADR-0030](0030-split-mannie-into-a-core-and-plugins.md), decision 1).
- Plugins select the agents that get their tools and sections by name, such as `conversation`, `general` and `explore`, and the check that keeps a tool with side effects from an agent that only reads compares a name.
- The policy decides about accesses and never reads the agent, so a definition's tool list is what limits an agent. A plugin's tools and an executor's tool bypass that list today.
- The owner chose on 2026-10-15 that children use the provider profile of the reply that started them, with no setting for it.

## Decision

1. The owner writes agent definitions in the app. A custom definition is a JSON document in the table `runtime_agents`, under its key. The runtime keeps them in memory and finds a definition in this order: the core's, those of plugins that are on, the custom ones. A run keeps the definition it started with, so an edit applies from the next reply or task.
2. A custom agent's key is `custom.<slug>`, which the core makes from its name when it is created and never changes. The name can change. `check_agents` refuses a plugin's agent whose name starts with `custom.`, so a plugin that is turned on later cannot take over a stored agent, whose tools may have been chosen to be narrow ([ADR-0034](0034-build-plugins-on-a-plugin-sdk.md), decision 6, grows).
3. A custom agent is either a conversation agent, which answers to the owner, or a child agent, which answers to the agent that gives it tasks. Its kind never changes. Each definition has a `base`, the built-in agent that plugins see it as. `AgentSelector::Agents` and `SectionContext.agent` read the base, so a plugin needs no change, and a plugin's section speaks to a custom agent as it speaks to its base.

   | Kind         | Only reads | Answers to | Base           |
   | ------------ | ---------- | ---------- | -------------- |
   | Conversation | No         | Owner      | `conversation` |
   | Conversation | Yes        | Owner      | `explore`      |
   | Child        | No         | Agent      | `general`      |
   | Child        | Yes        | Agent      | `explore`      |

4. A definition only narrows. Its tools are names from a fixed list for its kind, its `plugins` are the plugins whose tools and sections it gets, and its `children` are the child agents it may give tasks to. A conversation agent may name the system tools, the task tools, `ask_owner` and `save_plan`. A child may name only the tools of the general child, because a task's run does not otherwise exclude `move_to_project`. The core checks a definition when it is saved, and `setup_for` applies it again for every run, because the webview is untrusted ([ADR-0004](0004-keep-system-access-in-the-rust-core.md)) and other rows can change after saving. The policy, the journal and full access stay as they are: a custom agent's operations ask as anyone's do.
5. A definition with `read_only` is offered only what reads. One function in `setup_for`, shared with assigned read-only tasks, keeps the tools of the class `ReadOnly`, removes the follow-ups of background commands, limits the roster to children that are read-only themselves, and offers no executors. `follow_up_task` refuses a child outside the run's roster and any task of an executor on a read-only run, because a conversation that switched agents still holds the children of its earlier replies. `offers` reads this field in place of comparing the name `explore`, and the explore child has it.
6. A conversation holds its agent in `runtime_conversations.agent_key`, `NULL` for the built-in one. `StartConversation` and the draft of the new conversation pane's controls gain it, `set_conversation_agent` changes it for the next reply, and `new_run` uses it for every reply, retry and wake-up. A key that no definition has reads as the built-in agent. The core checks in Rust that the key names a conversation agent. Deleting a definition removes its row and then sets each of its conversations back through the conversation's hub, so every window hears of it. Compaction keeps using the built-in definition, because it needs no agent's tools or words.
7. A custom definition may name a provider profile. Choosing a conversation agent that names one also sets the conversation's profile, which the owner can still change, and a new conversation starts with it. A custom child uses its own profile, and the parent's when its own was deleted or does not use tools. The built-in children keep following the parent, as the owner decided. This reverses the decision of 2026-10-15 for custom children only (D49).
8. Any definition that answers to the owner may name `ask_owner`, which refines [ADR-0058](0058-let-agents-ask-the-owner-questions.md), decision 1. Decision 9 of that ADR stands: child agents and workers do not ask.
9. A definition may have steps, each with a title, what to do, who does it, whether several may work at the same time and whether to ask the owner first. The core renders them into the definition's instructions, and the model follows them, skipping what a request does not need. They are instructions, and the runtime does not track or enforce them. There is no workflow engine.
10. Depth stays at one: a child never gives tasks, whatever its definition says (T-22, [ADR-0024](0024-run-child-agent-tasks-in-the-parent-run.md)).
11. The default roster keeps its words. While a run's roster is exactly explore and general, `start_task` is byte for byte what it was. Otherwise the tool's description and its `agent` argument speak generally, and the agent's instructions list the roster with each description, since a tool's description is limited in length by some providers.
12. A definition that vanished ends a queued run with the new `RunFailure::AgentMissing`, and a task for it gets a new `TaskRefusal`, instead of an internal failure.
13. A conversation's background commands outlive a switch of agents. A run without `read_command_output` reads a note that does not name it, and a command's end does not wake an agent that cannot start commands: the end waits for the next reply.
14. The desktop writes the starters Orchestrator and Plan once, from constants in `texts.rs`, on its first start after the upgrade, and notes that in the settings. They are then ordinary rows that the owner can edit or delete. The same constants are templates in the editor, so a deleted starter can come back. Workers neither store nor offer custom agents.
15. Contracts grow by addition ([ADR-0002](0002-grow-through-extension-points.md)): a table, a column, a field of `StartConversation` and of a conversation's summary, which a summary without an agent leaves out so the Workers link's documents stay as they were, a change of the store, a run failure, a task refusal and the commands of [custom agents](../features/custom-agents.md#contracts).

## Consequences

- Positive: an owner shapes what an agent does with a form, and every run still goes through one loop, one policy and one journal. A plugin needs no change. A conversation that uses the built-in agent, with no custom children, sends the same requests as before.
- Negative: `AgentDefinition` holds owned text and more fields, so the worker's constant and the tests that build definitions change. The runtime has a third source of definitions to keep in memory. The steps guide a model and do not bind it. An agent that gives many tasks costs several times a single reply, and this version has no limit on tokens or cost.
- Risks:
  - A plugin's tool reaches a read-only agent by a path nobody tested. The tests walk each path: registered tools, plugins' tools, published tools, executors, follow-ups and background commands, also in full access (T-86).
  - Script in the webview edits a definition. A definition can only narrow tools and never widens the policy, and instructions give it what sending a message already gives it (T-87).
  - A release adds a built-in agent or a plugin's agent that wants a key of an owner's agent. The prefix `custom.` keeps these apart.

## Alternatives considered

| Option                                                     | Why not chosen                                                                                                                                                                  |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A plugin that adds custom agents                           | It needs every core change above and an extra extension point, and turning it off would break the conversations that use its agents. It would hold only the editor              |
| A workflow engine that runs the steps in a fixed order     | The owner chose that the model follows the steps. A simple question would still go through every step, and it needs a new durable engine beside the run's actor                 |
| Definitions in files, as Codex's TOML                      | The owner asked for a form in the app, and the store already gives upgrades and transactions. Import and export can come later                                                  |
| The base `conversation` for a read-only conversation agent | It would read sections that say it may run commands on SSH hosts or change databases                                                                                            |
| Changing every plugin's selectors to name custom agents    | A plugin cannot know the owner's agents, and each new plugin would have to repeat it                                                                                            |
| A checklist of single tools in this version                | Groups are easier to choose, and a checklist needs messages for every plugin's tools. The stored list holds tool names, so a checklist can come later without changing the data |
| Editing the built-in agents                                | Their tests and guarantees, such as explore's reads, rest on what they are. Duplicate gives the owner a copy to change                                                          |
| Keys without a prefix                                      | A plugin turned on later could take over a stored key, including one that a read-only conversation uses                                                                         |

## Validation

M17: the runtime tests of custom agents (the tool sets, the roster, the read-only paths also in full access, switches, deletions, profiles of children, background commands and the byte-identical default requests), the store's upgrade tests, the link's fixtures, the UI's tests, the end-to-end test of the editor and the picker, and the live evaluation in which the Orchestrator gives its work to children.

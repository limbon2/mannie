This revision replaces the text that D56 accepted. That text ran an installed Chrome headless and drew its screenshots in the pane; the owner rejected the result as a workaround (D58). [ADR-0065](0065-let-browser-access-follow-the-conversation.md) refines decisions 5 through 10.

## Context

- The owner wants agents to use a real browser that the owner watches and uses beside the conversation, as Codex does: the pane shows the live page, painted by the browser engine, and the agent drives that same tab. Images exist only where the agent asks to see the page. The owner can give the agent sign-in credentials for the session. Localhost and intranet sites are in scope.
- The owner limits the first release to Windows (D58). Tauri 2 on Linux has only WebKitGTK, which has no DevTools Protocol, so an agent could not drive the tab that the owner sees there.
- The app webview stays on Mannie's origin under [ADR-0004](0004-keep-system-access-in-the-rust-core.md) and is untrusted. A capability that names the main window also covers its child webviews (`apps/desktop/src-tauri/build.rs`), and Tauri injects its IPC bridge into every webview that it creates.
- Verified on 2026-11-12:
  - WebView2 gives each webview a DevTools Protocol endpoint of its own, `CallDevToolsProtocolMethod` and `GetDevToolsProtocolEventReceiver`, usable only on the thread that created it. It raises native events for navigation, new windows, permissions, downloads, external protocols, authentication, certificates, context menus and accelerator keys. [WebView2 Win32 reference](https://learn.microsoft.com/microsoft-edge/webview2/reference/win32/).
  - `webview2-com` 0.39.1 and `windows` 0.62.2 are already in `Cargo.lock` through Tauri and expose every interface this decision uses. The Evergreen runtime on the owner's workstation is 157.0.4341.46.
  - Tauri 2.12's support for several webviews in one window is behind its `unstable` feature. Tauri 3 with its CEF runtime is alpha, its notes say "Keep production apps on 2.x", and it runs without its sandbox on Windows.
  - The environment variables `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` and `WEBVIEW2_USER_DATA_FOLDER` override what the host requests. tauri-driver sets the first to open a debugging port.

## Decision

1. Browser is an optional desktop plugin, off by default, for Windows. On other systems it does not start and reports its own failure code `unsupported_platform`, which the Plugins page shows. The sensitive desktop SDK service `browser` (major 1) owns sessions and exposes typed tab, navigation, observation, agent input and control operations, plus placement, focus, stills and a status stream for the pane. The plugin registers `browser_tabs`, `browser_navigate`, `browser_observe` and `browser_interact`, plus the side panel and transcript presentation. The host supplies the current conversation and run identity, and the service checks plugin and conversation ownership at every entry. Agent browser tools are available to agents acting in a local conversation under its policy. Read-only Plan and Explore runs and workers have no browser access.
2. The engine is WebView2, hosted by the desktop core with `webview2-com` outside Tauri's webview manager: no IPC bridge, no host objects, no web messages, no custom protocols and no script that Mannie injects into pages. Each conversation session gets its own WebView2 environment with a fresh, private user data folder under `<data>/browser/`, so it has its own browser process, cookies and storage. The host checks the runtime version, and checks that the environment reports the folder that it requested. A browser tab is one WebView2 controller in a child window of the main window, with DevTools UI, autofill, password saving, external drops, status bar and web messages off. Every WebView2 call runs on the main thread and never waits there; the service posts work to it and receives results and DevTools events through bounded channels, and a full event channel ends the session.
3. The desktop process removes the `WEBVIEW2_*` variables from its environment once the main window exists, so a session never inherits a debugging port or another folder, while tauri-driver still reaches the app webview. A session whose folder holds a `DevToolsActivePort` file is refused. The service's only automation channel is each webview's own DevTools endpoint.
4. Containment follows [ADR-0014](0014-contain-process-trees.md): a kill-on-close Job Object holds the session's browser process from the moment its environment exists. The engine's renderer, GPU and utility processes leave such a job, so the host ends them through their browser process: ending a session, deleting its conversation, disabling the plugin or quitting Mannie terminates the job, waits until every process that the environment listed has exited, and only then deletes the folder. Startup removes abandoned session folders after checking that they have no live owner. A request never waits inside the engine for the owner (decision 8), so the order in which processes end when Mannie is killed cannot release one.
5. The pane shows the live page: the native child window sits above a placeholder in the side panel, and the app webview reports the placeholder's rectangle in CSS pixels. The core clamps the rectangle to the window's client area and uses its own scale factor, because the app webview is untrusted. The app webview keeps its origin, content policy and capabilities, and only WebView2 renders websites. When an app dialog is open, or a menu, popover or select overlaps the page, the native window hides and the pane shows a still of the page under the overlay. A tooltip that overlaps the page is cut out of the native window's region. The page lays out at the pane's real size. A tab that no pane shows keeps rendering while an agent uses the session.
6. Under agent control the page's window is disabled, so the owner's mouse, touch and keyboard cannot reach the page while DevTools input does. Drops stay on: WebView2 has one drop target for a page, and turning off drops from other programs also turns off the page's own drag and drop, which the owner and agents need (D59). Before the core disables it, focus returns to the app, because a page that keeps focus still receives keys. In takeover the window is enabled and the owner uses the page directly. Take over and Resume follow [ADR-0065](0065-let-browser-access-follow-the-conversation.md). The pane's "Focus page" moves keyboard focus into the page, and Tab past either end and F6 move it back to the app. A screen reader reads the real page.
7. Browser site consent is keyed by the host's conversation and the canonical HTTP or HTTPS origin, including scheme and port ([ADR-0065](0065-let-browser-access-follow-the-conversation.md), decision 2). This refines [ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md), decisions 1, 3 and 6: full access still asks for a browser origin, and its confirmation describes the exception. The first agent observation or interaction with an origin asks. The same grant allows subsequent actions including clicks, text entry and form submission. A targeted frame on another origin needs its own grant. Owner input grants the agent nothing. Cancelling a run ends its pending approvals.
8. The browser permits top-level navigation to HTTP and HTTPS origins, including local and private sites. This adds an opt-in browser case to NFR-OPS-04 in [Goals and scope](../product/goals-and-scope.md). Each webview enables request-stage interception (`Fetch.enable`) before it can navigate. A popup's new window is deferred, gets its webview and interception, and only then receives the page that the opener asked for; WebView2 holds its first request until then. Redirects and popups are checked at each destination. A paused request to an approved origin continues at once. A paused request to any other origin fails at once, and the runtime actor asks the owner through the conversation approval flow. On approval the host journals the authorized continuation and replays the navigation, giving the replayed request the original method, body and headers at the request stage. Denial, timeout, run cancellation, takeover or tab closure ends the approval without a replay. The browser checks history destinations and committed origins before the agent can access them and turns off the back-forward cache, prerendering and speculative prefetch, which would bypass interception. Native handlers allow navigation only to `http`, `https` and `about:blank`, deny permission prompts, cancel downloads, external protocol launches, HTTP authentication prompts, client certificate requests and certificate errors, and refuse printing. Site grants govern top-level navigation and agent control. Pages load resources and issue background requests under the engine's normal rules.
9. `BrowserAction` extends the SDK access types, core policy and operation journal. The SDK has an effect for observing an already loaded page under policy without starting a browser or writing a side effect to the journal. Session startup, navigation and agent input are journaled operations. The first agent operation that starts a session includes the origin it will open, so site approval precedes startup. Prepare resolves the origin, session, tab, document and control generation and the requested action without changing state. The host issues authorization evidence bound to that prepared action. The service revalidates it against the live session and checks the element or viewport immediately before input. The journal carries sanitized action metadata. After a lost response to dispatched input, the operation becomes uncertain, and the agent observes the page before issuing another gesture. The replay of a request to an unapproved origin is a separate authorized operation.
10. The owner supplies a password or code through a protected Browser pane command. The host keeps the value in memory for that session and exposes an opaque reference scoped to the specified origin. After site approval the agent can fill an eligible form field by reference. The service checks the origin of the actual field before sending the value. The value stays out of model arguments, transcripts, journal entries and logs. Observations omit editable values, redact copies of supplied values from text and withhold model screenshots of documents where a protected value was entered. The website receives the value through normal browser input. The owner can remove the value during the session, and ending the session clears all such values. HTML form sign-ins work through normal browser actions. A browser-native authentication prompt reports a specific error.
11. The WebView2 host is the second place where Mannie's Rust may use `unsafe`, beside the supervisor's platform modules: the WebView2 platform module of `mannie-desktop-core`, because WebView2's COM API is `unsafe` throughout. Each `unsafe` block there carries a `// SAFETY:` comment, as the [engineering standards](../engineering/standards.md#2-rust) require.

## Consequences

- The owner sees and uses the real page at the pane's size, with the engine's own scrolling, selection, video, accessibility and input methods, and the agent drives the same tab. Web content runs in the sandbox of WebView2's renderers without a Mannie IPC bridge.
- No browser install is needed: the Evergreen WebView2 runtime that Mannie already requires is the engine. Runtime updates can change DevTools behavior, so the real-engine tests and V13 are release gates.
- Linux has no Browser until a Chromium webview is usable there. The plugin says so on the Plugins page.
- A native window floats above the app's HTML. The pane must hide it under every overlay, and a stale rectangle would leave a page over the app; the status subscription is the lease of the native view, and the core cancels every lease when the app page loads again.
- A click or keypress can cause arbitrary website behavior. The approval shows the origin and the grant's scope. An authenticated page can use the permissions of the site's account and send data under ordinary browser rules.
- The engine's renderer, GPU and utility processes leave a job that is assigned after their browser starts, so containment rests on ending the browser process, which they follow (validation, check 4).
- A navigation that needs approval shows an error page until the owner decides, and the approved request is sent again. A site sees the request once, after approval.

## Alternatives considered

| Option                                         | Why not chosen                                                                                                               |
| ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| Headless Chrome with screenshots in the pane   | The earlier text of this ADR. The owner rejected streamed images and forwarded input as a workaround (D58).                  |
| Tauri's several webviews                       | Behind `unstable`, injects Tauri's IPC bridge, and the main window's capability would cover the page.                        |
| Tauri 3 with CEF                               | Alpha, and runs without its sandbox on Windows.                                                                              |
| Load websites into the app webview             | Exposes the shell to third-party content and changes its origin and IPC boundary.                                            |
| Chrome as a separate window docked to the pane | The owner's Chrome install becomes a dependency, and a top-level window cannot follow the pane's layout, overlays and focus. |
| WebKitGTK on Linux in the same release         | No DevTools Protocol, so the agent would need a second automation and interception design.                                   |
| Attach to the owner's regular browser profile  | Reuses active sign-ins and tabs. Gives the agent access to browsing state outside its conversation.                          |

## Validation

Six checks ran on 2026-11-12 in a scratch harness outside the repository, on Windows 11 Pro for Workstations 10.0.28000 with WebView2 runtime 157.0.4341.46, `webview2-com` 0.39.1 and `windows` 0.62.2.

| Check                                             | Result                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | Consequence                                                                                                                                               |
| ------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Rendering and capture while the pane is hidden | With the controller visible, `requestAnimationFrame` ran at 60 frames a second and `Page.captureScreenshot` followed DOM changes in under 70 ms with the container hidden, with an empty window region, and with the main window minimized or hidden as in the tray. With the controller set invisible, frames and timers stopped and the capture timed out. Turning off `CalculateNativeWinOcclusion` made no difference.                                                                                                   | The host hides the container window and never sets the controller invisible.                                                                              |
| 2. A disabled container blocks owner input        | Mouse clicks, injected touch and keys reached the page while enabled and none reached it while disabled. DevTools mouse, key and touch input and capture worked while disabled. A key reached the page when it had focus at the moment it was disabled. The harness could not complete an OLE drop even on the enabled page, so drops were not checked. A later run with real mouse input (D59) showed that turning external drops off also stops in-page HTML drag and drop: no drag-over events, against 81 with drops on. | Focus moves to the app before the container is disabled. External drops stay off, and V13 checks drops by hand.                                           |
| 3. A popup's first request is held                | `Fetch.enable` on the new webview before `put_NewWindow` succeeded. For `window.open` with an opener, with `noopener`, and for a `target=_blank` link, the first request paused in the popup, the server saw nothing while it was paused and one request after it continued, and `window.opener` was set only for the first.                                                                                                                                                                                                 | Popups use the deferral (decision 8).                                                                                                                     |
| 4. A held request and the end of the browser      | Terminating a job that held the browser process: 0 of 200 paused requests reached the server. Killing the host process with such a job: 19 of 200 reached it. With the host process in a kill-on-close job from its start, 0 of 200 for each. A job assigned after the browser starts held only the browser process; its renderer, GPU and utility processes stayed outside, and none outlived the browser.                                                                                                                  | The fallback: a request to an unapproved origin fails and is replayed after approval (decision 8), and containment ends the browser process (decision 4). |
| 5. `WEBVIEW2_*` variables                         | With `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=0`, the app webview and a session both wrote `DevToolsActivePort`. After removing the variables, a new session wrote none, and the app webview's port still accepted connections. `WEBVIEW2_USER_DATA_FOLDER` replaced the requested folder, as `UserDataFolder` reported.                                                                                                                                                                               | Decision 3, and the folder check in decision 2.                                                                                                           |
| 6. A window region clips WebView2 content         | With a hole cut in the container's region, the screen showed the parent window's color in the hole and the page outside it, also after the page repainted. Removing the region showed the page again.                                                                                                                                                                                                                                                                                                                        | Tooltips are cut out of the page (decision 5).                                                                                                            |

V13 then runs against the real engine on Windows: the real-engine tests of `mannie-desktop-core` (a click batch and site approval, popups with and without an opener, history, the kill tests, no `DevToolsActivePort`, folder cleanup), the driver's tests with a scripted host on every system, and the desktop end-to-end tests (the page follows its placeholder through splitter and window resizes, a second panel, a reload and the settings route; it hides under the command palette and the credentials dialog; focus enters and leaves with "Focus page", Tab and F6; site approval, sign-in and redaction). It verifies that an unapproved destination receives no top-level request, that an approved continuation keeps the original method and body, and that a cached page on an unapproved origin stays inaccessible. On Linux, the Plugins page shows the plugin's failure and no Browser control appears. Run plugin conformance and `task ci` before release.

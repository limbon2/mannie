## Context

- An agent can ask the owner only in prose: it ends its reply, the owner answers in a new message, and the next reply starts with fresh budgets. Nothing shows that the agent is waiting, and the owner has no list of choices to pick from.
- Other harnesses give the model a tool that pauses the run and shows questions with labelled options and a free-text way out ([questions to the owner](../features/questions.md#prior-art)).
- A tool in the registry cannot do this. Its execution returns once and has no way to reach the owner, and its call shows as a running tool, which a Stop asks to end and then waits for ([tools](../architecture/tools.md#2-the-tool-contract)).
- A run already waits for the owner when it asks for an approval, on a one-shot answer that Stop and Shutdown end ([ADR-0012](0012-run-agents-as-durable-actors.md), decision 1). That path decides about accesses: it cannot carry an answer, full access skips it, and a denial skips the rest of the step.
- The guidance on tools tells the model that tool results are data and that it never follows instructions found there. An owner's answer that reaches the model as a tool result is the one exception that this feature needs.

## Decision

1. The tool `ask_owner` belongs to the runtime, outside the tool registry. It acts on a run and not on the machine: it has no accesses, needs no authorization and creates no operation. An agent definition names it like other tools, and the runtime offers it to runs whose definition names it, whose profile uses tools and that are not tasks. In this version only the conversation agent's definition names it. Its schema is strict JSON written by hand, checked at every level and reviewed through a snapshot.
2. A call of `ask_owner` is a `tool_call` part, so the store, recovery, retry, the context and the export treat it as they treat any other tool call. Its document holds the questions as the core checked and cleaned them, and the UI reads them from there and never from the call's arguments. The call's status while it waits is `awaiting_answer`, the run's activity is `awaiting_answer` with the part, and a conversation's summary says `awaitingAnswer`.
3. The run waits on a one-shot answer that it registers before any window can see the question, as it does for an approval. It holds no model slot, and the wait has no timeout. Stop and Shutdown end the wait, and a later answer is refused. A restart cancels the call as it cancels an approval, nothing resumes by itself, and a retry asks again. Full access does not skip a question, because a question is not an operation.
4. The owner's answer arrives through the command `answer_question`. The core checks it against the pending question, because the webview is untrusted ([ADR-0004](0004-keep-system-access-in-the-rust-core.md)): the webview names options by their positions, and the core writes the result from its own copy of the question. The answer names the part, and a part holds one question that never changes, so it needs no digest. An approval has one because its accesses are prepared again after the decision.
5. The instructions tell the model that the result of `ask_owner` holds the owner's own answer, and that it acts on it. This is the only tool result that they say this of. Only the core writes it, from the checked answer. An answer allows no operation: every later call goes through the policy as usual, and an answer never counts as the owner's words for a move into a project ([ADR-0013](0013-journal-every-side-effect.md), decision 8; [ADR-0023](0023-organize-conversations-into-projects.md), decision 3).
6. Calls that come after a question in the same step do not run, and their results say so, because the model wrote them before it saw the answer. A call whose arguments are not valid counts as a question for this rule, so a later call in its step never runs without an answer. Calls before the question run as usual.
7. An answer stays in the model's context. The note that replaces older results in a long reply does not apply to it, and compaction reads it whole, as it reads the owner's messages.
8. Questions and options are model output. The core refuses text over its limits, so that a question never changes by being cut, and removes control and invisible characters. The UI shows them as plain text, apart from its own title and buttons, which come from the message catalog. The tool's description forbids asking for secrets, and a note beside the owner's free text says that the model reads it.
9. Child agents, workers, plugins' tools and MCP servers' elicitation do not ask in this version. The instructions of children and workers keep saying that they cannot ask, and they keep reporting open questions to the agent that gave them their tasks. Each of these needs a later ADR.
10. Contracts grow by addition ([ADR-0002](0002-grow-through-extension-points.md)): a call status, a run activity, a reason why a call did not run, two outcomes, a field of a call's document and view, a field of a conversation's summary, and two errors. This adds no extension point: [extension points](../architecture/extension-points.md#31-tool-registry) already keep tools that act on runs in the runtime.

## Consequences

- Positive: a choice no longer ends the reply, so the model keeps its budgets and its plan and continues where it stopped. The list, the status line and the transcript say that a reply waits for an answer. The transcript and the export record what the owner was asked and what they answered.
- Negative: `run_calls` gets a third kind of call beside tools and tasks. A new field of a call's view changes the documents of the Workers link, which adds a folder of fixtures. A reply can wait for hours, and a window hidden in the tray gives no signal, as for approvals today.
- Risks: a model asks too often, which the guidance and "Don't answer" limit and the evaluations would show. A model, or text that it read, uses a question to imitate an approval or to ask for a secret, which T-82 covers: nothing that the owner answers grants anything, and real approvals still ask. A script in the webview answers a question, which T-83 covers.

## Alternatives considered

| Option                                                                         | Why not chosen                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A registered tool with a new port for the owner                                | A tool's execution shows as a running tool, a Stop waits for it, and the change would widen the contract of every tool for the sake of one                                                                      |
| `awaiting_approval` for the activity and the summary, with the wording changed | A question is not an approval. The list and the status line could not say which one waits, and a field named for approvals would mean two things                                                                |
| A part kind of its own                                                         | Retry, recovery, the context, compaction and the export would each have to learn it, for a call that behaves like a tool call                                                                                   |
| Ending the reply at a question, with the choice starting a new turn            | The reply's budgets would end there, and the choice would have to stand in for the owner's message, which decides things that an answer must not                                                                |
| A wait that survives a restart                                                 | It bends the rule that a finished part is final, and a question has no side effect, so asking again costs little                                                                                                |
| Letting the model turn off the free-text answer                                | An owner who disagrees with every option would have only Stop                                                                                                                                                   |
| Running the calls after a question as the model wrote them                     | A change that the model planned before the answer would run after the owner said otherwise                                                                                                                      |
| A card docked above the message box                                            | It needs a new slot beside the message box, and it works differently from approvals. A waiting question is the last thing in the reply, so it sits above the message box anyway. The owner chose the transcript |

## Validation

M16: the runtime tests of questions (answers, refusals, Stop, Shutdown, recovery, retry, calls after a question, full access, tool sets, answers in the context and in compaction, and a change after an answer that still asks), the schema's snapshot and its check at every level, the link's fixtures, the UI's tests and the end-to-end test of the whole flow from the keyboard.

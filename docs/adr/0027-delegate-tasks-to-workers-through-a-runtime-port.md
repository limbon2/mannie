## Context

- The conversation agent delegates tasks to workers, which run their own runtime on their own hosts ([ADR-0015](0015-run-an-agent-runtime-on-every-machine.md)). The link carries tasks, their states, the events of task conversations, approvals and credential leases ([ADR-0016](0016-link-machines-over-pinned-mtls-grpc.md)).
- Child agents already give the runtime a task contract: the task tools, the part `task`, a number for each task of a conversation, the board on which a task publishes its state, lanes, background tasks, follow-ups and recovery ([ADR-0024](0024-run-child-agent-tasks-in-the-parent-run.md)). Its consequences expected workers to reuse the part, the contract and the lanes.
- The runtime depends on the store, the provider adapters and the tools, never on the link ([repository](../engineering/repository.md)).
- A worker keeps the conversations of its tasks in its own database, and the master shows them by subscribing over the link ([ADR-0015](0015-run-an-agent-runtime-on-every-machine.md), decision 6). Chat's conversation view and side panel, and the approvals of tools, work with conversation IDs that the runtime serves.
- ADR-0024 decision 9 lets a parent's run end only after its children ended, and its end stops them. A worker finishes its task while the master is offline ([decision D5](../roadmap/milestones.md#5-decisions)), so that rule cannot hold for worker tasks.

## Decision

1. The runtime defines a port, `Delegation`, which the master's composition root gives it in `RuntimeDeps`. The port lists the paired workers with their names, purposes, statuses, host facts and ceilings, and carries what the runtime asks of a worker: submit, look up, cancel and follow tasks, deliver and revoke credential leases, and read and decide in task conversations. `mannie-link` implements it. The runtime never depends on the link, and a worker gives its runtime no port.
2. `delegate_task` is a task tool of the runtime, outside the tool registry like the other task tools. Its arguments are the worker, a title, the instruction, `background`, and `read_only`, which narrows the worker's ceiling for the task. The runtime offers it to a run whose definition names it, whose profile uses tools and which is not a task itself, while at least one worker is paired. A master without workers offers exactly what it offered before.
3. A worker task is a task of ADR-0024: a `task` part whose task section names the worker, a number shared with the child agents of the conversation, the board, the lanes, background tasks, `follow_up_task` and `wait_for_tasks`. The master chooses the IDs of the task and of its conversation and stores them in the part before it submits the task, so a submission whose answer was lost finds the same task when it is sent again.
4. On the master, a worker task's conversation is a row with the parent, the number, the agent `worker` and the worker, without turns and without local events. The runtime serves its subscription, earlier turns, checkpoint, archived outputs, approval decisions and Stop by forwarding them through the port, and puts its own summary of the conversation in place of the worker's. The conversation view, the side panel and the approvals work as they do for a child.
5. The runtime follows the tasks of each worker through one stream of task states, which starts with the states of the worker's active tasks, and asks the worker about each task that it still follows after every connection. Each state carries the version of its task's latest stored state on the worker, and a state older than the one stored changes nothing. The runtime publishes each state on the parent's board, as a child does. While the parent's run lives, it writes the state into the task's part, as the only writer of the parent conversation. The master's task row keeps the latest state at any time.
6. Worker tasks are an exception to ADR-0024 decision 9. Stopping the parent's reply cancels its worker tasks: the cancel is stored, sent, and confirmed by the worker within 10 seconds, or the task is let go and the cancel stays queued for the worker. Quitting the master leaves worker tasks running. A part that ends while its worker task runs records that the task continues on the worker, and `wait_for_tasks` takes such a task up again and follows it to its report.
7. At startup, a worker task that was active stays active on the master, and the master compares its tasks with the worker's once the link connects. A task that the worker does not know ends as interrupted. Nothing submits a task again by itself.
8. A worker's report reaches the model only as the result of a task tool, as a child's does. The workers' names, purposes and host facts reach the conversation agent in an instruction section after the environment, shortened, cleaned of control characters and introduced as data that the workers wrote.
9. The edits in other features: the card of child agents shows a worker task with the worker's name, and the toolbar's "Child agents" button lists only child agents; chat names a worker task's conversation in the side panel, the read-only footer and the status line, and shows the activity of a run that waits for its credential lease and the failures of a worker that cannot be reached.
10. Extension points grow by addition: `RuntimeDeps` gets the port, the instruction context gets the workers, the task section and the summary of a task conversation get the worker, and the runtime's decision of an approval becomes asynchronous.

## Consequences

- Positive: the conversation agent uses one task contract for children and workers. The owner reads and answers a worker task the way they read and answer a child's. Chat and tools work unchanged on a worker's conversation, and the runtime stays free of the link.
- Negative: the runtime grows a remote kind of task and forwards reads of conversations that it does not store. A worker task's card does not change once its part ended, and the master reconciles its tasks with each worker after a restart.
- Risks: a worker that never answers keeps its task active on the master; the owner sees it in the workers list and stops it there. A compromised worker sends hostile reports and descriptions; they reach the model only as tool results and as data, and every side effect on the master still needs the policy or the owner.

## Alternatives considered

| Option                                                     | Why not chosen                                                                                                                                  |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| A copy of every task conversation in the master's database | A replication protocol for events and deletions, two copies of every transcript, and ADR-0015 decision 6 keeps task conversations on the worker |
| A part kind and a card of their own for worker tasks       | The store, the context and the recovery would handle a second kind of task call, and numbers, waits and follow-ups would be built twice         |
| `delegate_task` in the tool registry                       | A tool's execution returns once and cannot follow a task in the background, as ADR-0024 found for child agents                                  |
| ADR-0024 decision 9 for worker tasks as well               | Stop would wait for an offline worker without end, and quitting the master would cancel work that ADR-0015 lets a worker finish                 |

## Validation

M4 and V6: runtime tests of delegation through an in-process port with injected faults, crash tests of the master during a delegation, the link's tests over loopback, and the end-to-end tests of a delegated task.

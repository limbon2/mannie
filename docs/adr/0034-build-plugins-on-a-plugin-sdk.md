## Context

- The owner found that each plugin changed the core, so the plugin system behaves like a set of modules. They want plugins to be self-contained: a plugin depends on a plugin SDK, the SDK is the bridge to the core, and when a plugin needs something that the SDK lacks, the SDK changes ([decision D32](../roadmap/milestones.md#5-decisions)). A third party should be able to add a plugin without changing the core. Third-party plugins themselves stay deferred, but the design must not rule them out. The work lands in M5, before v0.3.0, so the storage and contracts of Workers and Images are settled before a release ships them.
- A survey on 2026-10-17 of the commits of Workers, mentions and Images (4a0611a, ebaef98 and 0a7fb72) found 184 items of coupling: places where the core changed for a plugin or a plugin reached into the core, and 20 core features that plugins build on. Images changed 133 files outside `plugins/`. The split that made Workers a plugin changed 200, part of which is the plugin system itself. Mentions, a core feature, changed five files of Workers that had nothing to do with mentions. The main causes:
  - Plugins see the whole core. The plugin-facing types live in `mannie-runtime` and `mannie-plugins`, and `mannie-plugins` depends on the runtime and the store. Workers calls `ExecutorServices`, which wraps the whole `Runtime`, and its store code runs raw rusqlite closures through `pub use rusqlite as sql`.
  - The surfaces are closed. `PluginContributions`, `Grants`, `ContributionError`, the UI slots, `SendMessage` and `Change::StartTurn` are fixed structs and enums. A new kind of contribution or service edits all of them, and a new field on a struct literal ripples into every crate that builds one.
  - Plugin commands are hand-written in `mannie-desktop`: a module for each plugin, its entries in `ipc.rs`, `build.rs` and `capabilities/main.json`, and accessors in `state.rs`. ADR-0003 d2 keeps Tauri in that crate, so a plugin cannot declare a Tauri command itself.
  - Host conditions are variants of each plugin's error enum (`PluginOff`, `StoreUnavailable`, `ShuttingDown`), and each plugin checks that it is on.
  - Host services that a plugin needs, such as the file dialog for Images, have no route other than code in the desktop crate.
- Constraints that hold: Tauri only in the desktop app ([ADR-0003](0003-build-the-desktop-app-on-tauri-2.md)), an untrusted webview with a grant for each command ([ADR-0004](0004-keep-system-access-in-the-rust-core.md)), SQLite only in `mannie-store` ([ADR-0009](0009-persist-state-in-sqlite.md)), provider credentials in the master's credential store ([ADR-0010](0010-keep-provider-credentials-on-the-master.md)), every side effect journaled and authorized ([ADR-0013](0013-journal-every-side-effect.md)), and the worker-host mechanisms in the core ([ADR-0031](0031-move-workers-into-the-first-plugin.md) d3).
- Facts verified on 2026-10-17 with the pinned versions (tauri 2.12.3, tauri-build 2.7.2, tauri-specta and specta 2.0.0-rc.25, specta-typescript 0.0.12, rusqlite 0.40.2), by experiment except where marked:
  - tauri-build's `Attributes::plugin` with `InlinedPlugin` registers a Tauri plugin whose commands are known at build time. Its handler can be one generic closure in the desktop app, so the plugin's crate needs no Tauri. With Tauri's mock runtime, the static ACL refused an undeclared `plugin:<id>|<command>` and every window without a grant, with `dynamic-acl` off. The real app on WebView2 and WebKitGTK is not checked yet.
  - A crate without Tauri exports its own TypeScript types and typed functions with specta-typescript's `Exporter::framework_runtime`. A file for each plugin avoids the name clashes of one flat file.
  - Tauri's ACL cannot inspect arguments, so input checks stay in Rust (read in Tauri's source).
  - rusqlite offers `Connection::authorizer` behind its `hooks` feature, which adds no crate (read in rusqlite's source). SQLite names the table and columns in a failed UNIQUE or PRIMARY KEY constraint, and the constraint's name only for a failed CHECK.

## Decision

1. The SDK has three parts, all in this repository and versioned with Mannie:
   - `mannie-plugin-sdk` in `crates/`, the Rust surface of plugins;
   - `mannie-plugin-harness` in `crates/`, a dev-dependency that hosts one plugin through the real host for its tests, with fakes for the services and builders for the core's inputs, and whose `conformance()` checks a plugin's manifest, its store module and listed statements under the authorizer, that its interface equals its handlers, that every input refuses unknown fields, its refusals while off, its start, stop and second start, the IDs of its contributions, and that none of its codes equals a host code;
   - `@mannie/plugin-sdk`, the TypeScript surface, in `apps/desktop/src/lib/sdk/`.

   The core depends on the SDK and adapts to it. The SDK depends on `mannie-types`, which performs no I/O, and on a fixed list of third-party crates: serde, serde_json, specta at its exact pin, schemars, futures-util, thiserror, uuid, tracing and tokio's `sync`, and, behind features, specta-typescript for the bindings exporter and toml for the manifest. It re-exports items of `mannie-types` one by one, so a type can move into the SDK later without a change in any plugin. No SDK item names `Runtime`, the store, rusqlite, Tauri or another host type. Public SDK structs are `#[non_exhaustive]` and have constructors.

2. A plugin's library crates depend on `mannie-plugin-sdk`, on crates of their own plugin, and on third-party crates that pass [ADR-0017](0017-license-and-dependency-policy.md). Their tests may also use `mannie-plugin-harness`. A program that the plugin ships, and a library crate that only its programs use, may also depend on `mannie-host-kit` (decision 12). The manifest names such a crate under its program, and the boundary check refuses `mannie-host-kit` in the graph of the plugin's entry crate. No plugin crate depends on another plugin, on `mannie-types` directly, or on `mannie-runtime`, `mannie-store`, `mannie-tools`, `mannie-provider`, `mannie-secrets`, `mannie-logging`, `mannie-plugins`, tauri, rusqlite, rfd or the keyring crates. The rules cover normal, build and dev dependencies on every target. [ADR-0035](0035-find-plugins-at-build-time-in-folders-of-their-own.md) says where they are checked.
3. The SDK follows protocol rules, so that a later adapter could carry the same calls across a process or WebAssembly boundary for third-party plugins:
   - arguments and results are owned values that serialize, and only handle types, such as a file handle or a stream, are exempt;
   - methods return futures and streams that own their data, and cancelling means dropping them;
   - the host never hands a plugin a callback into host code, and the plugin hands the host trait objects.

   SDK 1 moves today's extension points in their current shapes, with SDK types in place of core types, apart from three changes: a plugin tool names its agents through a selector (decision 6), a mention provider checks reads through the context in place of the tools verdict, and an image source works on file handles in place of paths. Those shapes break the protocol rules in places: the executor contract, mention providers, image sources, instruction sections and agent definitions. A test lists them as known exceptions, and reshaping them is the SDK change that comes before third-party plugins. The SDK has a major version, `1`, which each plugin's manifest names. The host refuses a plugin for another major with the code `sdk_incompatible`.

4. A plugin implements `Plugin`: its interface of commands, channels and constants, its store module, its default and its start. A start returns `Started`, which holds the plugin's contributions, its command and channel handlers, and an `Instance` that reports work in progress as items with a code and a count and that stops the plugin. Contributions and handlers exist only between start and stop, so a plugin that is off has nothing that can be called. The host answers `plugin_off` for every plugin, and plugins drop their own checks and their `PluginOff` variants. A plugin's entry crate calls `export_plugin!`, which embeds the plugin's manifest at compile time.
5. A plugin gets core services by declaring them in its manifest. The start context returns a declared service with `service::<S>()`. It refuses an undeclared one with `grant_missing`, and a start fails with `service_unavailable` when the plugin declares a service that no provider of this host offers. The context also gives the clock, Mannie's version and the host's profile, release, development or validation, which replaces the desktop's `validation` feature for plugins, such as Workers' shorter retry delay in validation builds. Each service has a name, a major version and a flag for sensitive services. The crate that provides a service lists its providers (`Runtime::service_providers()`, `mannie_store::service_providers()`, and the desktop's providers), and the composition root passes these lists to the host once. The host binds each service to the plugin: secrets to entries under `<id>/`, the executor host and credentials to the executor kind that equals the plugin's ID, and a credential lend to an active task of that kind whose profile snapshot names the profile. SDK 1 has five services: `store`, `secrets`, `credentials`, `executor-host` and `file-dialog`. The file dialog returns handles, so a path never reaches a plugin. The closed `Grants` struct goes. A new service changes the SDK and the one core module that provides it.
6. Contributions go through one registry keyed by extension point. An extension point has a name, a major version, an entry type and an ID rule:
   - `Owned`: the plugin's ID, or the ID and a dot and more (mention providers, image sources);
   - `PluginKind`: exactly the plugin's ID (task executors);
   - `Global`: unique among the core's and every plugin's entries (tools, agents, sections).

   The module that owns a point consumes it, so `executors.rs` consumes executors and `images.rs` image sources. The host takes a plugin's contributions all or none, and a run reads a snapshot of the registry once, when it starts (ADR-0030 d8). A plugin that contributes to a point that has no consumer fails to start with `contributions_refused`, and a test checks that every point of the SDK has a consumer. SDK 1 keeps the six points that exist: tools, agents, instruction sections, task executors, mention providers and image sources. A plugin tool is the SDK's `Tool`, and names the agents it is offered to through a selector (conversations, child agents, every agent, or named agents), so it no longer depends on the core's agent names. Its prepare returns accesses from the SDK's `ToolAccess`, which has no variant in SDK 1, so a plugin tool reads only its own plugin's data and asks nothing, and the runtime's adapter runs it through the core's tool loop (ADR-0013). A plugin tool or command that acts on files, processes or the network, or takes a path, a shell string or a URL, needs an SDK change, with an ADR, that maps it onto the core's accesses and policy (ADR-0004 d2, ADR-0013). Until then plugin commands take handles, never paths. A new kind of contribution changes the SDK and the one core module that consumes it, and the host, the composition root and every plugin stay as they are.

7. A plugin stores data through the `store` service, as statements that are data:
   - A plugin module lists every statement that it runs. The store prepares each listed statement when it registers the module and refuses any other text with `unknown_statement`.
   - Queries return rows of SQL values. Writes run as a batch of statements in one transaction on the store's writer, with an expected change count for each statement and a mapping from constraints to the plugin's codes: a unique or primary key by its table and columns, and a CHECK by its name. No plugin code runs on the writer thread.
   - An SQLite authorizer confines every plugin statement and migration to tables named `<prefix>_*`. It refuses transactions, savepoints, `ATTACH`, pragmas, triggers, views and `load_extension`. Plugin statements are always prepared fresh while the authorizer is installed, and never through the store's statement cache, which the core shares.
   - The one exemption is a frozen record in `mannie-store` for Workers' migration 4 (`0028_move_worker_deletions_to_the_outbox.sql`). M5 added it and no release has shipped it yet. It moves the worker deletions that a 0.2.0 database holds into the core's outbox, and its hash pins it because M5 development databases already applied it. No other plugin can be added to the record.
   - Plugin data attached to core entities stays where ADR-0031 put it, in the executor's columns, its document and the outbox, and plugins reach it only through `executor-host`. A general facility for plugin data on core entities comes with its first user.
8. A plugin declares its commands and channels in Rust, with `CommandSpec` and `ChannelSpec`: a name, an input that implements `Validate` and refuses unknown fields, an output, an error type with codes, and a size limit for the input. The host dispatches every plugin call in one place, which can be tested without a webview. It checks, in order, that the store is available and Mannie is not quitting, that the plugin is on, the size of the input, its decoding and its `Validate` checks, and only then calls the handler. A log line records the plugin, the command, the outcome code and the duration, never the input or the output. Each Mannie plugin becomes an inlined Tauri plugin, generated at build time: every command gets its own permission `<id>:allow-<command>`, the main window alone gets the plugin's grant, and the desktop app forwards every call to the host's dispatch with no code for any plugin. The host ends a plugin's channels with `plugin_off` when the plugin stops and with `shutdown` when Mannie quits. Turning a plugin off removes its contributions, refuses new calls, ends its channels, waits up to 5 seconds for its handlers and tool executions, aborts the rest, and only then calls `stop` and reports the plugin as off. The journal record of an aborted tool execution becomes uncertain at once, as after a crash ([ADR-0013](0013-journal-every-side-effect.md) d5), the run reads that the plugin was turned off, and the operation never runs again.
9. The bindings program writes the TypeScript bindings of each plugin into the plugin's folder, together with its constants, such as tool names and limits. A generated transport carries the calls, and the envelope types are written once for the core. Plugin code never calls `invoke` and never names the route, so a later build can route a plugin through a bridge command without a change in the plugin. A command's error crosses IPC as `CommandError<PluginFailure<E>>`, where `PluginFailure` is either a host refusal with its code (`plugin_off`, `store_unavailable`, `shutting_down`, `unknown_command`, `invalid_input`, `input_too_large`, `host_service_failed`) or the plugin's own error. A plugin's refusal inside a core flow, such as a task executor's, is a `PluginRefusal` with the plugin, a code and its arguments.
10. A plugin's ID namespaces its folder, its tables, its settings section, its message keys, its commands (`plugin:<id>|`) and its secrets (`<id>/`). The SDK reserves the names of Tauri's own plugins (a Tauri plugin with a taken name replaces the earlier one without an error), the core's table and message prefixes, and `mannie`, `plugin`, `plugins`, `sdk` and `host`. No prefix of a plugin may begin another plugin's prefix or a core prefix, and no core prefix may begin a plugin's, so an authorizer for `log_` never admits the tables of `log-viewer`, and the core's `chat_` keys never cover a plugin's. Workers' entry `link/master-key` from 0.2.0 stays the one legacy secret name, frozen in the core's credential provider, because paired workers pin the key that it holds.
11. The TypeScript SDK gives a plugin's UI everything it may use: `definePlugin`, whose `register(context)` gets slots that carry the plugin's ID, `whileOn` and a cleanup return (ADR-0030 d11); the slot catalog with every entry type; the IPC helpers; messages for host refusals; formatting through `Intl`; navigation to settings, the Plugins page and side panels; re-exports of the installed shadcn-svelte components that plugins use, which stay unedited ([ADR-0006](0006-use-shadcn-svelte-through-its-cli.md)); icons; and test helpers. The slot catalog is one record, so a new slot is written once, in the SDK, plus the component that consumes it. A plugin's UI imports the SDK, its own files and its own generated files, and nothing else.
12. The worker-host mechanisms stay in the core, as ADR-0031 d3 decides: assigned tasks, leases, the ceiling, credential arrival and scoped redaction. A program that a plugin ships, such as the worker, is a composition root of its own. It and the library crates that only it uses reach the core through `mannie-host-kit`, a new core crate that re-exports by name what such a program needs from the runtime, the tools, the store, logging and the provider. For a program, the host kit is the way into the core, as the SDK is for a plugin's library crates. The link's worker side moves into a new crate of the Workers plugin, `mannie-link-worker`, so `mannie-link` depends only on the SDK. `hostname()` and `programs_on_path()` move from `mannie-tools` into the worker. The names of the link's crates, services and packages stay (ADR-0031 d1), and so does its wire format, which the v0.2 fixtures guard.
13. Internal plugins keep the core's rights (ADR-0030 d13). The dependency rules, the authorizer, scoped services and the ACL catch mistakes and make review concrete, and they do not sandbox a plugin. A plugin's manifest grants it its services, the sensitive `secrets` and `credentials` included, and no file of the core approves the grant. The review of the manifest in the plugin's change is the gate. `task plugins:grants` prints, for every plugin, its services, secret entries, commands, channels, programs, the crates that only it may use and its allowed native exceptions ([ADR-0035](0035-find-plugins-at-build-time-in-folders-of-their-own.md) d6), and the Plugins page shows the same for each plugin. The host grants nothing beyond the manifest.
14. When a plugin needs something that the SDK lacks, the SDK changes, with an ADR for a new or changed extension point or service (extension-points rule 5). An additive change keeps the major version. The SDK grows when a plugin needs it, as ADR-0002 d8 says: services such as settings, HTTP or tool accesses to files, processes and remote services come with the first plugin that needs them.
15. These IPC shapes change once in v0.3.0, without a deprecation period, because the bundled webview and the core ship as one artifact: the 0.2.0 commands of Workers, which move under `plugin:workers|`; the host variants that leave the plugins' error enums; `PluginWork`, which becomes a list of work items; and `WorkerListUpdate::Ended`, which the host's channel end replaces. Every other IPC type keeps the full rule of ADR-0002 d4, and so do the types that the link carries as JSON documents, which the v0.2 fixtures pin, and the documents that the store keeps.
16. `SendMessage` and `StartConversation` get constructors and become `#[non_exhaustive]`, and the harness offers builders for them, which ends the ripple of new fields into plugin code and plugin tests.

## Consequences

- Positive: a plugin's library crates see one reviewed surface, and a change inside the runtime or the store no longer reaches them. A plugin's programs see the host kit's re-exports, so a change there can still reach a program such as the worker. Adding a plugin needs no code in the desktop app, the runtime or the store. A new kind of contribution or service changes the SDK and one core module. Host refusals, channel ends and the order of turning off are written once, for every plugin. Plugin storage is confined to its tables by the store itself. A later third-party adapter keeps plugin source, the manifests and the core's consumers as they are.
- Negative: the migration has eight steps before v0.3.0, and its first step alone is about the size of the runtime part of 4a0611a. The store code of Workers is rewritten as listed statements and batches, and the desktop's plugin commands, the runtime's contribution types and the host are rebuilt. Plugins lose raw SQL and transactions with logic. The SDK is one more surface to keep, with protocol rules and stated exceptions. Each integration that ADR-0030 names, such as git, a terminal or Jira, needs an SDK change for its accesses before it can be built. A plugin UI cannot add an npm package on its own; the SDK adds and re-exports it.
- The threats in [security](../architecture/security.md) change: T-30 (grants come from manifests, entries under `<id>/` and the frozen legacy name, lends bound to tasks of the plugin's kind), T-31 (the order of turning off in decision 8), and new threats for plugin statements that leave their prefix (mitigated by the authorizer and fresh prepares), IDs that collide with a Tauri plugin or a prefix (mitigated by reserved IDs and the nesting rule), and one plugin's UI calling another plugin's commands from the shared JavaScript realm (T-35, mitigated by lint, a Vite check and review until plugin UI moves into frames).
- Risks: SQLite's authorizer callbacks for DDL, `INSERT ... SELECT` and re-preparation after a schema change must behave as described, which a spike checks on the 0.2.0 fixture before the authorizer lands. Inlined plugin dispatch was checked only with Tauri's mock runtime, and a spike checks it in the real app on WebView2 and WebKitGTK, in release and validation builds, before plugin commands move. specta is a release candidate in the SDK's public surface, so a specta upgrade is an SDK major.
- Refinement in step 0 ([M5 validation results](../roadmap/m5-validation.md#11-plugin-sdk-spikes-step-0)): the spikes on Windows made these decisions concrete. Decision 7's authorizer also allows the statements that SQLite nests in a plugin's DDL (writes of `sqlite_master`, the automatic indexes of the plugin's tables, the `REINDEX` of a new index and the `quick_check` that `ADD COLUMN` runs) and reads of no column of the plugin's tables, and it refuses `VACUUM`, virtual and table-valued tables, temporary objects and `AUTOINCREMENT`. Because it never sees `ALTER TABLE ... RENAME TO` or a `REFERENCES` clause, the store compares the schema outside the prefix after each plugin migration, inside its transaction, and refuses any change there and any foreign key to a table outside the prefix. A batch maps a unique or primary key by its table and columns, a unique index on an expression by its name, a NOT NULL or STRICT type error by its table and column, a CHECK by its name, and a failed foreign key, which SQLite reports with no detail, to one code. The exemption's hash is taken over the migration's text with LF line endings. In decision 8, each plugin's generated capability grants the main webview by its label under `webviews`, because a grant for a window also covers its child webviews; the host answers every call that turning off aborted with `plugin_off`, because Tauri never answers a call whose resolver is dropped; a body that is not JSON and a panicking handler get host refusals; and a decode failure logs only its category, because serde's messages quote the input. Decision 9 adds the host code `not_allowed`, which the transport reports when Tauri's ACL refuses a call, and the exporter needs specta-serde beside specta-typescript, writes the text of `PluginFailure<E>` itself and refuses a plugin code that equals a host code. The bindings exporter, the transport and the UI's switch to the generated bindings land in step 2. Plugins import icons through `@mannie/plugin-sdk/icons/<name>`. Inlined plugin dispatch passed on WebView2 in release and validation builds, and WebKitGTK stays open.

## Alternatives considered

| Option                                                                            | Why not chosen                                                                                                                                                                                                                                                                                                                                                                           |
| --------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An SDK that re-exports a selection of the core crates                             | Plugins would still compile against core types, so a change in the runtime or the store would still reach them                                                                                                                                                                                                                                                                           |
| A generic bridge command, `plugin_invoke`, for every plugin                       | One grant would cover every command of every plugin. Tauri's ACL cannot inspect its arguments, so a scope that limits the plugin and the command is enforced only by the command's own Rust code, where an empty allow list matches everything and the unscoped generated grant passes. A later build can use a bridge for plugins loaded at run time, behind the transport (decision 9) |
| tauri-specta wrappers generated inside `mannie-desktop` for each plugin           | The desktop crate would hold code for each plugin, generated or not, and plugin types would have to be visible to it                                                                                                                                                                                                                                                                     |
| Moving the worker-host mechanisms into the Workers plugin                         | The runtime's authorization path enforces the ceiling and a host's choices, which a plugin cannot enforce from outside, and moving them before v0.3.0 reworks assigned tasks, leases, the ceiling and approvals in the runtime, which is the largest regression risk                                                                                                                     |
| Generic attachments, plugin part kinds and the split of the executor contract now | No plugin needs them yet (ADR-0002 d8). The constructors of decision 16 stop the ripple that they would have solved                                                                                                                                                                                                                                                                      |
| Plugins loaded at run time, as WebAssembly or as processes                        | Third-party plugins are deferred (D32). The protocol rules keep this open                                                                                                                                                                                                                                                                                                                |

## Validation

M5:

## Context

- The owner wants Mannie to use MCP (Model Context Protocol) servers through a plugin ([decision D42](../roadmap/milestones.md#5-decisions)): the tools of local servers that Mannie starts as programs and of remote servers over HTTP, with secret headers and OAuth sign-in, the servers' resources through "@" mentions and a tool, and the images that their tools return. A secret that the owner enters for a local server may go into that server's environment. Every call asks, and a grant covers one tool on one server with any arguments.
- Facts about MCP, verified on 2026-10-24:
  - The current revision, 2026-07-28, is stateless: every request carries its protocol version and the client's capabilities, and `server/discover` replaces the `initialize` handshake. Most servers still speak 2025-11-25 or older, so a client that serves both probes on stdio and inspects the body of a 400 response on HTTP. A spike connected rmcp 3.7.0 to the official everything server of both eras over stdio (M12 validation results).
  - A server's tool list can change while it runs, and the server says so with `notifications/tools/list_changed`. Tool names should match `[A-Za-z0-9_.-]{1,128}`, input schemas may use any JSON Schema 2020-12 keyword, and the servers' annotations, such as `readOnlyHint`, are untrusted unless the server is trusted.
  - A local server reads its credentials from its environment, as the GitHub server reads `GITHUB_PERSONAL_ACCESS_TOKEN`. A remote server takes a bearer token or OAuth.
- The design rules this out today:
  - A plugin's contributions are fixed when it starts, and the core takes them all or none (ADR-0034 d6). A run keeps the snapshot it started with (ADR-0030 d8).
  - A plugin tool's name is lower-case snake case of at most 64 characters, unique among every tool. OpenAI's profiles send `strict: true` for every tool of a request, and a server's schema is rarely strict.
  - `ToolAccess` has no access for a call of a third party's tool, and a plugin tool that acts on the network needs an SDK change with an ADR (ADR-0034 d6).
  - The service `processes` runs bounded runs of programs that the manifest names, `.exe` files only on Windows, and refuses variables whose names look like secrets (ADR-0038 d7). A `[native] processes` grant gives no containment (ADR-0038, alternatives).
  - Plugin commands take handles and never paths (ADR-0034 d6, ADR-0038 d10), and a command reaches the network only on the owner's action to test a registered host (ADR-0036 d9).
  - Secrets never reach a child process environment (NFR-SEC-05, security §7).
  - A tool kind is registered for each tool name (ADR-0039 d1), and the TypeScript SDK cannot open a link.

## Decision

1. A plugin may give agents the tools of a tool server that the owner registered with it, such as an MCP server: a program that Mannie starts on the master, or an HTTP endpoint. A tool server is untrusted. Its tools, descriptions, instructions and results are content, and each call of its tools is an operation that the master's policy decides.
2. A new extension point, `tool-sources` (major 1, ID rule `Owned`), lets a plugin publish tools while it runs:
   - A plugin contributes a `ToolSource` when it starts. The core takes the source's stream of sets once. Each set is the complete current list of the source's `PluginTool`s and replaces the one before it, under the registry's write lock, while the plugin's start is the one registered.
   - A run reads the current sets with its snapshot and keeps them (ADR-0030 d8). A stream that ends empties the source's set, and stopping the plugin drops the stream with the plugin's other contributions.
   - The core checks each published tool alone and drops one that breaks a rule, with a log line, while the rest of its set stays: its name starts with the plugin's ID and an underscore, the checks of a static plugin tool's spec apply, and a source holds at most 64 tools. The SDK exports the same checks as a pure function, so a plugin applies them before it publishes.
   - A published tool gives way to any tool of the core, a task tool, an executor's tool or a static plugin tool of the same name, so a source never makes another plugin's start fail.
   - A run offers at most as many tools as its provider takes. Published tools are left out first.
3. A plugin tool's spec says whether its schema is strict, as `strict`, true unless the plugin calls `with_loose_schema()`. The core's `Tool` trait and the provider's tool definition gain the same flag, and the adapters send `strict` only when the profile's quirk and the tool both ask for it.
4. The SDK's `ToolAccess` gains `ExternalTool`, a call of a tool server's tool, which the adapter maps onto a new `Access::ExternalTool` with the plugin's ID:
   - It names the plugin's key for the server (the target), the server's name as the owner gave it (the label), its endpoint, the tool as the server names it, or `read_resource` for a read of a resource, the tool's title, the arguments as JSON with sorted keys, and the server's hints.
   - The endpoint is structured: a program with its arguments, or a URL. It never holds credentials: the core refuses a URL with user information.
   - The workspace never allows the access, and full access does ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)).
   - A grant for the conversation, its project or every conversation covers the same plugin, target, endpoint and tool with any arguments. The access has no rules, since a rule would cover what the grant for every conversation covers.
   - The request names its own reason, `external_tool`, and the call's view cuts its arguments as it cuts a call's arguments.
   - The label, the title and the hints are shown and decide nothing. The digest covers every field, so a call whose server changed between the approval and the execution goes back to the policy (ADR-0013 d4).
   - On a worker, the ceiling refuses the access with `no_external_tools`.
   - A removed server leaves its grants listed and inert.
5. A new service, `local-servers` (major 1, sensitive), starts a program that the owner named in the plugin's settings and keeps it running with its standard streams:
   - `start` takes the program, its arguments exactly, a working folder that exists, the server's plain variables and its secret variables, and returns a `LocalServer`: `send` writes bytes to its input, `output` streams its output as bytes, `errors` streams lines of its error output, and `stop` closes its input, waits a grace time and ends its process tree.
   - The program is an absolute path, or a name that the core finds on Mannie's `PATH` with the rules of ADR-0038 d7, never inside a project or Mannie's folders. On Windows a found name may also be a `.cmd` or `.bat` file, which starts as Rust's standard library starts batch files: it quotes each argument for `cmd.exe` and refuses one that `cmd.exe` would read as code. An absolute path inside a project is allowed, and the plugin warns about it.
   - The environment is the environment of commands, the names that the owner added, and the server's own variables, which may look like secrets but neither load libraries nor replace a name of the allow list.
   - The supervisor contains the server's process tree as it contains a program's (ADR-0038 d8), with no timeout. A dropped `LocalServer` ends its tree.
   - `ServiceProvider` gains `release`, which the host calls for a plugin after its `stop` and after a refused start, so no server outlives its plugin. Quitting Mannie ends every server.
6. A plugin's settings commands may take what the owner typed to register a tool server: a program, its arguments, a working folder and a URL. Rust checks every field. Script in a compromised webview could register a program and have it started, which gives it nothing that turning on full access and sending a message does not already give (security §8).
7. A secret that the owner gave a tool server reaches only that server: its process environment, under the name that the owner gave, or the headers of the requests to its endpoint. The plugin removes such a secret from what it shows, returns, stores and logs, as the SSH plugin removes a host's password from output (ADR-0036). A URL with a query parameter whose name looks like a secret is refused, so a secret never sits in an endpoint.
8. A plugin connects to the tool servers that the owner registered and enabled when it starts, when the owner adds, changes, enables, restarts or signs in to one, and to execute a call that the policy authorized. It lists their tools and resources, and calls a tool only through the policy; a tool's preparation never reaches a server (refines ADR-0036 d9). It opens its HTTP connections itself under `[native] sockets`, follows no redirects, and sends a credential over plain HTTP only where provider credentials may go: the rule moves from the provider into `mannie-types`, and the SDK re-exports it.
9. The TypeScript SDK gains `@mannie/plugin-sdk/links`, whose `openLink` opens a link through the core's own command after the same checks as links in model output, and the slot `toolKinds` takes an entry with `everyTool` that describes every tool of its plugin without an entry of its own (refines ADR-0039 d1).
10. The threats of [security](../architecture/security.md) gain T-55 to T-63: a prompt injection that calls a tool server's tool, a server that poisons its descriptions, instructions, results or images, a server's secret that leaks, an attack on OAuth's redirect, a local server that outlives its plugin, a compromised webview that registers a program, a server's metadata that points the client at internal addresses, the packages that `npx` or `uvx` fetch at each start, and a program inside a project that agents change. NFR-OPS-04 also allows the tool servers that the owner registered and the authorization servers that their metadata names.

## Consequences

- Positive: agents use the tools that MCP servers offer, local and remote, under the same approvals, grants, full access and journal as every other tool. The tool sources, the external-tool access and the local servers serve any later plugin that relays a third party's tools. Turning the plugin off ends its servers.
- Negative: the core gains an extension point, an access with its grants, a service with a mode of the supervisor and a release hook, and a flag on every tool definition. A tool server acts outside Mannie's path policy: a file system server that the owner allowed can write where its own rules let it, Mannie's folders included. A server shared by every conversation keeps its own state across them. The core keeps no rules for external tools, so "Allow for every conversation" is the way to allow a tool everywhere.
- Risks: servers differ in protocol era, schemas and the number of their tools, which the plugin's tests against both eras and the owner's checks against real servers find. A server can change its tools after the owner trusted them; a tool that a server adds later starts off in the plugin. A server whose package `npx` fetches at each start runs whatever that package becomes, which the plugin's documents warn about.

## Alternatives considered

| Option                                                        | Why not chosen                                                                                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| One fixed tool that calls any server's tool by name           | The model would read every tool's schema as prose and call worse, and the definitions would cost as much                        |
| Approvals inside the plugin                                   | Grants, full access and the journal would split from the core's policy, as ADR-0036 found for remote commands                   |
| Processes in the plugin under `[native] processes`            | No containment, no environment from the allow list and no program that the core resolved (ADR-0038)                             |
| Owned I/O handles in the service                              | The SDK depends only on tokio's `sync` feature and takes owned values and streams (ADR-0034 d1, d3)                             |
| Strict versions of the servers' schemas                       | Optional properties would become required and nullable, and a free-form object cannot be strict                                 |
| Rules for external tools                                      | A rule would cover what the grant for every conversation covers, since grants take any arguments                                |
| A new service that opens the browser                          | The core's link command already checks and opens links, and an authorization URL holds no secret                                |
| A naming rule for tools across plugins, checked at build time | Tool names live in code, which the boundary check does not read; a published tool gives way to a static one at run time instead |

## Validation

M12:

- Runtime tests with a fake tool source: a set replaces the one before, a tool that breaks a rule is dropped alone, a published tool gives way to a static tool, a run keeps the set that it started with, the source's tools leave with its plugin, and a run offers no more tools than its cap.
- Policy and runtime tests for the external-tool access: a grant covers the same tool with other arguments, another tool or endpoint still asks, full access, a worker's ceiling, a removed server's inert grants, and a changed server between the approval and the execution.
- Tests of the supervisor's server mode on Windows and Linux: piped input and output, a closed input that ends a server, `stop` and a dropped handle that end a grandchild, a `.cmd` file with a corpus of arguments, and a planted secret that reaches only its own server.
- The plugin MCP's tests against servers of both protocol eras over stdio and HTTP, and the owner's checks against real servers.

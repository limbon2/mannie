## Context

- The owner wants Mannie to support skills "that can be added via npx skill commands". The command is the CLI `skills` of vercel-labs (skills.sh), which this repository already uses for its own agent skill. The npm package `skill` is another program, which installs into `.codebuddy/skills`.
- A skill is a folder with a `SKILL.md`: YAML frontmatter with a `name` and a `description`, a Markdown body, and any other files, such as scripts and references. Harnesses list each skill's name and description in the model's instructions, and the model reads the rest when a task fits ([Agent Skills specification and client guide](https://agentskills.io/specification), verified on 2026-11-07).
- The CLI 1.7.6 copies a skill into `<cwd>/.agents/skills/<name>/`, and with `-g` into `~/.agents/skills/<name>/`, for every agent whose folder is `.agents/skills`, such as the agent `universal` (its `src/agents.ts` and `src/installer.ts`, read on 2026-11-07). It refuses an agent that its list does not hold, and Mannie is not in the list.
- Mannie reads no instruction files of projects. Text from a project's folder reaches the model only when a tool reads it or the owner mentions it.
- The policy allows reads inside the conversation's workspace and asks for every other read, apart from the reads of registered databases ([ADR-0056](0056-let-plugins-work-with-the-owners-sqlite-files-through-the-core.md), decision 7). The folder of this computer's skills lies outside every workspace.
- Skills written for other harnesses carry fields such as `allowed-tools`, which Claude Code reads as permission to run tools without asking. Content that a model reads never grants a permission ([ADR-0013](0013-journal-every-side-effect.md), security objective SO-4).
- Workers own their hosts and run no plugins, and the master ends a worker's stream of transcript updates when it meets one that it cannot read ([ADR-0015](0015-run-an-agent-runtime-on-every-machine.md)).

## Decision

1. Skills are a feature of the core on the master (D50). Workers neither find nor offer skills. The tool `read_skill` is registered only by the desktop app's composition root and never by `system_tools()`, so a worker never offers it and never sends its outcome over the link.
2. Mannie finds skills in two places: `~/.agents/skills`, the folder of this computer, and the `.agents/skills` folder of the conversation's project. A skill is a direct subfolder that holds a file `SKILL.md`. Mannie never writes into these places, never installs, updates or removes a skill, and never runs anything that a skill holds: a script that a skill names runs only as a command that the policy decides. The owner adds skills in a terminal with `npx skills add <source> --agent universal`, with `-g` for this computer.
3. A project's skill folder must resolve inside the canonical workspace. No skill folder may resolve into one of Mannie's own folders, to a folder that holds one of them, or to a folder that holds its place. A folder that breaks a rule shows with its reason in the settings and is not a skill.
4. Mannie reads four fields of the frontmatter: `name`, `description`, `disable-model-invocation` and `user-invocable`. The last two only narrow: `disable-model-invocation: true` keeps a skill out of agents' list, and `user-invocable: false` keeps it out of "@". No field grants anything, `allowed-tools` included. A reader in the core reads the frontmatter's top-level scalars, tolerates what real skills write, such as a colon in a plain value, and expands no aliases, so no YAML library is needed.
5. Each skill has a switch, which the table `runtime_skill_switches` keeps. A skill of this computer is on until the owner turns it off. A project's skill is off until the owner turns it on, each skill on its own, and so is a skill that appears later. Turning a project's skill on records a digest of its name, its description and `disable-model-invocation`, and when they change, the skill reads as off until the owner turns it on again. A project's switches go with the project.
6. The core section `skills`, at position 180, between the guidance on sources and the owner's instructions, lists the skills that are on and that agents may see, by name and description, in the calls that are offered `read_skill`. A project's skill hides a skill of this computer with the same name. The list holds at most 12 KiB: past that, descriptions are cut, and the skills that still do not fit are left out, which the settings show.
7. `read_skill` is a tool of the registry with the class read-only. A call is offered it when the conversation has a skill that is on. It reads a skill's `SKILL.md` or another of its files, and its preparation returns the canonical path as a read access, so the operation's lifecycle applies as it does for `read_file` ([ADR-0013](0013-journal-every-side-effect.md)). It refuses a path that leaves the skill's folder, a link that leads out of it, and a file whose name may hold secrets.
8. The policy gains a source of decisions, `skill`: a read inside the canonical folder of a skill that is on, in one of the conversation's places, runs without asking. It comes after Mannie's own folders, which still ask, and before grants, as the source of registered databases does. A change inside a skill's folder follows the usual rules. This refines the rule that reads outside the workspace ask.
9. The mention provider `skills` offers the skills that are on and the project's skills that are off, apart from those with `user-invocable: false`, with the token `@skill_<name>`, whose hyphens become underscores, so that a skill's name never stands in for the owner's words about a project. It reads through the policy of a model's read, so [ADR-0032](0032-let-features-and-plugins-add-kinds-of-mentions.md), decision 8, stands.
10. Every built-in agent may use `read_skill`. Custom agents get it through a new group of tools, Skills, which refines [ADR-0059](0059-let-the-owner-define-agents.md), decision 4. The templates Orchestrator and Plan include the group, and stored agents keep the tools they have.
11. Contracts grow by addition ([ADR-0002](0002-grow-through-extension-points.md)): a table, the commands `list_skills` and `set_skill_on`, the outcome `skill_read`, two tool failures, a source of the policy's decisions, a group of tools, and fields of the runtime's dependencies, of a call's surroundings, of the availability of tools and of the instructions' context.

## Consequences

- Positive: a skill that the owner adds with the CLI reaches the agents of the master without a restart, skills written for other harnesses work as they are, and a conversation without skills sends the same requests as before.
- Negative: the policy has one more source, and the instructions one more section, whose text changes when skills change, which costs a provider's cached prefix after position 180. A project's skills need a switch each. Worker tasks get no skills.
- Risks:
  - A repository's skill writes into the instructions. A project's skills start off, and the digest pins the text that the owner turned on (T-88).
  - A skill's link or path reads a secret or a file outside its folder without asking. Canonical containment, the refusals of the scan and of `read_skill`, and Mannie's own folders, which ask first, limit it (T-89).
  - A skill claims a permission. No field and no text grants anything, and every operation goes through the policy (T-90). In full access, injected text runs unasked, as any content's can (T-29).
  - A hostile `SKILL.md` exhausts the scan or the reader. Both are bounded (T-91).

## Alternatives considered

| Option                                                   | Why not chosen                                                                                                                              |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| A plugin                                                 | The owner chose the core (D50)                                                                                                              |
| Mannie in the CLI's list of agents                       | It needs a change and a release of the CLI, and `--agent universal` already writes where Mannie reads. It can come later                    |
| Also reading `.claude/skills` and other harnesses' trees | The CLI writes to `.agents/skills` for every agent that reads that folder, and other trees bring skills written for other tools' tool names |
| A project's skills on as soon as they arrive             | A cloned repository could then write into the instructions of its conversations (D50)                                                       |
| Honouring `allowed-tools`                                | Content never grants a permission                                                                                                           |
| `read_skill` without accesses, as `read_tool_output`     | It would read files outside the operation's lifecycle, and the transcript would not show the path                                           |
| A YAML library                                           | Real skills break YAML, only four scalar fields matter, and a library would expand the aliases of a hostile file                            |
| Installing skills from the app                           | The owner adds skills in a terminal (D50), and running `npx` would need Node.js and a way to start `npx.cmd` on Windows                     |

## Validation

M18: the tests of the reader, the scan, `read_skill` and the policy; the runtime tests of the list, the switches, the digest, the agents and the mentions, with the same requests as before when there are no skills; the end-to-end test of the settings section; the live evaluation in which a request that fits a skill makes the model read it; and a run of the CLI that confirms its folders.

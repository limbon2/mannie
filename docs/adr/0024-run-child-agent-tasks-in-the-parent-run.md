## Context

- [Child agents](../features/child-agents/README.md) let the conversation agent give tasks to child agents on the same machine: explore children that read and general children that also change files, in parallel up to a limit, in the background, with follow-ups that keep a child's context, approvals in the parent's conversation, and stopping that reaches every child ([orchestration](../architecture/orchestration.md#3-child-agents)).
- The runtime runs a step's tool calls one at a time, inside the run's actor ([agent runtime](../architecture/agent-runtime.md#3-the-loop)). The architecture anticipated lanes, in which tasks for different children run in parallel, for when child agents arrive.
- A tool in the registry prepares an operation, which the policy authorizes and the journal records, and its execution returns once with a typed outcome ([tools](../architecture/tools.md#2-the-tool-contract)). A task has no accesses of its own, runs for as long as a child works, reports progress and an approval request on the way, and in the background its result comes long after its call ended.
- [ADR-0023](0023-organize-conversations-into-projects.md) rejected a move into a project handled outside the tool registry, because a move is a side effect that the policy, the approvals and the journal must cover.
- A conversation's workspace, project and grants decide what its tools may do ([operations and approvals](../features/system-tools/operations-and-approvals.md#policy)), and a conversation's turns are owned by its requester, which is an agent for a task conversation ([domain model](../architecture/domain-model.md#3-conversations-turns-steps-and-parts)).

## Decision

1. The task tools, `start_task`, `follow_up_task` and `wait_for_tasks`, belong to the runtime, outside the tool registry. They act on runs, not on the machine: they have no accesses, need no authorization and create no operations, because every side effect of a child is an operation of the child's own run, which the policy, the approvals and the journal cover. Agent definitions name them like other tools; the runtime offers them to runs whose definition names them, whose profile uses tools and that are not tasks themselves. Their schemas are strict JSON written by hand, and their definitions are reviewed like the tools' through a snapshot.
2. A call of a task tool is a transcript part of the kind `task`. Its document holds the call's record, as for a tool call, and a task section with the task's state, the child's activity and pending approval, the report and the result that the model reads. The store and the runtime treat a `task` part as a call wherever they treat a `tool_call` part as one, and the model reads an open `task` part, such as a start in the background, with the result it was given.
3. A task runs in a task conversation: a conversation of the runtime with a parent, a number among the parent's children and an agent. The conversation list leaves it out, deleting the parent deletes it, and it belongs to no project. Its tools work under the parent's workspace, project, grants and rules, which the runtime reads from the parent, and grants that the owner gives from a child's request belong to the parent. Its turns are the parent agent's: the owner's commands refuse it, except Stop, and its messages never count as the owner's words.
4. Each start or follow-up is a task, with an ID that the parent's runtime chooses and stores in the parent's part before the task exists. The child's conversation, its turn and the task are created in one transaction, and creating a task with an existing ID returns that task.
5. A step's calls start in order. A start or a follow-up does not hold up the step; the step's other calls run one at a time, as before; and the step ends when its calls are done and its tasks that do not run in the background reported. The parent holds no model slot while it waits.
6. A machine-wide pool of slots limits the children that run at once, with a limit from the owner's settings. A child takes its slot in its own run and keeps it until it ends.
7. The parent's run is the only writer of the parent's conversation. Each child publishes its latest state to its parent's run, without waiting for it, and the parent stores it in the task's part; while a child waits for the owner, the parent's activity says so with that part. The owner's decision names the child's conversation, as every decision names its own.
8. A child is asked once to confirm that it finished before it reports. Reports reach the parent's model only as results of the task tools. A reply that wants to end while its background tasks run waits for them, and asks the model, with a note of Mannie's own, to read reports it left unread.
9. A parent's run ends only after its children ended, and its end stops them first. Stopping a child stops only that child, and the parent continues.
10. At startup, task conversations recover before the others. A task that ran becomes interrupted, and a parent's open part completes from its task. Nothing restarts a task by itself.
11. Extension points grow by addition ([ADR-0002](0002-grow-through-extension-points.md)): an agent definition says whom its agent answers to and how many tasks a reply may start; the instruction context says whether a run is offered the task tools; the transcript gets the part kind `task` and the activity `waiting_for_tasks`; and a conversation's summary names the parent of a task conversation.

## Consequences

- Positive: children run in the same runtime and loop as the conversation agent, with their operations journaled and authorized like the parent's. The parent's transcript records each task, its progress and its report, and one recovery path covers both. Workers can reuse the task part, the task contract and the lanes in M4.
- Negative: the runtime grows a second kind of call, which the store and the context must treat as calls; the parent's actor multiplexes its children's states with its own work; and a task conversation is a conversation that the owner cannot write to.
- Refinement in M4: tasks that the conversation agent gives to workers reuse this contract, but decision 9 does not hold for them: Stop cancels them without waiting for an offline worker, and quitting the master leaves them running ([ADR-0027](0027-delegate-tasks-to-workers-through-a-runtime-port.md)).
- Risks: a report carries an injection that the parent's model follows, which the policy and the owner still stop and the injection corpus tests; a parent waits forever for a child that never ends, which every child's wait for its mailbox and the stop that the parent's end sends prevent; the slot limit starves a reply's foreground tasks behind other conversations' children, which the order of the pool keeps fair.

## Alternatives considered

| Option                                                      | Why not chosen                                                                                                                   |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Task tools in the tool registry, with a capability for runs | A tool's execution returns once, cannot report a child's state or approval, and cannot stay open for a task in the background    |
| Tasks as `tool_call` parts with a task section              | The tools feature's outcome and renderer would have to know tasks, and a task's result is not an operation's outcome             |
| A child's state through a separate channel to the UI        | The parent's transcript would not record the task's progress, and the status line and the list would not know that a child waits |
| Children that keep running after their parent ends          | A retry or a message of the parent could overlap a child that still works, and nothing would stop a forgotten child              |
| Reports in a message of the user at the end of a reply      | Text that another model wrote would reach the parent's model as the owner's words                                                |

## Validation

M3: the runtime tests of tasks (reports, the confirmation, tool sets, slots, background tasks, follow-ups, approvals and grants through the parent, stopping, budgets and refusals); the crash tests of tasks; the prompt-injection corpus with a hostile report; the store's tests of task conversations, recovery and deletion; the end-to-end tests of child agents; and an evaluation of a multi-step task split across children.

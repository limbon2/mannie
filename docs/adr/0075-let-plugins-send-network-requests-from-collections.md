## Context

- The owner wants a network client plugin in `plugins/network/` that lets agents run HTTP requests from owner-configured collections like Postman's, so agents prefer the owner's configured APIs over `curl` or shell HTTP scripts when working with a covered API. The plugin must import OpenAPI v2 (Swagger 2.0) and v3 (3.0 and 3.1) specifications, support custom variables, headers, query parameters, path parameters and cookies, redact cookies and secrets as `[redacted]` for agents while letting the owner see them as-is, and leave room to add other protocols later (raw TCP, GraphQL, WebSockets, gRPC and tRPC).
- On 2026-11-21, the owner chose four rules for version 1:
  - every agent HTTP request asks by default, with grants per saved endpoint (conversation, project or always), and full access runs requests without asking;
  - agents run only saved requests defined in the owner's collections (filling path, query, header, variable and body inputs), never arbitrary URLs;
  - collection secrets and cookies live in the operating system credential store, the owner sees them as-is in the Network Client view (collections, variables, cookies and manual responses), and chat transcripts, tool-call cards, model results, logs and exports stay redacted;
  - version 1 includes a Postman-style workbench in the activity bar for managing collections, importing OpenAPI specifications and sending requests manually to inspect live responses.
- Earlier decisions that this design touches:
  - [ADR-0034](0034-build-plugins-on-a-plugin-sdk.md), decision 6: `ToolAccess` has no variant for network requests from collections, and any plugin tool or command that acts on the network needs an SDK change with an ADR that maps it onto the core's accesses and policy.
  - [ADR-0013](0013-journal-every-side-effect.md): every side effect is a journaled, authorized operation; `Access`, `GrantScope`, `ApprovalReason` and `Refusal` are exhaustive across the core.
  - [ADR-0004](0004-keep-system-access-in-the-rust-core.md) and [security](../architecture/security.md) (SO-2 and section 7): the webview is untrusted, and no plugin has previously returned stored secret values to the webview over IPC.
  - [ADR-0036](0036-let-plugins-run-commands-on-remote-hosts.md), decision 9, and [ADR-0043](0043-let-plugins-offer-the-tools-of-tool-servers.md), decision 8: outbound network connections from plugin commands on the owner's action require an ADR.
  - NFR-OPS-04 in [goals and scope](../product/goals-and-scope.md) enumerates the network endpoints Mannie may reach.
  - [ADR-0017](0017-license-and-dependency-policy.md) governs adding a YAML parser for OpenAPI YAML specifications.
- Facts verified on 2026-11-21:
  - `saphyr-parser` 0.4.0 ([crates.io](https://crates.io/crates/saphyr-parser/0.4.0), `MIT OR Apache-2.0`, Rust 1.85 or newer) is a pure-Rust YAML 1.2 event parser that depends only on `arraydeque` 0.5.1 (`MIT OR Apache-2.0`) and `thiserror` 2.0.20 (already in `Cargo.lock`). Driving its event stream directly into `serde_json::Value` enforces hard bounds on input size, nesting depth, total nodes and alias expansions before constructing any document.
  - `reqwest` 0.13.5 (`MIT OR Apache-2.0`, built with `http2`, `rustls-no-provider` over `ring`, and `system-proxy`) is already in the workspace and used by `plugins/mcp/`.

## Decision

1. Add an optional internal plugin `network` in `plugins/network/` (order 90, off by default on new installations per D28). Its manifest declares `store = 1`, `secrets = 1` with keyed families `collection`, `environment`, `cookie`, `request` and `global`, `file-dialog = 1`, the exclusive crate `saphyr-parser`, and `[native] sockets`. Version 1 supports the `http` protocol; stored schemas, IPC contracts, UI indicators and core accesses carry an explicit `protocol` tag so later protocols (`graphql`, `websocket`, `grpc`, `trpc`, `tcp`) arrive by addition ([ADR-0002](0002-grow-through-extension-points.md)).
2. Add `ToolAccess::NetworkRequest(NetworkRequestAccess)` in `mannie-plugin-sdk` and `Access::NetworkRequest` in `mannie-types`:
   - The core adapter supplies `plugin`. The plugin supplies `collection_id` (immutable key), `collection_label` (display only), `request_id` (immutable key), `request_label` (display only), `protocol` (lower-case ASCII identifier, 1 to 32 characters, `"http"` in version 1), `method` (upper-case ASCII operation tag, 1 to 32 characters, such as `"GET"` or `"POST"`), `origin` (canonical `http` or `https` origin without user information, path, query or fragment), `target_url` (resolved target URL without user information and with every secret variable or parameter value replaced by `[redacted]`), and `summary` (sanitized JSON of non-secret request parameters, headers and body metadata, with all secret variables, secret headers, secret query parameters and cookies replaced by `[redacted]`).
   - The adapter checks field lengths, control characters, protocol and method syntax, canonical origin and absence of URL user information before authorization; a broken access fails the call with `plugin_invalid` and nothing runs.
   - `Access::NetworkRequest::changes()` is `true`. The operation digest covers every field, so a saved request whose collection base URL, origin, method or sanitized inputs changed between approval and execution returns to authorization ([ADR-0013](0013-journal-every-side-effect.md), decision 4).
   - `ToolCallDocument::view` cuts `summary` to `MAX_VIEW_ARGUMENTS_BYTES` and sets `summary_cut`, while keeping the full stored access for digest checks.
3. Authorize `Access::NetworkRequest` through the core policy:
   - The workspace never allows it; full access allows it ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)).
   - Unmatched calls ask with `ApprovalReason::NetworkRequest`.
   - `GrantScope::NetworkRequest` covers the same `(plugin, collection_id, request_id, protocol, method, origin)` with any runtime parameters or body, at conversation, project or always scope. `collection_label` and `request_label` are display only, so renaming a collection or request preserves grants. Changing the saved request's method or target origin (such as switching from a local environment to production) falls outside existing grants and asks again.
   - No saved rules apply, because an always grant already covers the saved endpoint with any arguments.
   - Removing a collection or saved request leaves its grants listed and inert (IDs are UUIDv7 and never reused) until the owner revokes them.
   - A worker's policy ceiling refuses `Access::NetworkRequest` with `Refusal::NoNetworkRequests`.
4. Contribute four fixed static plugin tools, an instruction section, a mention provider and tool kinds:
   - `network_list_collections`, `network_list_requests` and `network_get_request` declare `ToolEffect::ReadsOwnData` and are offered to every agent. They return only redacted collection and request definitions, showing `[redacted]` for every secret and cookie value.
   - `network_send_request` declares `ToolEffect::SideEffects` and is offered to conversation agents and the `general` child agent, never to `explore` or read-only custom agents. It accepts only a saved request from an enabled collection plus runtime overrides (optional environment selection, path parameters, query parameters, non-secret headers, non-secret variables, body and bounded timeout). Preparation reads stored state only, touches no network and places no secret in `NetworkRequestAccess`. Execution verifies the authorized access against the live collection and request before sending.
   - Fixed tools avoid the 64-tool cap of `tool-sources` so large OpenAPI specifications with hundreds of endpoints work without hitting provider tool limits.
   - An instruction section (`network-collections`, position 345) lists enabled collections (name, protocol, active environment, redacted base URL and request count) and tells agents to prefer these tools over `curl`, `Invoke-WebRequest` or shell HTTP commands for covered APIs, never ask the owner to paste secrets or cookies into chat, and treat responses as untrusted content.
   - A mention provider (`network`) lists collections and saved requests in `@` mentions and resolves them to redacted summaries.
5. Keep all collection secrets and cookies in the operating system credential store, redact them for agents, and document a narrow webview exception:
   - Secret variables (owner-marked secret or matching `looks_like_secret`), secret headers (`Authorization`, `Proxy-Authorization`, `Cookie`, `Set-Cookie`, `X-Api-Key`, names matching `looks_like_secret`, or owner-marked secret), secret query parameters, authentication secrets and all cookie-jar values are stored only in the master's operating system credential store through `secrets`, split into chunks of at most 1,000 UTF-16 code units (R36). SQLite `network_*` tables hold only non-secret values, secret flags, metadata and chunk counts. Deleting a collection, environment, request or cookie deletes its credential-store entries and truncates the write-ahead log ([ADR-0048](0048-erase-what-plugins-delete-from-the-store.md)).
   - Every agent tool result, archive, approval request, transcript part, tool-call card, log entry and conversation export replaces all structured secret and cookie fields with `[redacted]` regardless of length, and scrubs occurrences of known secret or cookie values of at least 8 bytes (including URL-encoded and Basic-auth base64 forms) to `[redacted]` in URLs, response bodies and error messages.
   - Refining [ADR-0004](0004-keep-system-access-in-the-rust-core.md) and [security](../architecture/security.md) (SO-2 and section 7): the plugin's Network Client IPC commands return this plugin's own collection secrets, cookies and manual-run responses as-is to the main webview so the owner can view and edit them directly in the Network Client workbench. This exception covers only the `network` plugin's own collection secrets and cookies; provider keys, ChatGPT tokens, SSH passwords, MCP secrets, Browser credentials and Workers keys stay unreachable from the webview. The frontend never persists revealed secrets in browser storage.
6. Run HTTP requests with `reqwest` under `[native] sockets` and enforce transport safety:
   - Requests carrying any secret or cookie must satisfy `credential_transport_allowed` (`https`, or plain `http` only to `localhost`, loopback, private LAN IPs, link-local or `100.64.0.0/10`). URLs with embedded user information (`user:pass@host`) are refused.
   - Requests follow no automatic redirects, preventing secret headers or cookies from forwarding to another origin; responses report the 3xx status and `Location` header.
   - Response downloads are capped (10 MiB in the owner workbench; agent outputs bounded to `result_limit` with up to 2 MiB of redacted response archived via `ToolArchive` for `read_tool_output`). Timeouts default to 30 seconds and are bounded to 1 to 300 seconds.
   - When the owner clicks Send in the Network Client workbench, the plugin runs the request directly on the owner's action without an agent approval prompt and without writing a chat transcript part, refining [ADR-0036](0036-let-plugins-run-commands-on-remote-hosts.md), decision 9, and [ADR-0043](0043-let-plugins-offer-the-tools-of-tool-servers.md), decision 8.
   - NFR-OPS-04 in [goals and scope](../product/goals-and-scope.md) allows outbound connections to endpoints of collections configured by the owner while the `network` plugin is on.
7. Import OpenAPI v2 (Swagger 2.0) and v3 (3.0.x and 3.1.x) documents in JSON and YAML through `file-dialog` or pasted text, with a preview before saving:
   - YAML parsing uses `saphyr-parser` 0.4.0, listed under `[crates] exclusive` in `plugins/network/plugin.toml`, enforcing hard limits of 10 MiB input, nesting depth 64, 200,000 nodes and 1,000 alias expansions so YAML anchor bombs fail safely.
   - Local `$ref` pointers resolve with cycle and depth limits. Remote `$ref` URLs are never fetched.
8. Add threats T-113 to T-118 to [security](../architecture/security.md): prompt injection invoking saved API requests, leakage of collection secrets or cookies to agents, transcripts, logs or SQLite, credentials traveling over plain HTTP or redirects, hostile OpenAPI YAML or JSON files, webview compromise reading `network` collection secrets or triggering manual sends (residual risk bounded to the opt-in plugin), and hostile API response bodies attempting prompt injection.

## Consequences

- Positive:
  - Agents use the owner's configured APIs, variables, headers and cookies through one audited policy path instead of falling back to `curl` or pasting credentials into chat.
  - Collection secrets and cookies stay out of SQLite, logs, agent context, chat transcripts and conversation exports while remaining visible and editable as-is for the owner in the Network Client view.
  - Fixed tools and a protocol-tagged access model handle OpenAPI specifications of arbitrary size and prepare cleanly for raw TCP, GraphQL, WebSockets, gRPC and tRPC without breaking existing contracts.
  - `saphyr-parser` 0.4.0 uses `MIT OR Apache-2.0`, adds only `arraydeque` 0.5.1 alongside `thiserror`, and bounds hostile YAML before document construction.
- Negative:
  - The core gains one new `Access`, `GrantScope`, `ApprovalReason` and `Refusal` variant across `mannie-types`, `mannie-plugin-sdk`, `mannie-tools`, `mannie-runtime` and the desktop approval UI.
  - Allowing the `network` plugin's IPC commands to return collection secrets to the webview widens the residual risk of a compromised webview to include this plugin's collection secrets and manual sends (while keeping all other Mannie credentials isolated).
- Risks:
  - Prompt injection can ask an agent to invoke a saved endpoint with hostile parameter values; every endpoint asks by default unless granted or in full access, and grants bind to the exact saved request, method and origin (T-113).
  - A server can echo a short secret (under 8 bytes) in an arbitrary field of a response body; structured secret headers, parameters and `Set-Cookie` values are always redacted regardless of length, and values of 8 bytes or more are scrubbed everywhere (T-114).
  - Real-world OpenAPI v2 and v3 specs vary in `$ref` usage, parameter styles and auth schemes; unit tests cover v2 and v3.0/v3.1 fixtures, both JSON and YAML, plus malformed and anchor-bomb inputs (T-116).

## Alternatives considered

| Option                                                   | Why not chosen                                                                                                                                             |
| -------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Publish one dynamic tool per endpoint via `tool-sources` | `tool-sources` caps sets at 64 tools and providers cap total tools, so real OpenAPI specifications would overflow and bloat every prompt                   |
| Reuse `Access::ExternalTool`                             | `ExternalTool` models MCP tool servers (`ToolServerEndpoint`, tool hints) and does not bind grants to protocol, HTTP method and canonical origin           |
| Keep secrets write-only in the UI like MCP               | The owner explicitly requires seeing collection secrets and cookies as-is in the Network Client workbench while redacting them for agents                  |
| Allow safe HTTP methods (`GET`) without asking           | The owner chose to ask on every request by default with grants per saved endpoint so `GET` calls cannot silently exfiltrate data or hit internal endpoints |
| Use `serde_yaml` or `serde_yaml_ng`                      | `serde_yaml` is unmaintained (blocked by `cargo-deny`), and `serde_yaml_ng` wraps ported C `libyaml`; `saphyr-parser` is pure safe Rust with explicit caps |
| Allow agents to send arbitrary URLs outside collections  | The owner restricted agents to saved requests defined in collections; ad-hoc requests stay outside this tool                                               |

## Validation

V15: unit, integration, runtime and end-to-end tests verify OpenAPI v2 and v3 (3.0 and 3.1) JSON and YAML import including hostile YAML alias bombs and cyclic `$ref` inputs; OS credential-store persistence and chunking with zero secrets or cookies in SQLite, logs, transcripts or exports; owner as-is visibility in the Network Client workbench alongside `[redacted]` agent tool results, archives and approval prompts; policy authorization, per-endpoint grants keyed by collection, request, protocol, method and origin, environment-switch re-approval, full access and worker ceiling refusal; `credential_transport_allowed` enforcement and no-redirect safety; manual workbench execution and cookie-jar updates against a local HTTP test server; plugin conformance; keyboard operability, axe checks in light and dark themes and the pseudo-locale.

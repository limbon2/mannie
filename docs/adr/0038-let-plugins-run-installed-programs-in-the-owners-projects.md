Later changes: [ADR-0043](0043-let-plugins-offer-the-tools-of-tool-servers.md) refines decisions 7 and 10: a local tool server is a program that the owner names, which may be a `.cmd` or `.bat` file on Windows and receives its own secret variables, while `processes` keeps its rules.

## Context

- The owner wants agents to work with git through tools made for it: read and search history, commit and branch, resolve the conflicts of merges, rebases, cherry-picks and reverts, edit commits and reach remotes, instead of driving git through `run_command` ([decision D37](../roadmap/milestones.md#5-decisions)). The plugin Git runs the owner's installed git program, which its own first ADR records.
- The design rules this out today:
  - A plugin tool's only access is a command on a remote host (ADR-0036). ADR-0034 d6 says that a plugin tool that acts on files or processes, or takes a path, needs an SDK change with an ADR that maps it onto the core's accesses and policy. A plugin tool also learns nothing of the conversation's workspace, and the adapter offers it to every run that its selector names.
  - ADR-0036 d3 lets a read-only plugin tool return no access, so a tool that reads the owner's files could never be checked against the workspace.
  - The process supervisor runs a shell with a command text, Windows PowerShell or `/bin/sh` (ADR-0014 d5). A plugin's library crates may not depend on `mannie-tools`, and a `[native] processes` grant only lifts a lint: the plugin's processes would have no containment, no environment from the allow list and no program that the core resolved.
  - `Access::Command` is a shell's command text. Its rules match words of the text and refuse metacharacters, and its grants match the text. A program that receives an exact argument vector has no shell, and a rule saved for `run_command` would match the plugin's runs.
  - Plugin commands take handles and never paths (ADR-0034 d6), so a plugin's UI cannot read a project's repository.
- The owner's answers of 2026-10-20 (D37): reads never ask inside the workspace; local changes follow the setting that allows changes in the workspace; running hooks, discarding uncommitted work, rewriting commits that are already on a remote-tracking branch and reaching a remote always ask, and grants and saved rules can allow them, also after a hook changed; full access runs all of it without asking; a git folder outside the project asks once, and a grant for the project covers the later calls; version 1 has a side panel that only reads.
- Facts verified on 2026-10-20:
  - The owner's workstation has git 2.54.0.windows.1 at `C:\Program Files\Git\cmd\git.exe`, a path with a space.
  - git runs hooks from its hooks folder and, since 2.54, hooks that configuration defines, which `git hook list <event>` names. Hook frameworks such as husky point `core.hooksPath` at files that the repository tracks.
  - git skips an editor whose command is exactly `:`, and runs every other editor command, and the `exec` lines of a rebase's todo, through a shell.
  - The supervisor's Unix wrapper reads the command text with `eval`, and on Windows PowerShell reads it from standard input (`crates/mannie-tools/src/supervisor`). Both expect a shell's text.

## Decision

1. A plugin tool learns where it acts. `ToolCall` and `ToolExecution` carry the conversation's workspace, the canonical folder of its project, or none, as a mention provider's context already does. The context of an instruction section names the tools that the run offers, so a plugin's section reaches only runs that have its tools.
2. A plugin tool says where it is offered: always, the default; only when the conversation has a workspace; or only when the workspace or a folder above it holds a marker, such as `.git`. The core evaluates the rule as data in its adapter, with a cached check of the file system that follows no link and climbs at most 32 folders, so no plugin code runs for each model call.
3. A plugin tool gets a third effect, `ReadsFiles`: it reads the owner's files. Its preparation returns 1 to 16 path accesses that only read, the policy decides on them as on the reads of `read_file`, and its calls are not journaled (ADR-0013 d6). It may be offered to the `explore` child agent. This refines ADR-0036 d3, under which a read-only plugin tool returned no access: `ReadsOwnData` still returns none, and `SideEffects` returns 1 to 16 accesses of any kind.
4. The SDK's `ToolAccess` gains a path access: an absolute path, its mode (read, write, create or delete) and an optional state, a text that the plugin read of the place, such as a repository's HEAD and the stamp of its index. The adapter maps it through the core's path rules onto the core's path access. The text rules refuse UNC paths, device paths and alternate data streams before any access to the file system (T-17). Links are followed to the canonical place for every mode, because the plugin's program does the writing and the core only decides. The policy is the policy of paths: reads inside the workspace are allowed, changes inside it follow the setting, and a grant covers one mode in a folder and below. The digest covers the state, so a repository that moved while the owner decided goes back to the policy.
5. The SDK's `ToolAccess` gains a program access, for a run that needs the owner beyond the workspace: the program's name in the plugin's manifest, its arguments, its working directory, its effects and an optional state. The adapter adds the plugin, the path of the program that the core resolved and the arguments that the manifest fixes, and maps it onto a new core access, `Access::Program`. The effects are a closed list, each shown to the owner:
   - `network`: the endpoint that the run reaches, such as a remote's URL, without credentials;
   - `runs_folder_code`: a program that the folder's own files or configuration name and the run starts, such as a hook, with its name and its source;
   - `discards_work`: what the run throws away, uncommitted changes, stash entries or commits, with their number, their names and whether the plugin keeps a snapshot first;
   - `rewrites_published`: commits that a remote-tracking branch already holds and that the run rewrites, with their number and those branches.

   A tool returns path accesses for what the workspace setting governs, and adds one program access when one of these effects applies. A run with a program access may also read with the same program in the same folder.

6. The policy decides a program access apart from commands:
   - The workspace never allows one. Full access allows it ([ADR-0029](0029-let-the-owner-give-conversations-and-hosts-full-access.md)).
   - A working directory inside Mannie's data or log folders asks and offers no grant (T-18).
   - A grant for the conversation, its project or every conversation covers runs of the same plugin and program path with the same fixed and plugin's arguments in the same working directory, whose effects the run that it was given for had. An effect counts by its key: an endpoint by itself, a program that the folder names by its name and source and not by its content, so a hook whose content changed keeps its grant (D37), and discarded or rewritten work by its kind.
   - A rule covers runs of the same plugin and program whose arguments start with its words, optionally limited to a folder, with only the effects, by their keys, of the run that it was saved from. A run that reaches another endpoint, starts a program that the folder names that the saved run did not, or discards or rewrites another kind of work asks. Arguments are exact and pass no shell, so a rule refuses no metacharacters. The rules of programs live in a table of their own, so a rule of `run_command` never matches a program run, and the reverse.
   - The request names its own reason, `program`, and shows the program's path, the fixed and the plugin's arguments, the working directory and each effect.
   - On a worker, the ceiling refuses a program access with `no_programs_on_host`. No plugin runs there, and the refusal keeps the policy's decisions complete.
7. A new service, `processes` (major 1, sensitive), runs the programs that the manifest declares, each with a reason, the arguments that the manifest fixes before the plugin's own, and the names of variables that a run inherits when Mannie's environment has them:
   - The core finds a program on Mannie's `PATH` and resolves its links. It takes absolute entries only, never a UNC or device path, never a folder inside a project or inside Mannie's folders, and on Windows only `.exe` files, never `.bat` or `.cmd`, which `cmd.exe` would read as text.
   - A run passes an argument vector exactly, never a shell's text, in a working directory that exists, with the environment of commands, the names that the owner added, the inherited names, and variables that the plugin sets, whose names must not look like secrets, load libraries (`LD_*`, `DYLD_*`) or replace a name of the allow list.
   - A run takes input of up to 16 MiB, returns output as bytes up to a limit of at most 16 MiB with its head kept and a cut marked, and error output up to 256 KiB, within a timeout of at most 600 seconds.
   - Dropping the run's future ends its process tree.
   - A tool's preparation may run a declared program to read, such as asking for a repository's HEAD, as it may read files. Neither changes anything, so the preparation stays free of side effects (ADR-0013 d2).
8. The supervisor gets a program mode. On Windows the program itself starts suspended, joins a job that ends the tree when it closes, and only then resumes. On Linux and FreeBSD the reaper shell runs its positional parameters and never reads an argument as code. Stop, the timeout and the end of the run end the whole tree as they do for commands, and the output is captured as bytes beside the text capture of commands.
9. A side-effect tool's execution carries its path and program accesses among the authorized accesses, and the tool acts on exactly those: when what they name, or their state, changed since, it fails without acting (refines ADR-0036 d5).
10. A plugin command and a mention provider may run a declared program only to read. They name the folders that the run reads, and the service checks them as a model's reads would be checked there before it starts anything: a command by its project's workspace and by the grants of the project and of every conversation, and a mention by its conversation's workspace, grants and full access. A read that would ask refuses the run with `read_not_allowed` and the folder. A command still takes a project's ID, never a path. A plugin command that changes a repository or reaches the network needs an ADR of its own.
11. The threats of [security](../architecture/security.md) gain T-44 to T-51: code that a repository holds or names runs during a program's run, options or pathspecs injected through the model's arguments, a program other than the owner's runs, credentials in remote URLs reach transcripts, a program acts outside the workspace through its own configuration, a run reaches a remote that an injection planted, an agent's run loses work, and script in the webview reads repositories through a plugin's commands.

## Consequences

- Positive: a plugin can act on the owner's projects through an installed program under the same workspace, approvals, grants, rules, full access and journal as the core's tools, with the program's processes contained like commands. Reads in the workspace run without asking, local changes follow the owner's setting, and only runs with effects beyond the workspace ask. Later plugins with installed programs, such as a code formatter or a database client, use the same service and accesses.
- Negative: the core gains a kind of access, its grants and rules, a table of rules and the program mode of the supervisor, and the SDK gains a service with an effect, two accesses and an offering rule. A grant or a rule for a hook covers it after its content changes, which the owner chose (D37): an agent that can edit a hook's file can then run it under that grant or rule. A program reads its own configuration, which can name more programs; the plugin must find them and declare them, and review checks that it does.
- Risks: the effects of a program's run come from the plugin's knowledge of that program, so a version of the program that runs something the plugin does not foresee runs it under the access that the owner allowed. Tests that record what actually runs, against the oldest and the newest version that the plugin supports, find such gaps. A Windows program that opens a window of its own, such as a credential manager's sign-in, waits for the owner until the timeout.

## Alternatives considered

| Option                                                    | Why not chosen                                                                                                                                                                          |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Access::Command` without a shell                         | Rules and grants of `run_command` would match program runs and the reverse, its rules refuse characters such as `$` and braces that exact arguments need, and its shell field would lie |
| A `[native] processes` grant and processes in the plugin  | No containment, no environment from the allow list, no program that the core resolved, and the owner chose the supervisor                                                               |
| Approvals inside the plugin                               | Grants, rules, full access and the journal would split from the core's policy, as ADR-0036 found for remote commands                                                                    |
| A callback that decides whether a tool is offered         | Plugin code and file system access would run for every model call, and a callback breaks the SDK's protocol rules (ADR-0034 d3)                                                         |
| One program access for every change                       | Every commit would ask, against the owner's choice that local changes follow the workspace setting                                                                                      |
| Separate access kinds for network, folder code and losses | One run's approval would split across kinds, and a rule could not cover the run whole                                                                                                   |

## Validation

M9:

- Policy tests for every source of a decision on a program access: the workspace, Mannie's folders, grants of the three scopes with the same and other arguments, effects and paths, rules with their words, folder and endpoints, full access and a worker's ceiling.
- Store tests for the rules of programs and their unique key.
- Runtime tests with fake plugin tools: reads inside and outside the workspace, the `explore` agent offered reads only, offering by a marker, a path write that follows the setting, a program access that asks and its three grants, a rule, a changed state that goes back to the policy, and full access.
- Tests of the supervisor's program mode on Windows and Linux: arguments that reach the program exactly, from a corpus with spaces, quotes, `%`, `^`, `$`, backslashes, non-ASCII text and empty strings; Stop, the timeout and a dropped run each end a grandchild; byte limits; and a resolver that refuses relative, UNC and project entries and `.cmd` files.
- The plugin Git's tests against the installed git 2.40 and the newest git, with hooks that record which of them run.

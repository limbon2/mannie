## Context

- Mannie was built as one product around the master and its workers ([decisions D4 and D5](../roadmap/milestones.md#5-decisions), [ADR-0015](0015-run-an-agent-runtime-on-every-machine.md)). The owner now wants a core that holds what every agent harness needs, and plugins for everything else, which each owner turns on when they need them: integrations such as Jira, git, a code editor, a terminal, database clients and log viewers. Not every owner needs workers, so the worker system becomes the first plugin ([decision D26](../roadmap/milestones.md#5-decisions)).
- Features plug into extension points through registrations that the composition roots and the UI's `composeShell()` make once, at startup ([ADR-0002](0002-grow-through-extension-points.md), [ADR-0020](0020-complete-the-ui-shell-slots.md)). The desktop app's composition root builds the agent definitions, the instruction sections and the tool registry and hands them to the runtime once. No registry and no UI slot can drop an entry, and nothing can switch a feature off while Mannie runs.
- The store's migrations are one ordered list in `mannie-store`, and SQLite's `user_version` holds how many of them a database has. The tables of each feature belong to a module of `mannie-store`, the only crate that uses SQLite ([ADR-0008](0008-one-workspace-two-binaries.md), [ADR-0009](0009-persist-state-in-sqlite.md)), and the runtime's deletions call into the workers' module inside their transactions.
- ADR-0002 rejected a runtime plugin system, because loading code at runtime brings security and compatibility problems, and the goals rule out third-party scripts or plugins in the webview ([ADR-0004](0004-keep-system-access-in-the-rust-core.md)). The owner wants internal plugins now and may want an API or SDK for third-party plugins later.
- The owner decided that turning a plugin on or off takes effect at once, without restarting Mannie, and that each plugin's code lives in a folder of its own, `plugins/<id>/` (D26).
- Only `mannie-desktop` depends on Tauri ([ADR-0003](0003-build-the-desktop-app-on-tauri-2.md), risk R1). The UI is one SvelteKit bundle ([ADR-0005](0005-build-the-ui-with-sveltekit-as-a-static-spa.md)), its IPC bindings are generated from one list of commands ([ADR-0007](0007-generate-ipc-bindings-from-rust.md)), and its text comes from one message catalog per locale ([ADR-0019](0019-keep-visible-text-in-message-catalogs.md)).

## Decision

1. Mannie consists of the core and plugins. The core is what every owner gets: chat with its provider profiles and projects, system tools with approvals and the journal, child agents, window and tray, the settings, the store, the credential store and logging. A plugin is an optional feature, or a group of features, that the owner turns on and off. Workers is the first plugin ([ADR-0031](0031-move-workers-into-the-first-plugin.md)).
2. Plugins are internal. Their code is in this repository, is reviewed like the core's, and is built and released with the desktop app ([ADR-0018](0018-release-from-tagged-builds.md)). The desktop app's composition root lists them in code, as ADR-0002 requires, and nothing is discovered, downloaded or loaded at runtime. Third-party plugins, and an API or SDK for them, need an ADR of their own.
3. A plugin has an ID of lower-case words joined by hyphens, such as `workers`. The ID names the plugin's folders and, with underscores in place of hyphens, prefixes its tables, its settings section and its message keys. Its definition in Rust gives the ID, the plugin's migrations, whether it is on when the owner has not chosen yet, and its start and stop. Its name and description for the owner are messages under its key prefix.
4. A new core crate, `mannie-plugins`, holds what plugins build on: the definition, the context that a start receives, the contributions that a start returns, the plugin states, and the host that starts and stops plugins and keeps the owner's choices. The composition root runs the host and connects it to IPC.
5. A plugin contributes through the extension points ([extension points](../architecture/extension-points.md)), including the ones that ADR-0031 adds. The tool registry and the registries of agent definitions, instruction sections and task executors keep each contribution with the ID of the plugin that made it, take a plugin's contributions while Mannie runs, and drop them when it stops. Two kinds of contribution stay fixed for the life of the process, because they cannot change while it runs:
   - A plugin's migrations run at startup with the core's, whether or not the plugin is on, so the schema never depends on a plugin's state. The store records the migrations that it applied for each module, the core's modules and each plugin, so a plugin numbers its migrations on its own. The first start of this scheme carries over what `user_version` recorded.
   - A plugin's IPC commands and channel messages are part of the generated bindings. While the plugin is not on, its commands refuse with the error `plugin_off`, and its channels end with that reason.
6. Turning a plugin on calls its start, which receives the core services that the composition root gives it and returns the plugin's contributions. The registries then take them and the UI shows them. A start that fails leaves the plugin failed, with an error code that the Plugins page shows with "Try again". Turning a plugin off first drops its contributions from the registries and the UI, then calls its stop, which ends its background work. A stop never repeats or loses an operation: work in progress ends as it ends when Mannie quits, and the plugin's feature document says what that means for each kind of its work.
7. A plugin's state is one of `off`, `starting`, `on`, `stopping` and `failed`. The owner's choice is a setting of the core. At startup, after the core's recovery, the host starts each plugin that the owner turned on, in the order of the composition root's list. A plugin without a stored choice starts when its definition says so for the data that the store holds, which lets an update keep a plugin on that the owner already uses. Quitting stops the plugins that are on, as turning them off does, and keeps the owner's choices.
8. A run keeps the tool definitions and the system prompt that it started with, so the tools that the model sees never change within a reply. A call into a plugin that stopped does not run, and its result tells the model that the plugin is off.
9. A plugin's data stays when the plugin is off, and the plugin continues with it when it starts again. A plugin owns its tables under its prefix ([ADR-0009](0009-persist-state-in-sqlite.md)), and its own code reads and writes them through the store's writer and readers, which `mannie-store` opens to the modules that the composition root registers. SQLite stays a dependency of `mannie-store` alone, and a plugin's statements get the same checks against the migrated schema as the core's. The core's tables never refer to a plugin's tables, and no deletion in the core cascades into them. Work that the core hands to a plugin while the plugin is off, such as the deletion of a conversation that the plugin holds data for, waits in the core until the plugin starts and takes it. Removing a plugin's data is outside this decision.
10. The core never depends on a plugin, and a plugin never depends on another plugin. A plugin reaches the core only through the core's public interfaces and the services that its start receives.
    - Rust: a plugin's crates, binaries and contracts live in `plugins/<id>/`, and the core's crates stay in `crates/` ([ADR-0008](0008-one-workspace-two-binaries.md) refined). cargo-deny refuses a dependency of a core crate on a plugin crate, and of a plugin's crate on another plugin's.
    - UI: a plugin's components, state, helpers, types and registration stay in the desktop app's folders for each kind, under the plugin's ID (`components/app/<id>/`, `registrations/<id>.ts`), and its Tauri commands stay in `mannie-desktop` under the plugin's ID as thin calls into the plugin's crates, because Tauri and the UI bundle belong to the desktop app. A lint rule refuses imports from a plugin's UI files in the core's UI files and in other plugins' UI files.
11. `composeShell()` calls every internal plugin's UI registration, which registers its entries with its plugin's ID, and can return a function that ends the plugin's subscriptions. The slots list a plugin's entries only while the core reports the plugin as on, through a channel of plugin states, so turning a plugin on or off changes the shell without reloading the webview. An address that opens a view, a settings page or a side panel of a plugin that is off shows a state that says so, with a link to the Plugins page.
12. What a plugin added to a conversation, such as a part or a task, stays readable while the plugin is off, from what the core stored, and an action on it that needs the plugin says that the plugin is off.
13. Internal plugins are trusted like the core: they run in the core's process with its rights. The start context is the only way a plugin reaches core services, so the composition root shows in one place what each plugin can use. A plugin reaches the operating system credential store only through a service that is limited to the entries that the plugin owns, and reads a provider credential only through a service of the core that the composition root grants it.
14. Extension points grow by addition ([ADR-0002](0002-grow-through-extension-points.md)): the registries in decision 5 learn plugin IDs and removal, the store learns modules with migrations of their own, the UI slots learn the plugin of an entry, IPC learns the error `plugin_off`, and the settings learn the owner's choices of plugins.

## Consequences

- Positive: an owner gets a core without features they do not use, and a new integration lands as a plugin with a boundary that cargo-deny and the lint rules check. Turning a plugin on or off needs no restart, and the core's tests run without any plugin.
- Negative: every registry and slot learns removal and plugin IDs, and each plugin writes and tests a start and a stop. A plugin's IPC commands stay in the bindings while it is off. The repository gets a third folder of code, `plugins/`, and the worker's code moves into it, with the paths of CI, the release workflow and the contract checks.
- Risks: a stop that leaves work behind, or a start that finds stale state. Each plugin's tests turn it off and on with work in progress and check that nothing runs twice and nothing is lost. A reply that keeps a stopped plugin's tools gets refusals until it ends. A defect in a plugin has the core's rights, as a defect in the core does, and review covers both.
- Refinement in M5: decisions 4, 7 and 13 were made concrete while the host was built ([plugins](../features/plugins.md)). A plugin without a stored choice follows its default once, at the first start that finds no choice, and the host keeps the outcome as the owner's choice, so a later change in the store's data turns no plugin on or off by itself. The start context gives a plugin only the services of its grant in the composition root: the runtime's services for a task executor, the lender of provider credentials, and the credential store limited to the plugin's own entries; a plugin that needs a service without its grant fails to start with the code `grant_missing`.

## Alternatives considered

| Option                                                                | Why not chosen                                                                                                                       |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Cargo features, with one build for each set of plugins                | The owner turns plugins on and off in one installed app                                                                              |
| Plugins loaded at runtime, as dynamic libraries or WASM               | ADR-0002 rejected loading code at runtime, and an API for third parties needs an ADR of its own                                      |
| Turning plugins on and off at the next start                          | The owner chose that it takes effect at once (D26)                                                                                   |
| Plugin crates in `crates/`, marked by name                            | The owner chose a folder for each plugin (D26)                                                                                       |
| A package of its own for each plugin's UI                             | The UI is one SvelteKit bundle with generated bindings and one catalog per locale, which a plugin's package would have to reach into |
| Tauri commands in each plugin's crates                                | Tauri would spread beyond `mannie-desktop`, which ADR-0003 and risk R1 keep it inside                                                |
| Registering every plugin always, with a flag that each feature checks | Every tool, section and component would check the flag, and a forgotten check would leak a plugin that is off                        |

## Validation

M5:

- Registry tests with a fake plugin that is turned on and off while a run uses it: a run keeps the tools it started with, a call into the stopped plugin is refused, and a new run gets the change.
- Host tests: the order of starts, a failing start, a stop with work in progress, the default for a plugin without a stored choice, and starts after the core's recovery.
- Store tests: a plugin's migrations run whether it is on or off, and the upgrade from the 0.2.0 fixture database keeps Workers on when a worker is paired.
- cargo-deny and the lint rule refuse a planted dependency of the core on a plugin, and end-to-end tests turn Workers off and on from the Plugins page, with the shell changing without a reload, on WebView2 and WebKitGTK, with axe.

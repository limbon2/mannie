Mannie adds features by registration. A feature is a vertical slice: Rust modules, IPC types, UI components, migrations and tests, plus its feature document. The slice plugs into the extension points below and leaves other features alone ([ADR-0002](../adr/0002-grow-through-extension-points.md)). An optional feature, or a group of features, is a plugin, which the owner turns on and off: its contributions enter the registries when it starts and leave them when it stops, while Mannie runs ([ADR-0030](../adr/0030-split-mannie-into-a-core-and-plugins.md)). A plugin reaches the extension points and the core's services only through the plugin SDK, which is the bridge between the plugins and the core: its Rust code depends on `mannie-plugin-sdk`, its tests also on `mannie-plugin-harness` and its programs also on `mannie-host-kit`, and its UI imports only `@mannie/plugin-sdk` ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md)).

## 1. Rules for every extension point

1. A feature owns what it registers. Other features reach it only through its public interface or through another extension point.
2. Registration is explicit code in a composition root (`mannie-desktop-core`, `mannie-worker`), in a plugin's start, or in a registry module of the UI shell. Nothing is discovered or loaded at run time. At build time, a folder with a `plugin.toml` under `plugins/` registers a plugin, and `task gen` writes the list of plugins that the desktop app runs from the manifests ([ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decision 2).
3. Contracts grow by addition. A reader that meets a variant it does not know skips it or shows it in a generic form, and does not fail.
4. Each extension point has an owning module and a test that registers a fake entry, so a broken extension point fails its own tests first.
5. A new extension point, or a change to an existing one, needs an ADR. An extension point is added when the first feature needs it.
6. A registry that takes a plugin's contributions keeps the plugin's ID with each one, and drops them when the plugin stops. A run keeps what it started with. The core never depends on a plugin, and a plugin never depends on another plugin.

## 3. The extension points

### 3.1 Tool registry

A tool implements the `Tool` trait. It declares its name, a description written for the model, an input schema generated from a Rust type with schemars, its permission class: read-only, or with side effects, and whether a model call is offered it, which can depend on the conversation's project and the owner's projects. Its executor follows the operation lifecycle ([ADR-0013](../adr/0013-journal-every-side-effect.md)): prepare, then execute after authorization. Results are typed values with a rendering for the model. An agent definition names the tools its agent may use, and a run gets those of them that the registry holds, so a tool that a platform's composition root does not register, such as `run_command` on FreeBSD until workers bring it, is not offered there. The registry rejects duplicate names when tools register. [Tools](tools.md) has the contract in full. Tools that act on runs rather than on the machine, such as the task tools of child agents, belong to the runtime and stay outside the registry ([ADR-0024](../adr/0024-run-child-agent-tasks-in-the-parent-run.md)).

A plugin's tools enter the registry when the plugin starts and leave it when it stops. A run keeps the tool definitions it started with, and its call of a tool whose plugin stopped does not run: the model reads that the plugin is off, and the call's part records the reason `plugin_off`. Turning a plugin off waits up to 5 seconds for the calls of its tools that run, and then aborts them: an operation becomes uncertain, and a read ends as not run.

A plugin's tool declares its effect ([ADR-0036](../adr/0036-let-plugins-run-commands-on-remote-hosts.md)). A tool that reads only its plugin's own data returns no access and is not journaled. A tool with side effects returns accesses of the SDK's `ToolAccess`, such as a command on a remote host, which the runtime maps onto the core's accesses, so the policy, approvals, grants, rules and the journal treat its calls as they treat the core's. Its execution receives the accesses that were authorized, the limit of the run's results and archive IDs that the core reserved, and its result may carry archives that `read_tool_output` reads. The core never offers a tool with side effects to the `explore` child agent.

### 3.2 Agent definitions

An agent definition names an agent's instructions, its tool set (tool names from the registry), its budgets and its default provider profile. It also says who the agent answers to, the owner or another agent, which chooses the wording of its base instructions, its notes and its denials, and how many tasks a reply may give to child agents. Built-in definitions include the conversation agent and the explore and general child agents. A plugin can add definitions while it is on, and a composition root can register its own, as the Workers plugin's service registers the worker agent, which the master never offers to `start_task`. A run names the definition it runs with, and a feature that needs a new kind of agent registers a definition. It does not change the loop.

### 3.3 Provider adapters and quirk profiles

An adapter implements the `Provider` trait for one API interface ([ADR-0011](../adr/0011-own-the-provider-adapters.md)). A quirk profile is data: it matches a server or a model and switches documented normalizations on, such as reading tool calls that the model wrote as text. A feature that supports a new provider adds an adapter or a quirk profile, together with recorded fixtures for its tests.

### 3.4 Instruction sections

The system prompt is assembled from sections that modules register, each with a fixed position. Stable sections come first (the base instructions, the agent definition, the tool guidance and the owner's instructions), and sections specific to a host or a session come after them, so that providers can cache the stable prefix. Context that changes from turn to turn goes into the latest user message instead of the system prompt. A section can depend on what a run is offered: the guidance on tasks reaches only runs that are offered the task tools, and an executor's section, such as the Workers plugin's list of workers, reaches only runs that are offered its tool. The context carries the description of its machine that a composition root gives the runtime, such as a worker's host, and a composition root can assemble a registry of its own, as the worker does. A plugin's sections enter and leave the registry with the plugin.

### 3.5 Transcript parts and run events

Parts and events are tagged enums in `mannie-types` with a version-tolerant encoding. A feature adds a variant together with its rendering for the model and its renderer in the UI. Code that reads parts handles unknown variants: the model sees a short placeholder, and the UI shows a generic card. An unknown event changes nothing that the UI shows, and the UI moves its cursor past it.

M1 adds the parts of chat: the owner's text, the reply's text, reasoning, and errors, each with a state (streaming, complete, stopped, interrupted, incomplete or discarded) and an audience (the owner, the model or both). Its events cover turns, runs, parts with their deltas, discarded attempts, checkpoints, the context's use and changes to a conversation ([conversations](../features/chat/conversations.md)).

M3 adds the part `task`, which records a call of a task tool together with its task, and the run activity `waiting_for_tasks` ([tasks](../features/child-agents/tasks.md#the-task-part)). Code in the store and the runtime that handles calls treats `task` parts as it treats `tool_call` parts.

M4 adds the worker to a task's section, for tasks that run on a worker, and the run activity `waiting_for_lease` ([delegation](../../plugins/workers/docs/delegation.md#contracts)).

M5 adds the executor to a task's section and to a task conversation's summary, with its kind and target, the refusal `executor` with the executor's code, the reason `plugin_off` for a call that did not run, and a count for each kind of task in `waiting_for_tasks` ([ADR-0031](../adr/0031-move-workers-into-the-first-plugin.md), decision 6). The worker's fields and refusals stay readable through 0.3.0, and the core's views show them in the executor's shape.

M6 adds the part `mention`: something that the owner's message mentions, stored after the owner's text with what the model reads of it and what the owner sees ([ADR-0032](../adr/0032-let-features-and-plugins-add-kinds-of-mentions.md), decision 7).

M7 adds the part `image`: an image of the owner's message, stored after its mentions, whose bytes the store keeps in a table beside the parts and the UI reads with `read_image`. The model reads it as an image in the same message, and the provider adapters send it inline ([ADR-0033](../adr/0033-let-plugins-attach-images-to-the-owners-messages.md), decisions 4 to 6).

### 3.6 IPC commands and channels

Each feature of the core defines its command arguments, results, errors and channel messages in `mannie-types` and registers its commands with tauri-specta in `mannie-desktop-core`, whose commands live in `apps/desktop/core/src/commands/`, one module per area ([ADR-0007](../adr/0007-generate-ipc-bindings-from-rust.md)). A plugin declares its commands and channels in its crates with the SDK's specs, and its start hands the host their handlers. The desktop binary's build makes each plugin an inlined Tauri plugin with a permission for each command, from the interfaces that `task gen` wrote, and grants them to the main webview, the desktop app hands every call to the host's dispatch, and the host checks the call and answers `plugin_off` while the plugin is not on and ends its channels with that reason ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 8). A plugin's TypeScript bindings are generated into its folder's `ui/generated/` (decision 9). Every command needs a capability grant ([ADR-0004](../adr/0004-keep-system-access-in-the-rust-core.md)). A changed contract gets a new command, and the old one is deprecated.

### 3.7 UI shell slots

The shell defines typed slots in `apps/desktop/src/lib/state/shell-slots.svelte.ts`, with their entry types in `types/shell-slots.ts` ([ADR-0020](../adr/0020-complete-the-ui-shell-slots.md)):

- navigation entries and views; a view's title can be content, such as a conversation's title, which the pseudo-locale check then skips;
- sidebar panels, below the navigation, such as the projects and the conversation list;
- overlays, mounted once at the shell's root, such as dialogs that several places open;
- settings sections, each a page of the settings that the settings sidebar lists by its icon and title;
- command palette actions, which can say when they are available;
- part renderers, keyed by part type, with a generic card for a type that no feature registered;
- side panels, each a kind of content that opens beside the main view with an argument, such as a conversation's ID, and whose component can close its panel and name its tab; open panels show as tabs, belong to the view that opened them through its address, and get a generic body when no feature registered their kind ([ADR-0025](../adr/0025-add-side-panels-to-the-shell.md));
- conversation controls, each a feature's compact button or menu in a conversation's toolbar, which receives the conversation's summary and the turns that the view has loaded, and renders nothing when it has nothing to offer ([ADR-0026](../adr/0026-add-conversation-controls-back-for-child-agents.md));
- task kinds, one for each kind of task of a plugin's executor, with its icon and the messages that the task card, the call note, a task conversation's read-only footer, the status line and its refusals use; without an entry, such as while the plugin is off, these show generic texts that name the target ([ADR-0031](../adr/0031-move-workers-into-the-first-plugin.md), decision 7);
- mention kinds, one for each mention provider, with the heading of its group in the "@" list, an icon for each variant, and the words of its warnings, refusals and summaries; without an entry, such as while its plugin is off, these show generic texts ([ADR-0032](../adr/0032-let-features-and-plugins-add-kinds-of-mentions.md), decision 4);
- image sources, one for each source of images, with its button in the message box, the files of a paste or a drop that it takes, and the words of its refusals; without an entry, the message box offers no images from the source ([ADR-0033](../adr/0033-let-plugins-attach-images-to-the-owners-messages.md), decision 7).

A feature registers its Svelte components in its registration, `src/lib/registrations/<feature>.ts`, and the shell renders whatever is registered. The shell never imports a feature directly. The window has a fixed height, so a view can keep parts of itself in place, such as a message box below a transcript. The frontend is sorted by kind, so the feature's components, state and helpers sit with the others of their kind ([desktop app](desktop-app.md#6-frontend-structure)).

A plugin registers through `composeShell()`, which calls the `register` of its `definePlugin(...)` with the plugin's context: its own view of the slots, so every entry carries the plugin's ID, whether it is on, and `whileOn()`. A slot lists such an entry only while the core reports the plugin as on, through the channel of plugin states, so the window changes without a reload. An address of a view, a settings page or a side panel of a plugin that is off shows a state that names the plugin, with the way to the Plugins settings. A plugin's UI state follows the plugin through the context's `whileOn()`, so its subscriptions run only while the plugin is on. The slot catalog of the TypeScript SDK, `@mannie/plugin-sdk/slots`, holds every slot with the type of its entries, and the type checks hold the shell's slots to it. Only the plugin list that `task gen` generates imports a plugin's UI, which the lint rule `mannie/plugin-boundaries` and a Vite plugin check ([ADR-0030](../adr/0030-split-mannie-into-a-core-and-plugins.md), decisions 10 and 11; [ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 11; [ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decisions 6 and 7).

### 3.8 Settings sections

A feature declares a settings section as a Rust type with defaults and validation. The store persists it, the settings show it as a page of its own through the feature's settings slot, and the core validates every change. Settings never contain secrets; a credential is a reference to the credential store. The owner's choices of plugins are the core's section `plugins`.

### 3.9 Store tables and migrations

A feature owns its tables, named with its module's prefix, and the forward-only migrations that create and change them ([ADR-0009](../adr/0009-persist-state-in-sqlite.md)). It reaches other modules' data through their repositories. A destructive change takes two releases: the first adds the new shape and stops using the old one, and the second removes the old shape.

Each module numbers its migrations on its own, and the store records how many of each module's migrations a database has. The core's modules migrate first, then the modules of plugins in the composition root's order, whether or not a plugin is on, so the schema never depends on a plugin's state. A plugin's code reaches its tables through the SDK's service `store`, as the statements that its module lists ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 7): the store checks the module before it opens the database, runs the module's migrations under an SQLite authorizer that confines them to the tables of the plugin's prefix and checks the schema outside the prefix after each one, prepares each listed statement under the same authorizer after the migrations, refuses any other text, and runs a plugin's writes as batches of one transaction each. A statement that does not prepare leaves only that plugin without its tables. The core's tables never refer to a plugin's tables. A database from before M5 carries its numbered migrations over to these records, also for a module that is registered only later.

### 3.10 Link services

The Workers plugin owns the link. A part of it that needs traffic between the master and workers adds a protobuf package `mannie.link.<service>.v1` under `plugins/workers/proto/mannie/link/<service>/v1/` with its own feature level ([ADR-0016](../adr/0016-link-machines-over-pinned-mtls-grpc.md)). The two sides agree on feature levels when they connect, and a feature checks the agreed level before it uses its service. `buf breaking` guards compatibility, and fixture tests guard the JSON documents that travel inside the messages.

### 3.11 Message catalogs

A feature adds its visible text as messages in `apps/desktop/messages/en.json`, with keys under the feature's own prefix, such as `chat_` or `tools_`, and a plugin in its own `plugins/<id>/messages/en.json`, under its ID, such as `workers_`, which `task gen` compiles with the core's into one catalog ([ADR-0019](../adr/0019-keep-visible-text-in-message-catalogs.md); [ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decision 8). Paraglide JS compiles the catalogs into typed message functions, so a component that uses a missing key fails the build. Error codes from the core map to messages in the same catalog. A feature never edits another feature's messages, the core's messages never name a plugin's things, and translations of a feature's messages go into the catalog of each added locale.

### 3.12 Task executors

A kind of task that runs somewhere other than the parent's run is a task executor, which a plugin registers while it is on ([ADR-0031](../adr/0031-move-workers-into-the-first-plugin.md), decision 4). It replaces the delegation port of M4. The executor gives its kind, which is its plugin's ID, its tool and its instruction section, which a run reads once when it starts; it plans a call or a follow-up, or refuses it with a code and the text that the model reads; it submits, cancels and serves the conversations of the tasks that the runtime stored first; and it says whether its tasks outlive the reply that started them. It reaches the core through the services that its plugin's manifest declares ([orchestration](orchestration.md#4-task-executors)).

### 3.13 Plugins

A plugin implements the `Plugin` trait of the plugin SDK, and its manifest gives its ID, its order and the services that it uses ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decisions 4 and 5): its module of the store if it has tables, whether it is on when the owner has not chosen yet, which reads its module, and its start. The start receives a context with the services that the host bound from the manifest, such as the secrets service with the entries that the manifest names and the keyed families whose entries the plugin creates and deletes, one for each host of the SSH plugin ([ADR-0036](../adr/0036-let-plugins-run-commands-on-remote-hosts.md), decision 8), and returns its contributions, tools, agent definitions, instruction sections, task executors, mention providers and image sources, with the instance that the host keeps until it stops the plugin and asks for the plugin's work in progress. A start fails with `sdk_incompatible` for a plugin built for another major of the SDK, `service_unavailable` for a declared service that the host could not bind, `grant_missing` for a service that the manifest does not declare, and `contributions_refused` for contributions that the core refuses. The host keeps the owner's choices, starts the plugins that are on after the core's recovery, makes one change at a time, and reports each plugin's state, `off`, `starting`, `on`, `stopping` or `failed`, through a channel ([plugins](../features/plugins.md)).

### 3.14 Mention providers

A mention provider gives the message box's "@" list a kind of mention ([ADR-0032](../adr/0032-let-features-and-plugins-add-kinds-of-mentions.md)). It has an ID, says whether it is offered where the owner writes, such as only in a conversation with a workspace, suggests entries for what the owner typed after "@", and resolves the key of an entry, which it checks again because the webview sent it, into content that renders within any number of bytes. The mentions of one message share the room of one tool result, and the core divides that room among them. A composition root registers the core's providers in a `MentionRegistry`, and a plugin adds providers in its contributions, with IDs that are its ID or start with it and a dot; they leave the registry when the plugin stops. The UI words each kind through the slot of mention kinds. The core's provider `files` offers the files and folders of a conversation's workspace ([mentions](../features/chat/mentions.md)).

### 3.15 Image sources

An image source gives the owner's messages images ([ADR-0033](../adr/0033-let-plugins-attach-images-to-the-owners-messages.md)). It has an ID, resolves a key that the message names into a prepared image with its thumbnail, which it checks again because the webview sent it, and lets the images of a message go once the message is stored. Only plugins add sources, in their contributions, with IDs that are their ID or start with it and a dot. The core checks what a source returns, PNG or JPEG within the limits of a stored image, and stores the image with the message, so it stays readable and reaches the model after the source's plugin stops. The UI's slot of image sources gives each source its button in the message box and the files of a paste or a drop. The first source is the plugin Images ([images](../../plugins/images/docs/README.md)).

## 4. Anatomy of a feature slice

| Layer            | What the feature adds                                        | Where                                                                                                                                          |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Feature document | Intent, behavior, fit, design and acceptance                 | `docs/features/<slug>.md`, or a folder for a big feature; a plugin's `plugins/<id>/docs/README.md`                                             |
| Rust logic       | A module in the crate that owns the capability               | `crates/<crate>/src/<feature>/`, or a plugin's crates in `plugins/<id>/crates/`                                                                |
| Shared types     | IPC types, parts, events and settings                        | `crates/mannie-types/src/<feature>/`, or the plugin's crates                                                                                   |
| Registration     | Calls to the registries                                      | The composition roots in `apps/`, or the plugin's start                                                                                        |
| UI               | Components, state and slot registrations                     | `apps/desktop/src/lib/`, sorted by kind: `components/app/<feature>/`, `state/`, `registrations/<feature>.ts`; a plugin's in `plugins/<id>/ui/` |
| Data             | Tables and migrations                                        | The feature's module of the store, or the plugin's own module                                                                                  |
| Link contract    | A protobuf package, when machines talk                       | `plugins/workers/proto/mannie/link/<service>/v1/`                                                                                              |
| Visible text     | Messages under the feature's key prefix                      | `apps/desktop/messages/`, or the plugin's `plugins/<id>/messages/`                                                                             |
| Tests            | Unit tests beside the code, integration and end-to-end tests | Next to the code and in each crate's `tests/`, and a plugin's UI and end-to-end tests in `plugins/<id>/tests/`                                 |
| Changelog        | One line                                                     | `CHANGELOG.md`, or the plugin's `plugins/<id>/CHANGELOG.md`                                                                                    |

## 5. When an extension point is missing

If a feature cannot be built without editing modules that belong to other features, an extension point is missing. Stop, and write an ADR that adds the extension point in a general form, with the feature as its first user. Build the extension point, then the feature on top of it. A one-off exception in another feature's code is not an acceptable shortcut.

A plugin that needs something the SDK does not provide gets it from the SDK: the SDK changes first, with an ADR for a new or changed extension point or service, and the plugin builds on that change ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 14). A plugin never reaches past the SDK into the core's crates, files or modules, so a plugin needs no change in the core to be added.

The desktop app is the master. It is a Tauri 2 application with a Rust core and a SvelteKit UI in the operating system's webview.

Its Rust code is two crates ([ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decision 4). `mannie-desktop-core`, in `apps/desktop/core/`, is a library of the root workspace with the composition root, the IPC commands, the window and tray and the forwarders of the plugins' calls, and it names no plugin. `mannie-desktop`, in `apps/desktop/src-tauri/`, is the binary: Tauri's configuration, its build script, the capabilities and the icons, and a `main` that runs the core with the plugins that `task gen` listed. The binary belongs to the launcher workspace that `task gen` writes into `.generated/desktop/`, so it builds only after `task gen`.

## 1. Trust model

The Rust core is trusted, and the webview is not ([ADR-0004](../adr/0004-keep-system-access-in-the-rust-core.md)). The webview renders model output, tool output and file contents, any of which may be hostile. The core therefore treats every command from the webview as untrusted input, validates its arguments, and applies the same policy that applies to a model's request. The webview holds no secrets, no transcripts and no settings that matter.

## 2. IPC contract

| Mechanism | Used for                                                                                                                     | Notes                                                                                            |
| --------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Commands  | Requests from the UI: send a message, decide an approval, change a setting                                                   | Typed arguments, results and errors, generated by tauri-specta                                   |
| Channels  | Ordered streams from the core: a conversation's events, the conversation list, the core's questions about closing the window | `tauri::ipc::Channel<T>`, created per subscription, a conversation's with a cursor               |
| Events    | Not used                                                                                                                     | The core's questions to the window travel over a channel, so the webview has no event permission |

- The types come from `mannie-types`, and the bindings are generated into `apps/desktop/src/lib/generated/` ([ADR-0007](../adr/0007-generate-ipc-bindings-from-rust.md)). The frontend calls only the generated functions. A plugin's bindings are generated into its folder's `ui/generated/`, and their calls go through the generated transport to the plugin's inlined Tauri plugin and the host's dispatch ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decisions 8 and 9).
- Errors are a typed enum with a stable code and its arguments. The UI shows the message for that code from its catalog and never parses error text. The English description in an error is for logs only ([ADR-0019](../adr/0019-keep-visible-text-in-message-catalogs.md)).
- Every command needs a capability grant through `AppManifest::commands`, and only the main window receives grants.

## 3. Streaming to the UI

- The UI subscribes to a conversation by opening a channel with the last sequence number it has, its cursor. The core first sends the stored events after the cursor, or a snapshot when there is no cursor or it lies too far back, and then the live events, in order and without gaps ([conversations](../features/chat/conversations.md)).
- The core sends a channel's messages in batches, at most one every 16 ms, so the frame rate of the webview sets the pace and not the token rate of the provider. An idle channel waits without waking up. Batches carry consecutive sequence numbers, and a UI that sees a gap subscribes again from its cursor.
- A subscriber that falls behind ends with `lagged` and subscribes again from its cursor. Each subscription has an ID, and a view that closes ends its own.
- When the window reloads, the core ends every subscription of the page before it, and the UI subscribes again with the cursor it kept. Runs never depend on a subscription ([ADR-0012](../adr/0012-run-agents-as-durable-actors.md)).
- A channel's task runs on Tauri's async runtime, which synchronous commands, running on the main thread, can reach too.

## 4. Security configuration

- Plugins: single-instance, and one inlined plugin for each of Mannie's plugins, which the build generates and whose calls go to the plugin host ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 8). The opener crate's Rust function opens a link that the owner confirmed; its plugin is not registered, so the webview cannot call it. The fs, shell and http plugins are not used, and any other plugin needs an ADR.
- `withGlobalTauri` is false, navigation is limited to the app's origin, and the webview cannot open new windows.
- Tauri's own handling of dropped files is off for the main window (`dragDropEnabled: false`), so the page receives a drop: the message box takes image files for an image source, a plugin's view may take the files dropped on it, such as the sources of a notebook, and the shell refuses files dropped anywhere else ([ADR-0033](../adr/0033-let-plugins-attach-images-to-the-owners-messages.md)).
- Content Security Policy: `default-src 'self'`; `script-src 'self'`; `style-src 'self'`; `img-src 'self' data: blob:`; `connect-src` limited to Tauri's IPC endpoints (`ipc:` and `https://ipc.localhost`); `object-src`, `frame-src` and `base-uri` set to `'none'`. Tauri adds the hashes of the inline bootstrap script that SvelteKit writes. V1 validates the policy with the full component stack; its [results](../roadmap/m0-validation.md) record what the policy blocks and how the app lives with it:
  - SvelteKit's route announcer and bits-ui's command wrappers carry static inline `style` attributes, which the policy blocks. `src/app.css` gives these elements the same presentation through selectors.
  - mode-watcher's inline head script is turned off. `static/theme.js`, a file the policy allows, applies the saved theme before the first paint.
  - SvelteKit fetches `_app/version.json` when the window gains focus, to notice a new deployment; `connect-src` refuses it, and nothing depends on it.
- The main window is at least 800 pixels wide, so the sidebar never switches to its narrow-screen sheet, whose text is built into the component ([patches](../../apps/desktop/src/lib/components/ui/PATCHES.md)).
- `useHttpsScheme` is true and stays true, so the app's origin, and with it the webview's storage, never moves.
- The isolation pattern is not used. [ADR-0004](../adr/0004-keep-system-access-in-the-rust-core.md) explains why.

## 5. Rendering untrusted content

- Model and tool output is parsed as Markdown by micromark and rendered by Mannie's own components, which bind text and never insert markup ([ADR-0021](../adr/0021-render-model-output-as-markdown-with-micromark.md)). Raw HTML shows as literal text. Code blocks render as text, with a copy button.
- Images in model output are never loaded; a placeholder shows their description and their address as a link. A link is a button without an address: clicking it asks the core, which checks the URL (http and https only) and returns it normalized; a dialog shows it, and the core opens it in the system browser only after the owner confirms.
- Text within cheap bounds is parsed on the main thread; longer or denser text is parsed in a worker with a time limit, after which it shows as plain text. While a reply streams, it is parsed at most once per frame.
- File contents and command output render as plain text, never as HTML.
- [M1](../roadmap/milestones.md#m1-chat) proves this with a corpus of hostile Markdown and HTML that a provider sends through the real path: it runs no script, loads nothing and connects nowhere.

## 6. Frontend structure

The frontend is sorted by kind: components sit with components, state with state, and helpers with helpers.

```text
apps/desktop/
├── messages/                    # message catalogs, one file per locale; en.json is the base (ADR-0019)
├── project.inlang/              # the Paraglide project: locales, plugins and Paraglide's options
├── static/theme.js              # applies the saved theme before the first paint
├── src/
│   ├── app.css                  # Tailwind CSS, the theme tokens, and the styles the policy blocks inline
│   ├── routes/                  # top-level views only; the root layout loads what the window needs
│   └── lib/
│       ├── components/
│       │   ├── ui/              # shadcn-svelte CLI output only (ADR-0006), plus PATCHES.md
│       │   └── app/             # Mannie's components, composed from ui/ and bits-ui
│       │       ├── shell/       # the shell: frame, sidebars, command palette, settings pages and startup views
│       │       ├── markdown/    # model output as Markdown, and the confirmation of links (ADR-0021)
│       │       ├── chat/        # conversations, the transcript's parts, provider profiles and instructions
│       │       ├── tools/       # tool calls and their approvals, permissions, rules and the tools settings
│       │       ├── child-agents/  # the cards of tasks and the child agents settings
│       │       ├── plugins/     # the Plugins settings and the way to them
│       │       └── window-and-tray/  # the questions about closing, and the window settings
│       ├── state/               # state modules: the shell's slots, settings, conversations, profiles, the window's questions
│       ├── utils/               # helpers: messages for error codes, the transcript's reducer, Markdown, calls, ordering
│       ├── types/               # shared types: the slot entries, command outcomes, the settings failures
│       ├── registrations/       # what fills the slots: the shell's entries, chat.ts, window-and-tray.ts, composeShell()
│       ├── sdk/                 # the TypeScript plugin SDK, @mannie/plugin-sdk and its parts (ADR-0034, decision 11)
│       ├── validation/          # the validation harness, which only validation builds load
│       ├── generated/           # IPC bindings, the plugins' envelopes and transport, and the plugin lists, generated and never committed
│       └── paraglide/           # message functions compiled from messages/, never committed
├── core/                        # mannie-desktop-core: the composition root, the IPC commands in src/commands/, the window and tray
└── src-tauri/                   # mannie-desktop: Tauri's configuration, build script, capabilities and icons, and main.rs
```

- An area's files carry its name inside each kind folder. The shell's components are in `components/app/shell/`, its slots in `state/shell-slots.svelte.ts`, and its entries in `registrations/shell.ts`. A feature adds its components in `components/app/<feature>/`, its state in `state/`, its helpers in `utils/`, and its registration in `registrations/<feature>.ts`, which it lists in `registrations/features.ts`.
- A plugin's UI lives in its folder's `ui/`, sorted by kind the same way, such as `plugins/workers/ui/components/` and `ui/state/workers.svelte.ts`. Its `index.ts` exports `definePlugin(...)`, and `ui/generated/` holds its bindings, its constants and the barrel of its own messages, which `task gen` writes. It imports only the SDK, `@mannie/plugin-sdk` and its parts such as `/slots`, `/ipc`, `/components/<name>` and `/icons/<name>`, Svelte and its own files ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 11). The composition root imports the plugin list that `task gen` generates, `#plugin-list`, which names every plugin and carries the definitions, with the fixture plugins in validation builds ([ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decision 7). The lint rule `mannie/plugin-boundaries` and a Vite plugin refuse any other import across these boundaries, and the lint rule also refuses a plugin's message key in the core's files (decision 6).
- Components that are not CLI output live in `components/app/` ([ADR-0006](../adr/0006-use-shadcn-svelte-through-its-cli.md)): shared compositions directly in it, and each area's components in a folder of their own.
- The app imports its own modules through the `#lib/*` subpath import, which SvelteKit 3 uses in place of `$lib`.
- The root layout's load function asks the core whether it started and loads the interface settings with their locale before anything renders.
- `composeShell()` creates the shell's slots, registers the shell's own entries (the interface settings and the commands for the settings and the theme), then calls each feature's registration, then each plugin's `register` with the plugin's context: its own view of the slots, whether it is on, and `whileOn`, through which its state follows the plugin. The shell renders whatever the slots hold and never imports a feature. A slot shows a plugin's entries only while the core reports the plugin as on, which the shell follows through the channel of plugin states from its start ([extension points](extension-points.md#37-ui-shell-slots)).
- The sidebar holds the activity bar, whose buttons are the navigation entries with Chat first, and "Find a command" and "Settings" at its foot, beside the content sidebar of the selected entry. Ctrl+B collapses the sidebar to the bar. The selected entry and the main area's address under each entry live in `state/activities.svelte.ts`, kept in the webview's storage ([ADR-0045](../adr/0045-switch-the-sidebar-between-views-with-an-activity-bar.md)).
- The settings are a page of their own (`/settings`). The shell then shows the settings sidebar in the content column, and the activity bar stays: a link back to the main view as the owner left it, and a page per settings section, which the `section` search parameter selects.
- Side panels open beside the main view, in a resizable split that keeps its size in the webview's storage, or over the view when the main area is narrower than 720 pixels ([ADR-0025](../adr/0025-add-side-panels-to-the-shell.md)). The main view's address holds the open panels, one `panel` search parameter each, and the visible one in `shown-panel`, so a view that opens other content leaves them behind, the settings lead back to them and a reload shows them again. `state/side-panels.svelte.ts` opens, shows and closes them and moves the focus.
- State lives in `.svelte.ts` modules in `state/` that use runes. Each open conversation has a state object that its channel subscription feeds.
- Components are small and do one thing. A view composes feature components through the shell's slots instead of importing features directly.
- Styling uses Tailwind CSS utilities and the theme tokens of shadcn-svelte, without hard-coded colors or per-feature global stylesheets.

## 7. Window and lifecycle

- The single-instance plugin focuses the running window when the app starts a second time, and shows it again if it was hidden in the tray.
- On the first close of the main window, Mannie asks whether to keep running in the system tray or to quit, and saves the answer as a setting that the owner can change later (D13). The [window and tray](../features/window-and-tray.md) feature describes the behavior.
- The core decides what a close does. When it needs the owner, it shows the window and asks over the window's channel; when no window can answer within 5 seconds, for example because its page failed to load, Mannie quits.
- In tray mode, closing the window only hides it. Runs, channels in the core and the plugins that are on continue, and the tray icon's menu opens the window again or quits.
- In quit mode, closing the window quits the app. While runs are active, Mannie warns first, and so does Quit in the tray menu. Quitting interrupts the master's runs, which can be retried. Tasks on workers keep running on their workers.
- Quitting ends the event loop, then shuts the core down: the runtime marks active runs as interrupted and waits up to 3 seconds for them, the plugin host stops the plugins that are on, as turning them off does, and keeps the owner's choices, the store writes what it holds, and the logs flush. A process that is killed instead leaves the recovery to the next start.
- The tray icon uses Tauri's `tray-icon` feature, which is part of Tauri itself and not a plugin. It appears once the window gives it its labels from the catalog, and Mannie runs without it when the system has no tray.
- Validation builds, which only the end-to-end tests run, open the window off every screen, without a taskbar button and without the focus, so a test run leaves the owner's screen and keyboard alone. `MANNIE_E2E_SHOW_WINDOW=1` shows it.
- After the computer resumes from sleep, provider calls that failed while it slept count as transient errors and are retried. With the Workers plugin on, the link to each worker reconnects.

## 9. Accessibility

The app meets WCAG 2.1 AA. Every action works from the keyboard, focus is always visible, and automated axe checks run in the end-to-end tests. shadcn-svelte and bits-ui provide the base behavior, and Mannie's own components keep it.

## 10. Languages

The interface is in English, and it is built so that a language can be added without changing code ([ADR-0019](../adr/0019-keep-visible-text-in-message-catalogs.md)):

- Every piece of visible text comes from the message catalogs in `apps/desktop/messages/` and in each plugin's `messages/`, whose keys all start with the plugin's prefix. `task gen` writes an inlang project in `apps/desktop/.generated/` that lists the core's catalog and then each plugin's, and Paraglide JS compiles them into one catalog of typed message functions for each locale ([ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md), decision 8). Components contain no literal text, and each feature owns the messages under its key prefix.
- The core sends codes and arguments, never display text. Content (model output, file contents, command output, the owner's own text) is shown as it is.
- Dates, times, numbers and durations are formatted with `Intl` in the current locale.
- The locale is a setting in the core, defaulting to the operating system's language when a catalog exists for it and to English otherwise. A custom Paraglide strategy reads it at startup. Changing it reloads the webview, which does not affect runs.
- The end-to-end tests also run in a pseudo-locale that marks and lengthens every message, so text that bypasses the catalog and layouts that break under longer text are caught.
- Adding a language means adding `messages/<locale>.json` and registering the locale in `project.inlang/`. A check reports keys that a locale is missing.

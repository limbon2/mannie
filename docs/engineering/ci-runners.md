Every workflow uses standard GitHub-hosted runners. Mannie's repository is public, so these runners have no minute charge. No job depends on the owner's workstation, a local controller or a registered self-hosted runner.

## 1. Where the jobs run

| Work                                                                          | Runner                                         |
| ----------------------------------------------------------------------------- | ---------------------------------------------- |
| Windows checks, end-to-end tests, service tests, installer and worker archive | `windows-2025`                                 |
| Linux checks, credential stores, service tests and static worker archive      | `ubuntu-24.04`                                 |
| Linux desktop packages and end-to-end tests on the oldest supported WebKitGTK | `ubuntu-22.04`                                 |
| FreeBSD tests, native worker build and install check                          | FreeBSD 14.4 virtual machine on `ubuntu-24.04` |
| Signatures, checksums, SBOMs, notices and draft release                       | `ubuntu-24.04`                                 |

GitHub provides a fresh machine for each job. The FreeBSD jobs start a virtual machine through the pinned [FreeBSD VM action](https://github.com/vmactions/freebsd-vm). The worker is built inside FreeBSD, as [ADR-0018](../adr/0018-release-from-tagged-builds.md) requires. Desktop builds target Windows and Linux; FreeBSD runs the headless worker.

Windows browser automation runs with restricted privileges at medium integrity. This uses the installed WebView2 runtime and its matching EdgeDriver. Verified on 2026-10-21: [WebView2 blocks its debugging endpoint for elevated applications](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5639). The helper gives the runner account write access to the checkout so the end-to-end runner can write failure diagnostics and performance reports under `target/`.

## 2. Running the pipeline

- Pull requests and pushes to `main` run `CI`: the checks of `task ci` on Windows and Linux, a single validation-app build per webview followed by balanced end-to-end shards, the credential stores (GNOME Keyring, KWallet and no Secret Service in one job), the plugin programs' service tests and cross-builds, and the core's FreeBSD checks. A failed job stops no other, so one run reports every failure. A new push cancels the obsolete run for that branch.
- The checks of `task ci` run as the groups of `scripts/ci.mjs`, each in a job of its own, and a job's name is the command that repeats it on a workstation, such as `task ci -- core`:

  | Group     | Checks                                                                                                          | Builds                                        |
  | --------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
  | `static`  | The documentation, the tests of the scripts, the contracts, the TOML files, the formatting and the dependencies | Nothing                                       |
  | `desktop` | ESLint, svelte-check, the message catalogs, Vitest and the Rust tests of the desktop binary, after `task gen`   | The bindings' programs and the desktop binary |
  | `clippy`  | Clippy in every workspace and the launcher, after `task gen`                                                    | The bindings' programs                        |
  | `core`    | The Rust tests and doctests of the root workspace                                                               | Its tests                                     |
  | `plugins` | The Rust tests and doctests of each plugin's workspace                                                          | Their tests                                   |

  Windows runs one job for each group. Linux builds about twice as fast, so `desktop` and `clippy` share one job and `core` and `plugins` another. A test of the script fails when a step of `task ci` belongs to no group, or when a platform's jobs miss a group. On pull requests and pushes that touch no Cargo manifest, lockfile or `deny.toml`, `static` sets `MANNIE_DENY_ALLOW_ADVISORY_CHURN=1` so newly published upstream `unmaintained` and `yanked` notices do not block unrelated changes; vulnerabilities, licenses, bans and sources stay enforced on every run.

- For each webview, `e2e-build` restores the commit's cached binaries when present. On a miss it builds the validation app, the `e2e` plugin programs and the plugin `*-test-server` examples once, then stages those binaries into `target/e2e-bundle`. The job archives the staged binaries and, on Windows, EdgeDriver, preserving executable permissions. The `e2e` shard jobs download the run's artifact without installing Rust or compiling again, set `CARGO_TARGET_DIR=target/e2e-bundle` and `MANNIE_E2E_PREBUILT=1`, and split specs across parts using weight-balanced sharding (`tests/e2e/support/shard.ts`). The artifact is retained for three days so a failed shard can be rerun even if GitHub evicts the optional cache. Each WebDriver session allocates ephemeral driver and native ports and cleans up its driver process tree on exit; failures capture a screenshot, page state and recent app log lines under `target/e2e-failures` and upload them as an artifact retained for three days.
- The `Performance` workflow (`.github/workflows/performance.yml`) runs report-only performance measurements every night and on manual dispatch, reusing the cached `e2e-build` binaries when available and writing both core and terminal measurements to the job log and summary without blocking pull requests or releases.
- The `Dependency audit` workflow (`.github/workflows/dependency-audit.yml`) runs the full strict `task lint:deps` check every day and on manual dispatch so upstream `unmaintained` and `yanked` advisories surface promptly.
- The `FreeBSD` workflow runs native FreeBSD tests for pull requests that change worker code, and `Nightly` runs them every night with retries on `pkg` and `rustup`, one unified worker-crate test build and serial execution for timing-sensitive tests.
- The `Release` workflow can be run manually from the Actions page. It builds the Windows installer, Linux packages and worker archives for all three platforms, runs the checks and installs the artifacts on fresh machines (Windows, `ubuntu:24.04` and pinned `fedora:45`, verified on 2026-11-24). The unsigned artifacts are downloads on that run, retained for one day. A manual branch build creates no release and receives no signing key.
- Pushing a prepared `vX.Y.Z` tag runs the same release pipeline, then signs the worker archives and creates a draft release after all checks and install tests pass. The draft holds the durable downloads. The owner publishes it after the [release checks](releasing.md#3-steps).
- A release takes its checks from the `CI` run that the push of its commit to `main` started, and waits for that run while it builds. A tag that is pushed with its commit would otherwise run every check twice at the same time. The release runs the checks itself when the commit has no such run, as in a manual build of a branch, and when the run was cancelled, as a later push to `main` does to it (`scripts/ci/commit-checks.mjs`). It always runs the full strict `task lint:deps` check itself, because a tag can follow its commit by days and advisories appear in between.
- For a repair, run the CI workflow manually with scope Rust or end-to-end tests and select the platform. Rust takes Cargo arguments as a JSON array with a package, an exact test or filter, and the locked dependencies. End-to-end tests accept one repository-relative spec file and reuse the cached `e2e-build` bundle when that commit was already built. Develop repairs on a branch without a pull request, then update the pull request once the focused checks pass.
- If code has not changed, use GitHub's Re-run failed jobs instead of starting the whole workflow again. When that repairs the `CI` run of a release's commit, re-run the release's job "Checks of the commit's push to main" afterwards, which then reads the new result.
- The live provider tests and evaluations run separately. Their configured providers can charge for model requests; they do not block a release.

Builds and tests run side by side across jobs. Each job has a timeout. A failed job reports its failing command, and GitHub can rerun that job without repeating successful jobs. Hosted end-to-end tests show their window on the disposable desktop so the webview paints normally. Before the end-to-end suite, one startup check opens a browser session and reaches the app. A driver that cannot start fails that check once; it does not retry the same startup failure for every test file. A cold Rust build can still take tens of minutes; hosted runners remove the local machine queue and maintenance rather than promising a fixed run time.

The groups exist because a runner has four processors, so the steps of `task ci` that build run one after another on it. Measured on 2026-11-09, after a dependency update that left the compiler cache without most of the workspace's crates, the one Windows job that ran every step took 46 min: `task gen` built for 6 min, the Rust tests for 16 min and Clippy for 8 min, and the tests then ran for 11 min. The same job took 18 min on Linux, and each end-to-end job 25 min, 5 min of them for the performance measurements. A dependency problem that cargo-deny found in the first minute showed when the job ended. A release ran all of this twice, once for the push to `main` and once for the tag.

Measured on 2026-11-09 on the branch that introduced the groups. A branch saves no Rust cache, so each of its runs fetched the registry and ran Clippy without its build folder. With an empty compiler cache, and the end-to-end specs still in one job for each webview, a run took 26 min, 24 min of them for the end-to-end job on Windows; the jobs of the groups took 2 to 16 min, and Clippy's on Windows 21 min. The third run, inside a manual release build, finished its checks in 17 min: the core's tests on Windows took 16 min, the two end-to-end parts on Windows 14 and 16 min, the performance measurements on Windows 15 min, Clippy on Windows 14 min, and no job on Linux more than 13 min. The static group took 2 min on Linux and 4 min on Windows in every run. That release build took 22 min with its checks and install checks, 21 min of them for the Windows installer, whose release build no run had cached.

Verified on 2026-11-10 against [GitHub's limits for Actions](https://docs.github.com/en/actions/reference/limits): GitHub Free runs 20 jobs of an account at a time. Further jobs wait: on 2026-11-09, when a release ran every check beside the `CI` run of the same push, some of its jobs started 100 s late. A full `CI` run now starts 13 jobs at once (8 check groups, 2 `e2e-build` jobs, 1 consolidated `credentials` job, `plan` and `core-freebsd`), followed by 4 lightweight `e2e` shards and 4 program jobs after their prerequisites finish. Staying well below the 20-job cap lets a `Release` run start beside `CI` without queueing delays.

## 3. Cost and storage

Verified on 2026-10-21 against [GitHub's Actions billing documentation](https://docs.github.com/en/billing/concepts/product-billing/github-actions):

- Standard GitHub-hosted runner minutes are free in public repositories. Larger runners are charged even for public repositories; no workflow uses one.
- Keep the repository's cache limit at the included 10 GB. Old caches may be evicted, which makes a later build colder rather than preventing it from running.
- The pinned sccache compiler wrapper stores completed Rust compilations in GitHub's cache as they finish, including before a later test fails. Results are keyed by compiler inputs, so unchanged libraries can be reused across fresh runner machines. Clippy's build folder is cached as well, with the dependencies' build scripts and procedural macros, which sccache cannot cache. sccache 0.18.0 stores Clippy's checks of the dependencies too: on 2026-11-09 Clippy's step on Windows took 13 min with nothing cached, and 7 min without the folder once the compiler cache held those checks. The Cargo registry and pnpm package store are cached too.
- Store debug compiler results through sccache instead of keeping a complete build folder for every job. This leaves more room for reusable results within the cache limit.
- Release intermediates expire after one day. Published release files remain in GitHub Releases. Performance measurements go into the job log and summary, which do not consume artifact storage.
- Making the repository private again restores GitHub's private-repository allowances and billing. Reconsider that cost before changing visibility.

Verified on 2026-10-21 against the [sccache GitHub Actions integration](https://github.com/Mozilla-Actions/sccache-action) and [Rust caching limits](https://github.com/mozilla/sccache/blob/main/docs/Rust.md). Compiler caching speeds compilation; tests still execute. A cold compiler cache and linking still take time.

The caches stay useful only while they fit the limit and the runs that need them can read them. Verified on 2026-11-10 against [GitHub's dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching): a run restores the caches of its own branch or tag and of the default branch, GitHub removes the caches that were read longest ago once the repository holds more than its limit, and a repository can add 200 cache entries a minute. On 2026-11-09 the caches that the run of the tag `v0.6.1` had saved, which only that tag can read, held 5.4 GB of the repository's 9.8 GB, and 3,200 of the 3,620 compiler results in the cache were of that day. The workflows therefore keep these rules:

- Only a run on `main` saves the caches of [rust-cache](https://github.com/Swatinem/rust-cache) (`save-if`, verified on 2026-11-10 for v2.9.2). Tags and pull requests restore `main`'s.
- Every job of a platform restores one cache of Cargo's registry, which the `static` job saves, and the job with Clippy restores the registry with Clippy's build folder and saves that. A cache of the registry for each job would hold the same crates many times.
- A release does not repeat the checks of its commit's push, and tagged desktop builds read `main`'s compiler cache (`compiler-cache: read`) so tag-scoped release compilations never evict `main`'s daily cache. The release's `windows-programs` job restores `main`'s Cargo registry cache, and `linux-programs` restores the cached release musl build saved by `CI`'s `program-builds` job on `main`.
- `ci.yml` and `release.yml` set the same variables whose names start with `CARGO_`, and the debug information of dev builds is set in `.cargo/config.toml`. sccache's key of a compilation holds every such variable (`src/compiler/rust.rs` of v0.18.0, verified on 2026-11-10), so a variable that one workflow sets alone keeps it from reading what the other stored. `e2e` shards set `CARGO_TARGET_DIR=target/e2e-bundle` only in jobs that run without Rust or sccache.
- Only one job builds each artifact per platform (`e2e-build` for end-to-end tests, one `credentials` job for all three Secret Service checks), avoiding parallel duplicate compilations and staying inside GitHub's limit of 200 new cache entries a minute. The `performance.yml` fallback build reads the compiler cache (`SCCACHE_GHA_RW_MODE=READ_ONLY`, verified on 2026-11-10 in [sccache's notes on GitHub Actions](https://github.com/mozilla/sccache/blob/v0.18.0/docs/GHA.md)) when no staged end-to-end bundle exists for the commit.

## 4. Security and maintenance

- Every action is pinned by commit SHA, Rust by `rust-toolchain.toml`, and pnpm dependencies by the committed lock. Keep pins current in dedicated dependency changes.
- Jobs have read-only repository access. Only the job that signs and drafts a tagged release gets write access and the release signing key. Pull-request jobs never receive that key.
- Require approval for workflow runs from every outside contributor. Use `pull_request`, never `pull_request_target`, to test their code. The live providers and evaluations run only on their schedules or through an owner's manual run.
- No self-hosted runner serves this public repository. Stop the old Hyper-V controller and remove its runner registrations when switching to hosted builds. Existing VM images can remain powered off.
- Before publication, scan all Git history for credentials and inspect matches. Do not publish a real credential, an owner's runtime database, a private key or a local environment file.

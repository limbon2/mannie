## Intent

The owner wants Mannie's core to hold what every agent harness needs, such as chat, tool use and child agents, and everything else to be a plugin that each owner turns on when they need it. In the owner's words, not everybody needs every feature, so things like a Jira integration, git, a code editor, a terminal, databases and log viewers become plugins that users can enable. The worker system is the first plugin, since only owners with several machines need it. Plugins are built into Mannie for now, and an API or SDK for third-party plugins may follow later.

After Workers and Images, the owner found that each plugin had changed the core, so the plugins felt like modules. In their words, plugins should be self-contained, so that nothing a plugin introduces requires changes in the core: plugins use a plugin SDK, the SDK is the bridge between plugins and the core, and when a plugin needs something that the SDK does not provide, the SDK changes. A third party should be able to add a plugin without doing anything in the core. Third-party plugins stay deferred, but the system should work as it would for them ([D32](../roadmap/milestones.md#5-decisions)).

## Behavior

- Settings has a Plugins page that lists every plugin built into this version of Mannie, each with its name, a sentence on what it adds, what it may use and a switch. What it may use opens below the sentence: the services of Mannie that its manifest declares, the sensitive ones marked, its entries in the credential store, the commands and channels of its window, the programs that ship with it, the libraries that only it may use and its system access outside Mannie's services. It lists Workers and [Images](../../plugins/images/docs/README.md).
- Turning a plugin on takes effect at once, without restarting Mannie. Its parts of the interface appear, such as the Workers group in the sidebar, its settings page and its commands, and replies that start from then on can use its tools.
- Turning a plugin off also takes effect at once. Its parts of the interface disappear, replies that start from then on no longer get its tools, and its background work ends. When the plugin has work in progress, the switch asks first and says what happens to it. For Workers, running tasks keep running on their workers, and Mannie follows them again when Workers is back on.
- A reply that is already running keeps the tools it started with, whatever the owner switches meanwhile. If it calls a tool of a plugin that was turned off, the call does not run, and the model reads that the plugin is off.
- Turning a plugin off keeps its data: its settings, its records and what it added to conversations. Turning it on again continues with that data. While a plugin is off, conversations still show what it added, read from what was stored, and an action that needs the plugin, such as opening a worker task's conversation, says that the plugin is off and links to the Plugins page.
- While a plugin turns on or off, its switch says so. A plugin that fails to start shows as failed, with what failed and "Try again", and the rest of Mannie keeps working.
- Each plugin on the Plugins page also shows what it may use: the core services it declares, with sensitive ones such as provider credentials marked, its secret entries, its commands and channels, the programs it ships, the third-party crates that only it may use, and its allowed exceptions to the core's rule against direct process, file and socket calls.
- Turning a plugin off waits up to 5 seconds for its commands and tool calls in progress, then stops them. A tool call stopped this way is reported as uncertain, as after a crash, and never runs again.
- Each switch is the owner's lasting choice. Mannie starts the plugins that are on when it starts, and quitting keeps the choices.
- A new installation starts with every plugin off. After the update from 0.2.0, Workers is on when at least one worker is paired, so an owner who uses workers keeps them, and off otherwise.
- Not included: installing, updating or removing plugins apart from Mannie, which ships them; plugins from anywhere but Mannie's own repository; removing a plugin's data; turning a plugin on for one project or conversation only; plugins on a worker's host.

## Fit

- Follows [ADR-0030](../adr/0030-split-mannie-into-a-core-and-plugins.md) for what a plugin is and how it starts and stops, [ADR-0031](../adr/0031-move-workers-into-the-first-plugin.md) for the extension points that let workers become a plugin, [ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md) for the SDK that plugins build on, and [ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md) for where a plugin's code lives and how the build finds it.
- Extension points: settings sections (the owner's choices), UI shell slots (the Plugins page, and the plugin that each entry belongs to), IPC commands and a channel of plugin states, and messages under the `plugins_` prefix.
- Every later plugin follows this feature: it gets a switch on the Plugins page, starts and stops at once, keeps its data while off, and has a feature document of its own.
- Must not change: the core behaves the same whatever plugins are on, and Workers behaves as it does in 0.2.0 while it is on.

## Design

### The host and its states

A plugin implements the SDK's definition, and `mannie-plugins` holds the host ([ADR-0030](../adr/0030-split-mannie-into-a-core-and-plugins.md), decision 4; [ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decision 4). The desktop app's composition root lists the plugins with their manifests, hands the host the core's providers of services and consumers of extension points, and runs it. The host lists the plugins in their manifests' order and binds each one the services that its manifest declares and no other.

- A plugin's state is `off`, `starting`, `on`, `stopping` or `failed`. The host makes one change at a time, and a change that arrives while another runs waits for it.
- Turning a plugin on stores the choice first, then starts the plugin, whose contributions go to the runtime; a start that fails leaves the plugin `failed` with a code, and the choice stays on, so "Try again" starts it again. Turning it off stores the choice, drops the contributions, then stops the plugin.
- The host's own failure codes are `sdk_incompatible`, for a plugin built for another major of the SDK, whose code never runs and whose default is never asked; `service_unavailable`, for a declared service that no provider offers at its major or that its provider refused to bind, such as a store module whose statements did not prepare; `grant_missing`, for a start that asks for a service that its manifest does not declare; and `contributions_refused`, for contributions that the core refuses: an ID that is taken or that breaks its extension point's rule, a tool's name or schema that the core does not accept, or a contribution to a point that no part of the core takes ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md), decisions 5 and 6). The core takes all of a plugin's contributions or none, and a refused start stops the plugin's instance. A plugin adds codes of its own, which it words in its UI registration.
- Quitting stops the plugins that are on, after the runtime, and keeps the owner's choices.

### Contracts

- IPC: `subscribe_plugins` follows the list of plugins through a channel, whose messages carry the whole list after every change and end with `lagged` or `shutdown`; `set_plugin_enabled` turns a plugin on or off and returns its view; `plugin_work` returns the plugin's work in progress as items, each a code of the plugin's and a count, which the plugin's UI words, as the plugin's running instance reports them, with no item while the plugin is not on and none whose count is 0. A plugin's view has its ID, its state, the owner's choice, the code of a failed start, and `uses`: the services that its manifest declares, each with its major and whether it reaches sensitive data, its entries in the credential store as the store names them, the commands and channels that its interface declares, which the build grants its UI, the packages of its programs, the crates that only it may use, and the categories of direct native calls that its manifest grants under `[native]`. The errors are `unknown_plugin`, `storage_failed`, `store_unavailable` and `shutting_down`.
- The error `plugin_off` names the plugin in chat's and tools' errors, the host answers it for a plugin's commands while the plugin is off, and the host ends a plugin's channels with the reason `plugin_off`, or `shutdown` when Mannie quits. A plugin's command fails with a `PluginFailure`: a refusal of the host, with `origin: host` and one of the codes `plugin_off`, `store_unavailable`, `shutting_down`, `unknown_command`, `invalid_input`, `input_too_large`, `host_service_failed` and `not_allowed`, or the plugin's own error, with `origin: plugin`. The core words the host's refusals with messages under `plugins_host_`.
- A call of a stopped plugin's tool ends with the reason `plugin_off`, and the model reads: Not run: the owner turned off the plugin "workers", which this tool belongs to. Continue without it, or tell the owner. A call for a task of the plugin's executor reads the same with the task's number.
- A call of a plugin's tool that ran has the outcome `plugin` with the plugin's ID. The model reads the tool's output, cut to the result limit with a note that says so, and the UI names the call by its tool.

### Data

- The owner's choices are the core's settings section `plugins`: the choice for each plugin by its ID.
- The store records the migrations of each module in `store_modules`, and a database from before M5 keeps its `user_version` in `store_legacy`, so a module that a later version registers still carries over its migrations ([extension points](../architecture/extension-points.md#39-store-tables-and-migrations)).
- The core keeps the executors' columns of `runtime_tasks` and `runtime_conversations` and the outbox `runtime_executor_outbox` ([orchestration](../architecture/orchestration.md#4-task-executors)).

### Interface

- The Plugins page lists the plugins in their manifests' order, each with its name, its description, "What it may use", which opens the list from the keyboard, and a switch, which shows "Starting…" or "Stopping…" while the plugin changes. A failed plugin shows what failed with "Try again". Turning off a plugin with work in progress opens a question that says what happens to the work, with "Turn off" and "Cancel".
- The slots show a plugin's entries only while the plugin is on. An address of a view, a settings page or a side panel of a plugin that is off shows that the plugin is off, with "Open the Plugins settings", and a task conversation that cannot be followed while its plugin is off says so and follows again once the plugin is on. A failed Stop or approval answer for a task of a plugin that is off has the same link beside its message.
- Messages: `plugins_` for the Plugins page, its states and errors and the state of a part of a plugin that is off; a plugin's name, description, question and failures under its own prefix.

### Threat notes

- Internal plugins run with the core's rights. A plugin reaches the credential store only in the entries that its manifest lists and provider credentials only through the core's lender, as its manifest declares (T-30 in [security](../architecture/security.md#5-threats-and-mitigations); [ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md) d5, d13).
- A plugin that is off can act through nothing: its contributions leave first, its tools do not run, its commands refuse and its channels end (T-31).
- A plugin's statements and migrations reach only the tables of its own prefix: an SQLite authorizer confines them, the store compares the schema outside the prefix after each plugin migration and refuses any change there and any foreign key to a table outside it, and plugin statements are always prepared fresh. The one exemption is Workers' migration 4, which may insert into the core's outbox and is pinned by the SHA-256 of its text ([ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md) d7).
- All plugin UI runs in one JavaScript realm, and Tauri's ACL limits calls by window, so one plugin's UI could call another plugin's commands. Lint, a Vite check and review keep each plugin's UI to its own commands until plugin UI moves into frames (T-35, [ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md)).

### Plugin SDK

[ADR-0034](../adr/0034-build-plugins-on-a-plugin-sdk.md) defines the SDK and [ADR-0035](../adr/0035-find-plugins-at-build-time-in-folders-of-their-own.md) the plugin's folder and the build that finds it. Once both are in place, a plugin is `plugins/<id>/` alone: its manifest, its Cargo workspace and lock, its crates and programs, its UI, messages, tests and documents. Its Rust code depends on `mannie-plugin-sdk`, its tests also on `mannie-plugin-harness`, its programs also on `mannie-host-kit`, and its UI on `@mannie/plugin-sdk`. `task gen` writes every list that names plugins into git-ignored folders. The manifests then give the plugins and their order in place of the composition root's list, declared services replace the grants, the definition and the start context move into the SDK while `mannie-plugins` stays the host, and the host's start failures add `sdk_incompatible` and `service_unavailable`, with `contributions_refused` also for a contribution to a point that has no consumer. Each plugin's entry on the Plugins page lists what its manifest declares, from a new `uses` field of the plugin's view, worded by messages under `plugins_`.

## Acceptance

- The host starts plugins in order after recovery, keeps a default as the choice, takes a change at once and keeps it, leaves a failed start failed until "Try again", stops the plugins that are on when Mannie quits, and counts a plugin's work (`crates/mannie-plugins/tests/host.rs`).
- A plugin's tool, agent and section reach the runs that start while it is on; a run keeps what it started with and its calls into a stopped plugin do not run; the runtime takes all of a plugin's contributions or none (`crates/mannie-runtime/tests/plugins.rs`).
- The store keeps the records of each module, refuses two modules with one name, carries over the migrations of a module registered after the conversion, and opens a module's store only to its modules (`crates/mannie-store/src/store/tests.rs`).

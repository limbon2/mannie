## Intent

Give agents one tool for each thing that they do with git, with arguments that say what they mean and results that they can read without parsing git's output, within the room of a tool result.

## Behavior

### Every tool

- A tool is offered where the conversation's project folder, or a folder above it, holds `.git`.
- `repository` names the folder of the repository, relative to the project's folder or absolute; without it, the project's folder. git finds the repository's top from there.
- Revisions, such as `main`, `HEAD~2`, `v1.0` or `abc1234`, are checked in the preparation: one that starts with `-` or holds white space is refused, so no argument reads as an option. A tool resolves each revision to its commit's full hash before git reads it, and one that names nothing fails with `unknown_revision`.
- Paths are relative to the repository's top and are matched literally, never as patterns, unless a tool says otherwise.
- A result says what it left out and how to get it, such as "call git_diff with offset 40 for the next ones". Tools that page fill the room of the result first; output that still does not fit is archived for `read_tool_output`.
- Submodules show only which commit they are at. A read never looks inside one, since git would run there with the submodule's own configuration.
- A failure names its code, such as `not_a_repository`, `git_missing`, `git_too_old`, `unknown_revision`, `dubious_ownership`, `identity_missing`, `locked`, `repository_changed` or `git_failed`, with what git said and what to do.

## Design

### Accesses

Each preparation runs git to read where the repository is and what it holds, and returns:

- for a read tool: the read of the repository's top, and of its git folder and its alternates where they lie outside it;
- for a change: the write of the repository's top, with a state that names HEAD, its branch, a hash of the index's entries, the operation in progress and the commits of the other refs that the change works with; the writes of its git folders that lie outside the top; and a program access when the change runs hooks or programs that the repository's configuration names, discards work, rewrites commits that a remote-tracking branch holds, or reaches a remote ([approvals](approvals.md)). The index counts by its entries and not by its file's time, which editors refresh on their own.

The execution plans the change again, with the repository locked against the plugin's other changes, and fails with `repository_changed`, running nothing, when the plan gives other accesses than the allowed ones: the state moved, or a hook, a discarded file or a published commit came or went.

### Contracts

- Each tool's arguments are a Rust type with a JSON Schema from schemars; every field is required and an optional one takes `null`, as the providers' strict mode needs.
- Each result is text for the model and data for the card (ADR-0039): the status, commits, files with their hunks, refs, conflicts or what a transfer sent, as JSON within 64 KiB.

### Cards

The plugin's interface registers a tool kind for each tool (`plugins/git/ui/index.ts`): an icon, a line from the call's data or arguments, the sentence of each failure code, and the card's details:

- `git_status`: the conflicted, staged, unstaged and untracked files.
- `git_log`: the commits, the commits of a line's history, or the commits that a reflog's entries name.
- `git_show`, `git_diff` and `git_commit`: the changed files with their line counts, each opening to its patch; a single file starts open.
- `git_conflicts`: the conflicted files, and the hunks of the file that the call named, with their current, base and incoming lines.
- `git_refs`: the branches with their upstreams, the remote branches and the tags.
- `git_grep`: the matching lines with their revisions, paths and numbers.
- `git_fetch` and `git_push`: the remote-tracking branches that a fetch moved, or the refs that a push updated; a pull shows how its merge or rebase ended.
- `git_merge`, `git_rebase`, `git_cherry_pick`, `git_revert`, `git_stash` and `git_operation`: the commits that a completed operation made, or the conflicted files of one that stopped.
- The other tools show their icon and line only.

### The text the model sees

The descriptions of the tools and the section live in `plugins/git/crates/mannie-git/src/texts.rs`, reviewed like code, with a test that keeps the definitions of all the tools within a budget of tokens.

## Acceptance

- Each tool against a real repository that the test builds, on Windows and Linux, with git 2.40 and the newest git (`plugins/git/crates/mannie-git/tests/`).
- The arguments: revisions and paths that start with `-`, magic pathspecs, `..` and absolute paths outside the repository are refused or stay literal.
- The budgets: a diff larger than the room continues with `offset`, and long output is archived.
- The cards: their lines and data readers for every tool and failure code, and their details rendered from data (`plugins/git/tests/ui/`), and a status, a hooked commit, a push and a commit's patch in the running app with axe in both themes (`plugins/git/tests/e2e/git.test.ts`).
